# 性能与内存专项分析报告

> 范围:商品数据链路(加载 → 存储 → 查询 → 渲染)在 **10 万条商品**规模下的内存占用与界面性能。
> 方法:代码走查 + 可复现基准实测(非纯推断)。
> 结论对应改造计划:**批次 1 ~ 批次 5**(见第 7 章)。

---

## 1. 结论摘要

| # | 结论 | 严重度 | 实测证据 |
| - | ---- | ------ | -------- |
| 1 | **10 万条商品当前根本无法加载**:文件体积 8.39 MB 超过程序内 8 MB 上限,被整体跳过,商品区显示为空 | P0 功能阻断 | 基线 D + `GenerateProducts.ps1` 输出 |
| 2 | 加载瞬间累计分配 **195 MB** 托管对象,是最终数据的 **8.4 倍**;最终只需 23 MB | P0 | 基线 B vs 基线 C |
| 3 | 解析在 **UI 线程**同步执行,进程冻结约 **1 秒**(且随规模线性增长) | P0 | 基线 A/B 耗时 + `LoadAsync` 续体分析 |
| 4 | 搜索/切分类触发 `ListCollectionView.Refresh` → 虚拟化面板 **Reset 时丢弃全部可视容器且不回收入池** | P0 | `VirtualizingWrapPanel.cs:235-237` |
| 5 | 关键字搜索单次全量过滤 **34 ms**(超过一帧 16.7 ms),搜索过程明显掉帧 | P0 | 基线 H / 基线 I |
| 6 | 扫码查找是 **O(N) 线性扫描**,最坏单次 5.73 ms,并随数据量线性恶化 | P0 | 基线 E / 基线 F |
| 7 | 中间表示(逐行 `Dictionary<string,string>`)单独保留即需 **110.5 MB**,是商品实体的 4.8 倍 | P0 根因 | 基线 A |
| 8 | `PosRepository.Products` 暴露可变 `List<Product>`,并已被 `ListCollectionView` 反向绑架(见源码注释) | P1 架构 | `PosRepository.cs:26-32` |
| 9 | 监控页待处理报文队列无上限、指标 key 逐帧拼接字符串 | P1 | `DeviceMonitorViewModel.cs:36 / 280` |

**一句话总结**:当前 47 行演示数据下"看不出来"的性能设计,在 10 万规模会同时踩中
**文件上限拒载 → 解析内存峰值 8 倍 → UI 线程冻结 → 过滤超帧 → 容器全量重建** 五个点,
其中第 1 点是功能阻断,不解除就谈不上性能优化。

## 2. 验证方法与可复现性

### 2.1 数据生成

```powershell
# 生成 10 万条商品到 Data/large/products.md（不覆盖 47 行演示数据）
pwsh -File tools/GenerateProducts.ps1
```

脚本输出实测:

```
已生成 100,000 条商品 -> ...\Data\large\products.md
文件体积：8.39 MB（当前程序内 8 MB 上限：会触发跳过）
```

> `Data/products.md`(演示数据)保持 47 行不变,大文件落在独立子目录 `Data/large/`,
> 不影响应用正常启动,也不参与 `csproj` 的 `Data\*.md` 复制(非递归通配)。

### 2.2 性能基准

```powershell
dotnet test tests/CommunityToolkitDemo.Tests/CommunityToolkitDemo.Tests.csproj `
  --filter "FullyQualifiedName~Performance" `
  --logger "console;verbosity=detailed"
```

基准位于 `tests/CommunityToolkitDemo.Tests/Performance/`,共 14 个用例:

| 文件 | 内容 |
| ---- | ---- |
| `TestProductData.cs` | 按 `Data/products.md` 字段约定生成 10w 行;复刻生产 `MapProduct` 映射语义 |
| `LoadBenchmarkTests.cs` | 基线 A ~ D:解析内存/耗时 + 文件上限行为 |
| `QueryBenchmarkTests.cs` | 基线 E ~ J:扫码查找、分类/关键字过滤、`ListCollectionView.Refresh`;批次 2 起新增指标 E'(索引构建) / E''(索引内存) / G'(分类切片),并把 E/F 改为**同轮线性对照** |
| `PerformanceTestCollection.cs` | 禁用并行(内存测量依赖进程级 GC 状态,并行会互相干扰) |

### 2.3 测量口径

- **耗时**:`Stopwatch`。单次查找类取 100 次平均;全量扫描/视图刷新类取 5 轮**最优值**
  (同条件下机器负载可造成 3 倍波动,取最优值更接近算法本身成本,前后对比才可复现)。
- **保留内存**:`GC.Collect() ×2 + WaitForPendingFinalizers` 后 `GC.GetTotalMemory(true)` 的差值。
  反映结果对象稳定的稳态占用,但会被"测量期间恰好触发的 GC"干扰(这正是基线 A/B 数值出现
  "分配更多反而保留更少"假象的原因)。
- **总分配**:`GC.GetTotalAllocatedBytes()` 差值。累计分配量,**不受 GC 时机影响**,
  是判断"内存峰值来源 / GC 压力"的可靠指标。

> **测量局限**:本轮为 **Debug** 构建(未内联、未优化),绝对耗时高于 Release。
> 本报告用于对比的**同类操作**与**内存分配量**不受影响;批次 5 会用 Release 复测并更新结论。

## 3. 实测基线数据

### 3.1 加载路径

| 编号 | 场景 | 耗时 | 保留内存 | 总分配 |
| ---- | ---- | ---- | -------- | ------ |
| A | 仅解析为字典(10w 行,保留全部中间表示) | 618.8 ms | **110.5 MB** | 185.0 MB |
| B | 解析并映射为 `Product`(生产实际路径) | 943.3 ms | 84.7 MB | **195.4 MB** |
| C | 仅构造 `Product` 实体(无任何中间表示) | 156.9 ms | **23.2 MB** | 29.4 MB |
| D | 12w 行文件(10.09 MB)> 8 MB 上限 | 23.6 ms | — | — |

**基线 D 输出**:`数据文件过大（10 MB），已跳过：products.md` → `Products` 为空。

**推论 1(峰值)**:B 的总分配 195.4 MB ÷ C 的保留 23.2 MB ≈ **8.4 倍**。
解析只产出 23 MB 数据,却制造了 195 MB 托管对象。

**推论 2(根因)**:A 的保留内存 110.5 MB 是 C 的 **4.8 倍**。
即"逐行 `Dictionary<string,string>`"这一层中间表示本身就是商品实体的近 5 倍体积。

**推论 3(上限临界点)**:实测 0.839 KB/行 → 8 MB 约对应 **9.5 万行**。
**10 万行恰好越过临界点**,这是"加载到 10w 之后界面性能瓶颈"最先撞上的墙。

### 3.2 查询/过滤路径

| 编号 | 场景 | 耗时 | 备注 |
| ---- | ---- | ---- | ---- |
| E | `FindByBarcode` 线性扫描(命中末位,最坏) | **5.7299 ms** | 100 次平均;平均命中约 3 ms |
| F | `FindByCode` 线性扫描(命中末位,最坏) | **3.7871 ms** | 100 次平均 |
| G | 分类过滤全量扫描(纯遍历) | 6.4 ms | 命中 14,286 条 |
| H | 关键字过滤全量扫描(纯遍历) | **33.5 ms** | 命中 4,000 条 |
| I | `ListCollectionView.Refresh`(全部 + 关键字,最坏) | **34.8 ms** | 首次 35.7 ms |
| J | `ListCollectionView.Refresh`(切到单一分类) | 5.0 ms | 首次 6.0 ms |

**推论 4**:基线 I(34.8 ms)与基线 H(33.5 ms)几乎一致 →
`ListCollectionView` 自身的调度开销很小,**成本几乎全部来自过滤算法本身**。
因此"关键字搜索卡顿"的第一性原因是"每次全量扫描 10w 项 + 非向量化字符串比较",而不是集合视图。

**推论 5**:基线 J(切分类)仅 5.0 ms → **分类过滤本身并不慢**。
"切分类卡顿"的主要来源不是过滤算法,而是它触发的 **Reset 导致可视容器全部重建**(见 4.4),
这部分开销无法在无 UI 的基准中量化,需要 UI 侧验证。

**帧预算对照**:60 fps 的单帧预算是 16.7 ms。基线 H/I 单次已达 **2 帧预算**,
叠加容器重建后,搜索过程中的掉帧是可感知的。

## 4. P0 瓶颈详析

### 4.1 P0-1 · 8 MB 文件上限让 10w 数据"整体跳过"

**位置**:`Services/MarkdownDataService.cs` → `MaxDataFileBytes = 8 * 1024 * 1024` 及加载前置校验。

**现象**:不是"加载很慢",而是**一条都不会加载**。10w 行文件 8.39 MB > 8 MB,
校验失败后记录 `数据文件过大（8 MB），已跳过：products.md`,仓储保持为空。

**根因**:
- 用"文件字节数"作为安全护栏,但**字节数与行数强相关于列宽/字符集**,不是一个稳定的规模度量;
- 8 MB 恰好落在目标规模(10w)之下,护栏与需求直接冲突;
- 上限是硬编码常量,无法按部署环境调整。

**影响**:功能阻断。商品区空白 → 收银不可用。

**方向**:上限改为"可配置 + 按行数/预估内存的软限制",或改为**流式读取**后不再受整体字节数限制
(流式方案可同时解决问题 4.2/4.3,是首选)。

### 4.2 P0-2 · 解析期内存峰值 ≈ 稳态的 8.4 倍

**位置**:`Services/MarkdownTableParser.cs` → `ParseFirstTable` / `ParseFirstTable<T>`;`Services/MarkdownDataService.cs` 读取段。

**分配链条(逐条叠加)**:

| 步骤 | 代码 | 产生的对象 |
| ---- | ---- | ---------- |
| 1 | `File.ReadAllTextAsync` | 整份文本驻留内存(UTF-16,约文件体积 2 倍) |
| 2 | `.Replace("\r\n", "\n").Replace('\r', '\n')` | **每次 Replace 新建一整份字符串**(两次 ≈ 2 倍文本临时) |
| 3 | `.Split('\n')` | 10w+ 个行字符串对象 |
| 4 | `SplitRow` 中 `trimmed[1..]` / `trimmed[..^1]` | **每行再产生 2 个切片字符串** |
| 5 | `trimmed.Split('|')` | 每行一个 `string[]` + 9 个单元格字符串 |
| 6 | `new Dictionary<string,string>(headers.Length, OrdinalIgnoreCase)` | **10w 个字典对象**(每个含桶数组 + 条目数组) |
| 7 | `ParseFirstTable<T>` 二次遍历映射 | 映射期间第 6 步的 10w 个字典**仍然存活**,无法提前回收 |

**实测佐证**:步骤 6 单独的保留内存 = 110.5 MB(基线 A);
全链路总分配 = 195.4 MB(基线 B);而最终产物只需 23.2 MB(基线 C)。

**根因**:解析过程**先构建完整中间表示、再二次映射**,
中间表示的生命周期覆盖整个映射阶段;加上"整串复制"与"逐行切片"两类冗余分配。

**方向**:改为 `StreamReader.ReadLineAsync` **逐行解析 → 立即映射为实体**,
只保留最终实体;列值直接按表头索引取,不再为每行构造字典。

### 4.3 P0-3 · 解析在 UI 线程同步执行,冻结约 1 秒

**位置**:`Services/MarkdownDataService.cs` → `LoadAsync` 中 `await File.ReadAllTextAsync(...)`
之后的解析调用;由 `App.xaml.cs` 在 UI 线程发起。

**根因**:`await` 只把 **IO** 交给线程池,续体默认回到调用方的
`SynchronizationContext`(UI 线程)。因此 `ParseFirstTable` 这一 CPU 密集段
**整段跑在 UI 线程**上 —— 基线 A/B 测得的 619 ~ 943 ms 就是界面无响应时长。

**影响**:启动后约 1 秒界面冻结;规模线性放大(10w→1s,100w→10s,而内存早已失控)。

**方向**:解析段放入 `Task.Run`,完成后仅回 UI 线程做一次集合替换;
同时避免在 UI 线程上做 `Clear() + AddRange()` 之外的逐条通知。

### 4.4 P0-4 · 虚拟化在 Reset 时退化为全量重建

**位置**:`Common/Controls/VirtualizingWrapPanel.cs:226-241`

```csharp
case NotifyCollectionChangedAction.Reset:
    RemoveInternalChildRange(0, InternalChildren.Count);   // 仅移除内部子元素
    break;
```

**对比**:同文件 `CleanUpItems`(`:192-223`)在滚动时**正确**地把容器交还生成器回收入池:

```csharp
if (recycling)
{
    ((IRecyclingItemContainerGenerator)generator).Recycle(position, 1);
}
else
{
    generator.Remove(position, 1);
}
```

**根因**:`Reset` 分支绕过了上述回收逻辑。而 `ListCollectionView.Refresh()` 恰好触发
`CollectionChanged(Reset)`(见 `ViewModels/CashierViewModel.cs` → `RefreshProducts`),
于是**每次搜索、每次切分类都会让可视区全部容器被丢弃**(未入池),
下一次布局必须重新实例化 `Button + Grid + 约 10 个视觉元素` 的整棵模板树。

**影响**:虚拟化的收益在最高频的两条交互路径上被完全抵消。
`Recycling` 模式虽然开启,但在 Reset 路径上形同虚设。

**方向**:Reset 时先 `Recycle` 再移除内部子元素;或改用"换 `ItemsSource`"等不产生 Reset 的更新策略。

### 4.5 P0-5 · 全量过滤 + 非向量化字符串匹配

**位置**:`ViewModels/CashierViewModel.cs` → `FilterProduct`(每项 2 次 `string.Equals`
+ 3 次 `Contains(..., StringComparison.OrdinalIgnoreCase)`)、`RefreshProducts`。

**实测**:关键字搜索(全部分类)单次 **33.5 ~ 34.8 ms**;分类切换 5.0 ms。

**根因**:
- `Contains(string, StringComparison)` 不做向量化(不同于 `IndexOf(string, StringComparison)` 的部分路径),
  10w × 3 字段 = 30 万次逐字符比较;
- 每次筛选都从零开始,没有利用"分类"这一天然索引,也没有关键字索引/预归一化;
- 搜索防抖(250 ms)只能降低触发频率,无法降低单次成本。

**方向**:分类走索引**直接分片**;关键字搜索移到后台线程 + 结果上限/分页;
关键字与待检索字段做大小写归一化,用 `IndexOf(Ordinal)` 替代 `Contains(OrdinalIgnoreCase)`。

### 4.6 P0-6 · 扫码查找 O(N)

**位置**:`Services/PosRepository.cs:101-109`

```csharp
public Product? FindByBarcode(string barcode)
    => Products.FirstOrDefault(p =>
        !string.IsNullOrWhiteSpace(p.Barcode) &&
        string.Equals(p.Barcode, barcode.Trim(), StringComparison.Ordinal));

public Product? FindByCode(string code)
    => Products.FirstOrDefault(p => string.Equals(p.Code, code, StringComparison.OrdinalIgnoreCase));
```

**实测**:最坏情况(命中末位)5.73 ms / 3.79 ms。

**根因**:线性扫描 + 逐项字符串比较;`FindByBarcode` 每项还要先做 `IsNullOrWhiteSpace`。
扫码是 POS **最高频**路径,成本随数据量线性增长。

**方向**:`ReplaceAll` 时同步构建 `Dictionary<string, Product>`(条码、编码,O(1) 查找),
索引作为仓储内部实现,公开签名不变。

## 5. P1 问题

### 5.1 `ReplaceAll` 逐条 Add 且未裁剪订单
`Services/PosRepository.cs:70-74` 用 `foreach + Add` 填充 `ObservableCollection<Order>`,
触发 N 次集合变更通知;同时**未套用 `MaxOrders = 2000` 裁剪**,重置后订单数可能超过上限,
与 `AddOrder` 的护栏语义不一致。→ 改为一次性替换并裁剪。

### 5.2 `CategoriesWithAll` 每次访问都分配
`Services/PosRepository.cs:80-92` 在属性 getter 中 `new List` + `new ProductCategory("全部")`。
分类数量少,影响有限,但属于"属性即分配"的反模式,且每次 `RebuildCategories` 都会踩到。→ 缓存。

### 5.3 监控页待处理队列无上限
`ViewModels/DeviceMonitorViewModel.cs:36` 的 `_pendingFrames` 用 `ConcurrentQueue` 但**无容量约束**。
当产帧速率持续高于 150 ms 的批量刷新节奏(例如 `IntervalMs` 很小、`FaultRate = 0` 的驱动),
队列会**无界增长** → 长时间运行内存持续上升。→ 加上限 + 丢弃/合并策略。

### 5.4 指标 key 逐帧拼接字符串
`ViewModels/DeviceMonitorViewModel.cs:280` 每帧每个指标执行 `$"{frame.Type}.{name}"`。
高频报文下产生大量短命字符串,增加 GC 压力。→ 改结构化键(`ValueTuple<ProtocolType, string>`)或按协议分表。
另外 `_metricIndex` / `Metrics` 没有显式容量保护:当前 5 种协议指标名固定,规模有界,
但一旦出现动态指标名即无界增长,建议加护栏。

### 5.5 卡片尺寸双份硬编码
`Views/CashierView.xaml` 中卡片样式为 `Width=162 / Height=128 + Margin=10`,
而 `ItemsPanel` 上 `ItemWidth=172 / ItemHeight=138` 与之手工对齐(162+10=172,128+10=138)。
两处必须同步修改,是隐性耦合。→ 收敛到单一来源或改为自动测量。

## 6. 架构问题

### 6.1 `Products` 暴露可变 `List<T>`,并被 `ListCollectionView` 反向绑架

`Services/PosRepository.cs:26-32` 的注释明确写出了这个约束:

> "这里刻意暴露具体 `List<T>` 而非只读视图：……收银台需要把它交给 `ListCollectionView`
> (其构造函数要求非泛型 `IList`)做「不重建集合」的过滤。"

这形成一条**从存储层直通 WPF 集合类型**的耦合链:
`PosRepository` → `IProductCatalog.Products` → `CashierViewModel` → `ListCollectionView`。
后果:
- 表现层被迫持有**全量**商品,无法演进为分页/服务端查询;
- 领域/服务层为迁就 UI 框架类型而牺牲封装(可变集合可被任意调用方 `Clear()`);
- `CashierViewModel` 无法脱离 WPF 单元测试。

### 6.2 `MarkdownDataService` 职责过载、无数据源抽象

同一个类承担"文件定位 → 体积校验 → 读文本 → 解析 → 映射 → 写仓储"。后果:
- 无法替换数据源(CSV / SQLite / 远程),也无法按需分页加载;
- 解析逻辑无法独立测试(本次为写基准不得不**复刻**一遍映射语义,见 `TestProductData.MapProduct` 注释)。

### 6.3 ViewModel 直接依赖 WPF 集合类型

`CashierViewModel` 持有 `ListCollectionView` / `ICollectionView`,业务筛选逻辑与 WPF 类型混在一起,
筛选规则无法复用(例如未来"批量改价"页也要同样的分类+关键字规则)。

### 6.4 `PosRepository` 仍是上帝对象

已抽出 `IProductCatalog` / `IDeviceCatalog`(值得肯定),但**订单**仍无契约,
`Orders` / `AddOrder` / `MaxOrders` 与其他职责混在同一类型中。

### 6.5 缺少性能回归护栏

本次改造前无任何性能测试,导致 8 MB 上限与 10w 需求的冲突**直到实测才暴露**。
本次已补齐 14 个性能基准用例(合计 110 个测试),建议纳入常规回归。

## 7. 改造路线(分批 + 验收标准)

> 原则:**先量化、再消除峰值、再索引、再改查询、最后收架构**。
> 每批结束必须 `dotnet build` **0 error / 0 warning**,并重跑基准记录前后对比。
> 允许破坏性重构(已确认),但**现有 47 行演示数据与既有页面视觉/交互须保持可用**。

| 批次 | 主题 | 依赖 | 预估影响 |
| ---- | ---- | ---- | -------- |
| 0 | 基准与可观测性(**已完成**) | — | 交付脚本 + 基准用例(现 14 项) + 本报告 |
| 1 | 流式加载(消除内存峰值与 UI 冻结)(**已完成**) | 批次 0 | P0-1 / P0-2 / P0-3 |
| 2 | 索引化存储(查询 O(1))(**已完成**) | 批次 1 | P0-6 / 5.1 / 5.2 |

## 10. 已知测量局限

1. **Debug 构建**:绝对耗时高于 Release。批次 5 会用 Release 复测并更新第 3 章数据。
2. **总分配 vs 峰值**:`GC.GetTotalAllocatedBytes` 衡量累计分配量,是峰值的**上界来源**;
   真实进程峰值同时取决于 GC 触发时机,可能低于累计分配量。
3. **容器重建开销未量化**:4.4 描述的 `Reset → 容器重建` 依赖 WPF 布局管线,
   无法在无 UI 的 xUnit 基准中测量,已在批次 4 用 UI 侧验证替代(容器数量 + 截图比对)。
4. **机器负载敏感**:同条件全量扫描实测在 33 ~ 95 ms 区间波动,
   故耗时类基准采用"多轮取最优",并在报告中标注单调趋势而非绝对阈值。

**索引设计要点**

- **懒构建 + 条数失效**:`Products` 是公开可变 `List<T>`(见第 8 章破坏性登记),调用方可直接 `Add`。
  索引因此不依赖"写入方主动通知",而是在查询时比较 `Products.Count` 与建索引时的条数,
  不一致即重建;`ReplaceAll` 则显式失效,兜底"条数相同、内容不同"的重载场景。
- **保持旧语义**:条码 `Ordinal` + 跳过空白条码;编码 `OrdinalIgnoreCase`;用 `TryAdd` 而非索引器赋值,
  以维持线性扫描"首个命中"的行为(重复条码 / 编码、大小写、去空格、`Code=null` 均已加测试锁定)。
- **分类索引**:`CategoryId` → 商品列表,保持 `Products` 原始顺序;`all` 直接返回 `Products` 本体,
  与 `FilterProduct` 的分类短路语义一致。该索引由批次 3 的 `ProductQueryService` 消费(当前为空闲状态)。
- **匹配语义回归**:旧实现中 `string.Equals(p.Code, null)` 会命中第一条 `Code` 为 null 的商品,
  索引跳过 null 键,该极端场景保留一次兜底扫描(不进入高频路径)。

**实测结果(同轮对照 —— 同一进程内先测线性扫描再测索引,消除机器负载干扰)**

| 指标 | 线性扫描(复刻改造前) | 索引查找 | 加速 |
| ---- | ---------------------- | -------- | ---- |
| `FindByBarcode` 单次(命中末位,最坏) | 5.7970 ms | **0.0003 ms** | **≈ 2.2 万倍** |
| `FindByCode` 单次(命中末位,最坏) | 4.1717 ms | **0.0001 ms** | **≈ 3.4 万倍** |
| 分类切片(10w 中 14,286 条) | 5.4967 ms | **0.0002 ms** | **≈ 2.7 万倍** |

> 索引侧单次耗时为 0.0001 ~ 0.0003 ms(100 次平均),已接近 `Stopwatch` 分辨率下限,
> 因此**跨多次运行的加速比在 2.2 万 ~ 3.8 万倍之间波动**,应读作"亚微秒级"而非精确倍数。
> 同轮对照的数字同时印证:基线 E/F(5.73 ms / 3.79 ms)不是机器抖动,而是算法复杂度使然。
