## 一、A 组：WPF 基础（6 题）

### A1. 依赖属性和普通属性有什么区别？为什么要搞这么个东西？

**怎么答（要点）：**

- 普通属性就是字段 + 读写；**依赖属性是注册进 WPF 属性系统的属性**，值存在属性系统里而不是实例字段里；
- 换来三种能力：**支持绑定、样式、动画**（属性值可以被多个来源按优先级解析——动画 > 本地值 > 样式 > 默认值）、**节省内存**（只存"与默认值不同的那部分"）、**变更通知与继承**（属性值可以沿可视树向下传播，字体之类）；
- 代价：必须静态注册（`DependencyProperty.Register`），读写要走 `GetValue/SetValue`，比普通属性慢，所以**只有 UI 层才用，业务对象绝不用**。

**对着代码讲：**项目里的附加属性就是依赖属性的直接应用：

```17:27:c:/code/WpfStudy/CommunityToolkitDemo/Common/Behaviors/AttachedProps.cs
public static readonly DependencyProperty PlaceholderProperty =
    DependencyProperty.RegisterAttached(
        "Placeholder",
        typeof(string),
        typeof(AttachedProps),
        new PropertyMetadata(string.Empty));

public static string GetPlaceholder(DependencyObject obj) => (string)obj.GetValue(PlaceholderProperty);

public static void SetPlaceholder(DependencyObject obj, string value) => obj.SetValue(PlaceholderProperty, value);
```

注意三个特征：**静态字段 + Register 注册 + 一对 Get/Set 方法**——这就是依赖属性的标准长相。

**可能的追问：**"业务模型为什么不用依赖属性？"——不能继承 `DependencyObject`（业务类要能脱离 WPF 测试），所以业务模型用 `INotifyPropertyChanged`（下一题）。

### A2. 附加属性是什么？你什么时候用过？

**怎么答（要点）：**

- 附加属性是**"挂在别人身上"的依赖属性**：类型 A 定义，却可以设置在任何 `DependencyObject` 上；
- 典型就是 `Grid.Row`、`Canvas.Left`——`Grid` 不认识你的 `Button`，但你的 `Button` 可以"借用" `Grid` 的属性来说明布局意图；
- 实际工程价值：**给原生控件补能力，而不需要继承它**。

**对着代码讲：**项目里没用任何第三方行为库，`AttachedProps` 一个类给原生控件补了五种能力：

| 附加属性 | 挂在谁身上 | 补什么能力 |
| --- | --- | --- |
| `Placeholder` | TextBox | 输入框占位提示 |
| `AutoScrollToEnd` | ScrollViewer / ListBox | 日志自动滚到底（`AttachedProps.cs:32`） |
| `EnterKeyCommand` | TextBox | 回车触发命令（`AttachedProps.cs:128`） |
| `DecimalOnly` | TextBox | 只能输入数字和小数点（`AttachedProps.cs:173`） |
| `FocusOnLoaded` | FrameworkElement | 加载后自动聚焦（`AttachedProps.cs:219`） |

比如"回车触发命令"，XAML 里一行 `behaviors:AttachedProps.EnterKeyCommand="{Binding ScanCommand}"` 就够了，**不需要写一个 `ScanTextBox` 子类**——这就是附加属性的核心卖点。

**可能的追问：**"属性变化时怎么挂事件的？"——注册时传 `PropertyMetadata` 的**变更回调**，在回调里订阅/退订控件事件（`OnEnterKeyCommandChanged` 里先 `-=` 再 `+=`，防重复订阅）。

### A3. WPF 的绑定是怎么知道属性变了的？INotifyPropertyChanged 说清楚。

**怎么答（要点）：**

- 绑定引擎订阅源的 `PropertyChanged` 事件；属性 setter 里触发事件，UI 就刷新；
- 注意事件参数里**必须传对属性名**，传错/写错大小写 UI 就静默不刷新——这是手写 MVVM 最常见的坑；
- 所以 CommunityToolkit 用**源生成器**把属性和通知代码生成出来，杜绝手写错名（B2 详说）。

**对着代码讲：**项目所有 ViewModel 继承的 `ObservableObject` 就是这套机制的官方封装；手写版长这样（对比用）：

```csharp
private string _storeName = "";
public string StoreName
{
    get => _storeName;
    set { _storeName = value; OnPropertyChanged(nameof(StoreName)); }
}
```

项目里的实际写法是一个特性 + 一个字段：

```43:48:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/SettingsViewModel.cs
[ObservableProperty]
[NotifyDataErrorInfo]
[Required(ErrorMessage = "门店名称不能为空")]
[MinLength(2, ErrorMessage = "门店名称至少 2 个字符")]
[MaxLength(20, ErrorMessage = "门店名称最多 20 个字符")]
private string _storeName = string.Empty;
```

**可能的追问：**"一个属性变了想让另一个属性跟着刷新怎么办？"——`[NotifyPropertyChangedFor]`，见 B1 / A5 的联动例子。

### A4. IValueConverter 是干嘛的？你踩过什么坑？

**怎么答（要点）：**

- 绑定源和目标类型不一致时的"翻译器"：比如 `ConnectionState` 枚举 → 颜色画刷、`bool` → `Visibility`；
- 坑：**Convert 是高频调用路径**（每次绑定求值都会走），在里面分配对象等于给 GC 持续上刑；
- 经典错误：每次 `new SolidColorBrush(...)`。**正确做法：静态缓存 + `Freeze()`**。

**对着代码讲：**

```16:30:c:/code/WpfStudy/CommunityToolkitDemo/Common/Converters/Converters.cs

{
    public static SolidColorBrush Frozen(byte r, byte g, byte b)
    {
        var brush = new SolidColorBrush(Color.FromRgb(r, g, b));
        brush.Freeze();
        return brush;
    }
```

```110:113:c:/code/WpfStudy/CommunityToolkitDemo/Common/Converters/Converters.cs

private static readonly SolidColorBrush Connecting = BrushCache.Frozen(0xF5, 0x9E, 0x0B);
private static readonly SolidColorBrush Connected = BrushCache.Frozen(0x16, 0xA3, 0x4A);
```

两个点值得讲：**为什么 Freeze**——未冻结的 `Freezable` 会被属性系统登记变更通知，画刷又是不可变的，冻结后变成"线程安全 + 免通知 + 渲染层可优化"；**为什么报文日志那条不用转换器**——高频路径直接把格式化文本挂在数据对象上（`ProtocolFrame` 暴露格式化属性），根本不走转换器。

**可能的追问：**"ConvertBack 你怎么写的？"——单向绑定一律返回 `Binding.DoNothing`，别抛异常。

### A5. ObservableCollection 的通知机制？它有线程限制吗？

**怎么答（要点）：**

- `CollectionChanged` 事件通知"增删移换"，配合 `INotifyPropertyChanged` 通知 `Count`；
- **只能在创建它的线程上修改**——具体说是 UI 线程亲和：绑定到界面后，后台线程直接 `Add` 会抛 `NotSupportedException`（"这种类型的 CollectionView 不支持从调度程序线程以外的线程更改其 SourceCollection"）；
- 所以后台数据回 UI 必须切线程（D1 详说）。

**对着代码讲：**项目里最重的两个 `ObservableCollection`：

- `DeviceMonitorViewModel.Logs`——报文日志，环形缓冲 200 条（C6 详说）；
- `CashierViewModel.Products`——商品列表，**搜索与切分类时整表替换**。而 `ObservableCollection` 没有 `AddRange`，逐条 Add 会逐条通知、逐条重排，所以项目写了一个批量替换版本（C3 详说）：

```66:66:c:/code/WpfStudy/CommunityToolkitDemo/Services/PosRepository.cs
public RangeObservableCollection<Order> Orders { get; } = new();
```

**可能的追问：**"两个页面同时绑定一个集合会刷新两次吗？"——会，每个 `CollectionView` 各自收到通知；项目里"同一实例挂两处"的解法见第 03 篇（`LiveMetricItem` 一份两刷）。

### A6. DataTemplate 的查找规则了解吗？隐式 DataTemplate 是什么？

**怎么答（要点）：**

- `ContentControl` 遇到非 UIElement 内容时，按**内容的运行时类型**去资源链找 `DataTemplate`（隐式模板：`DataType` 设置了、`x:Key` 没设置）；
- 找到就 `LoadContent()` 实例化一棵视图；**没找到就直接 `ToString()`**；
- 关键细节：**换内容就重建视图**——这是导航场景的性能坑。

**对着代码讲：**项目的页面导航正是用隐式模板实现的（主窗口按 ViewModel 类型自动选 View）；然后针对"每次换页重建整棵视觉树"做了缓存：

```22:45:c:/code/WpfStudy/CommunityToolkitDemo/Common/Controls/CachedContentControl.cs
protected override void OnContentChanged(object? oldContent, object? newContent)
{
    base.OnContentChanged(oldContent, newContent);

    // 只处理"视图模型"内容；换成缓存视图后（FrameworkElement）不再二次处理，避免递归
    if (newContent is null || newContent is FrameworkElement)
    {
        return;
    }

    var view = GetOrCreateView(newContent);
    if (view is null)
    {
        return;
    }

    // 视图是复用实例，每次换页都要把 DataContext 指回当前视图模型
    view.DataContext = newContent;

    if (!ReferenceEquals(Content, view))
    {
        SetCurrentValue(ContentProperty, view);
    }
}
```

三个能讲出深度的点：用 `DataTemplateKey(type)` 手动走一遍模板查找（`:66-72`）；用 **`SetCurrentValue` 而不是 `Content = view`**——前者不破坏外部对 Content 的绑定，是个容易被追问的好细节；复用的视图**必须重设 `DataContext`**（`:39`）。

**可能的追问：**"为什么内置 ContentControl 不这么做？"——通用性：多数场景内容真的变了就该重建；缓存是有代价的（内存换重建），只对"已知会来回切换的页面"划算。

## 二、B 组：MVVM 与 CommunityToolkit（6 题）

### B1. MVVM 到底解决什么问题？V、VM、M 各自的边界？

**怎么答（要点）：**

- 一句话：**把"界面长什么样"和"界面干什么"拆开**。View（XAML）只管布局与绑定，ViewModel（属性 + 命令）只管状态与行为，Model 是纯数据；
- 判别标准：**ViewModel 不引用任何 WPF 控件类型**（`Window`、`TextBox` 一概不许出现），View 不写业务逻辑；
- 收益：ViewModel 可脱离 UI 单测、界面可换皮、逻辑可复用。

**对着代码讲：**拿"一键连接全部设备"举例，View 上只有一句绑定，其余全在 ViewModel：

```117:136:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/DeviceMonitorViewModel.cs
[RelayCommand(CanExecute = nameof(CanToggleAll))]
private async Task ConnectAllAsync()
{
    IsBusy = true;

    try
    {
        await _manager.ConnectAllAsync();
        SyncCardStates();
        Notify("已请求连接全部模拟设备", StatusNotificationMessage.StatusLevel.Info);
    }
    catch (Exception ex)
    {
        Notify($"连接设备失败：{ex.Message}", StatusNotificationMessage.StatusLevel.Warning);
    }
    finally
    {
        IsBusy = false;
    }
}
```

值得讲的细节：`IsBusy` 抑制重复点击（`finally` 里复位，异常也不会卡死按钮）；弹窗不直接开，而是广播状态消息让主窗口提示条显示——**"告警去哪了"是 ViewModel 与 View 解耦的试金石**。

**可能的追问：**"对话框这种纯 UI 行为 ViewModel 怎么弹？"——抽成 `IDialogService` 注入，ViewModel 只调接口，实现在 UI 层（`DialogService`）。

### B2. `[ObservableProperty]` 是什么原理？比手写好在哪？

**怎么答（要点）：**

- **编译期源生成器**：字段标注特性后，编译时生成真正的属性（getter/setter + `OnPropertyChanged`），不是运行时反射、也没有 IL 织入；
- 生成的属性名 = 字段名去掉下划线、驼峰化：`_storeName` → `StoreName`；
- 好处：**拼不出错**（不会手滑把 `"StoreName"` 写成 `"Storename"` 导致绑定静默失效）、**少写模板代码**、还免费送 `partial void OnXxxChanged` 钩子；
- 附赠联动特性：`[NotifyPropertyChangedFor]`、`[NotifyCanExecuteChangedFor]`。

**对着代码讲：**"依赖属性 + 命令可用性"两条联动一起出现在一个字段上：

### B3. 表单校验你怎么做的？`ObservableValidator` 讲一下。

**怎么答（要点）：**

- CommunityToolkit 的 `ObservableValidator` 把 **WPF 的 `IDataErrorInfo`/`ValidationEventArgs` 体系**和 **DataAnnotations 特性**（`Required` / `MinLength` / `Range` / `RegularExpression`）接到一起；

### B4. `ObservableRecipient` 的 `IsActive` 是干什么的？

**怎么答（要点）：**

- `ObservableRecipient` = `ObservableObject` + **消息接收器 + 生命周期管理**；
- `IsActive = true/false` 切换时自动 `RegisterAll/UnregisterAll`——**离开页面就退订消息，回来再恢复**；
- 价值：不活跃页面不再被消息驱动刷新（省 CPU），也不用手工管理订阅配对。

**对着代码讲：**设备监控页是最典型的"重页面"，离开时把驱动事件与计时器一起停掉：

```188:211:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/DeviceMonitorViewModel.cs

{

    _manager.DriverStateChanged += OnDriverStateChanged;
```

主窗口导航时的切换逻辑（`MainWindowViewModel` 的 `Navigate`）：离开监控页 `IsActive = false`、进入置 `true`；而**收银台是常驻激活**的——扫码枪随时可能报条码，不能因为页面切走了就收不到（`CashierViewModel` 构造函数里 `IsActive = true`）。

**可能的追问：**"消息订阅和事件订阅为什么分开管理？"——消息走 Messenger（`IsActive` 自动管），`.NET` 事件走 `+=/-=`（必须自己在 OnActivated/OnDeactivated 配对）。

### B5. 为什么用消息总线而不是事件？`WeakReferenceMessenger` 说清楚。

**怎么答（要点）：**

- 事件的问题：**发布方必须认识订阅方**（至少认识一个接口），跨模块就得层层转发；订阅还容易忘记退订导致**内存泄漏与重复回调**；
- 消息总线：发布方 `Send`、订阅方声明 `IRecipient<T>`，**双方互不认识**，靠消息类型对上暗号；
- "弱引用"指 Messenger 对接收方持弱引用：**订阅方没人引用时可被 GC**，不需要显式 Unregister 也不泄漏（代价：弱引用保不了"临时没人引用但还要活着"的对象，所以页面级还是用 `IsActive` 显式管理）。

**对着代码讲：**最漂亮的一个案例是**协议层与界面的解耦**——驱动只认"报文"，收银台只认"消息"，中间一个 30 行的桥接器完成翻译：

```48:64:c:/code/WpfStudy/CommunityToolkitDemo/Services/ProtocolMessageBridge.cs
{

        frame.Direction is not ProtocolDirection.In ||
        frame.Values is null ||
        !frame.Values.TryGetValue(ProtocolKeys.Barcode, out var barcode) ||
        string.IsNullOrWhiteSpace(barcode))
    {
        return;
    }

    UiDispatcher.Post(() => _messenger.Send(new BarcodeScannedMessage(barcode)));
}

private void OnAlarmRaised(object? sender, DeviceAlarm alarm)
```

### C1. 虚拟化是什么原理？你的换行面板为什么要自己写？

**怎么答（要点）：**

- 虚拟化 = **只为可视区生成控件容器**，滚动时回收离开视口的容器、复用给新进入的数据项，内存与首屏耗时从 O(N) 降到 O(可视区)；
- 前提：`VirtualizingPanel` 需要能**预知条目尺寸**（或做估算）来计算滚动范围；数据项容器由 `ItemContainerGenerator` 管理；
- WPF 内置只有 `VirtualizingStackPanel`（单列/单行）；**没有虚拟化的换行布局**——而收银台商品网格正是换行布局，普通 `WrapPanel` 会把 10 万个卡片全量实例化，所以自己实现了 `VirtualizingWrapPanel`。

**对着代码讲：**三个能镇住场子的点：

1. 商品面板 XAML 里显式给定格子尺寸（`ItemWidth/ItemHeight`），这是虚拟化面板计算滚动范围的契约；
2. **Reset 时容器无法回收**——这不是 bug：框架在 Reset 时已调用 `generator.RemoveAll()` 清掉位置映射，此刻回收不可能（内置 `VirtualizingStackPanel` 行为一致），并且写了对照测试钉住结论：`Reset_DropsContainersLikeBuiltIn`、`Reset_KeepsRealizedContainerCountBounded`、`Scroll_ReusesContainersFromRecyclePool`（`tests/.../VirtualizingWrapPanelTests.cs:64,109,140`）；
3. 滚动路径确实从回收池复用容器，有测试为证。

**可能的追问：**"启用虚拟化有什么代价？"——滚动时容器频繁生成/回收本身有开销；容器尺寸不一致会增加估高误差（滚动条跳动）；**几十条数据没必要开**。

### C2. 搜索过滤你是怎么做的？为什么不用 `CollectionView` 的 Filter？

**怎么答（要点）：**

- `ICollectionView.Filter` 是**逐条回调、在 UI 线程执行**的谓词过滤：10 万条 × 每条一次委托调用，一次输入够卡几百毫秒，且每敲一个字全量重跑；

### C3. `ObservableCollection` 没有 AddRange，你怎么办的？

**怎么答（要点）：**

- 逐条 `Add` = 每条一次 `CollectionChanged` = 绑定的列表控件逐条插入、逐次重排；
- 自定义 `RangeObservableCollection<T>`：**清空 + 批量填充之后只发一次 `Reset`**，视图只重建一次；
- 两个容易被追问的细节：**先物化再改集合**（防止清空后枚举惰性序列出现"边清边取"）；**内容没变就不发通知**（重复搜索/重复点同一分类时，无谓的 Reset 会让虚拟化面板把可视区容器全部重建一遍）。

### D1. 后台线程能直接改 UI 绑定的集合吗？怎么切回 UI 线程？

**怎么答（要点）：**

- 不能。`ObservableCollection` 绑定后其 `CollectionView` 是**调度线程亲和**的：非创建线程修改直接抛 `NotSupportedException`；普通属性赋值虽不抛，但**跨线程改绑定属性本身就是数据竞争**；
- 切回方式三选一：`Dispatcher.Invoke`（同步阻塞，最不推荐）、`Dispatcher.BeginInvoke/InvokeAsync`（异步投递）、`.ConfigureAwait(true)` 依赖同步上下文（WPF UI 线程默认捕获）；
- 项目做法：封装一个 `UiDispatcher.Post`——**已在 UI 线程就直接执行，否则异步投递**，不阻塞后台线程。

**对着代码讲：**

### D3. 后台循环怎么优雅停止？`CancellationToken` 讲一下。

**怎么答（要点）：**

- 模式：循环每轮 `Task.Delay(interval, token)` + 干活，`token` 取消时抛 `OperationCanceledException`，循环捕获后正常退出；

```110:144:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolDriverBase.cs
        catch (OperationCanceledException)
        {
            // 正常取消
        }
    }

    cts?.Dispose();

    await OnDisconnectAsync().ConfigureAwait(false);
    State = ConnectionState.Disconnected;
}
```

而"连接后立刻断开"的竞态是整个项目里最值得讲的注释——闭包如果直接读字段，断开已把字段置 null、后台任务才刚启动，读 `Token` 直接 NRE；**先用局部变量捕获本次 CTS 再交给闭包**：

```87:97:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolDriverBase.cs
// 先用局部变量持有本次的 CTS，再交给后台任务闭包捕获。
// 若闭包直接读取 _loopCts 字段，在"连接后立刻断开"的竞态下，
// DisconnectAsync 已把字段置为 null，而后台任务才刚启动，
// 读取 _loopCts.Token 会抛 NullReferenceException。捕获局部变量可彻底避免。
var loopCts = new CancellationTokenSource();
lock (_sync)
{
    _loopCts?.Dispose();
    _loopCts = loopCts;
    _loopTask = Task.Run(() => RunLoopAsync(loopCts.Token), CancellationToken.None);
}
```

**可能的追问：**"`Task.Run` 为什么传 `CancellationToken.None`？"——传有效 token 只是不**启动**任务，任务已在跑时停它仍要靠循环里的 token；这里语义就是"必启动、靠内层 token 停"。

### D4. `volatile` 干嘛的？为什么你的状态字段用 `int` 存？

**怎么答（要点）：**

- `volatile` 保证**可见性与顺序性**（读写不走缓存、不重排），不保证原子复合操作（`x++` 照样丢更新）；
- 限制：C# 里 `volatile` 不能修饰枚举字段，`Volatile` 类的泛型重载要求 `T : class`（枚举不满足）；
- 解法：**按底层类型 `int` 存，配 `Volatile.Read/Write`**——枚举底层是 int，读写本身原子，加内存屏障后读线程不会长期看到旧值。

**对着代码讲：**驱动状态字段被后台仿真循环写、UI 线程读，是货真价实的跨线程字段：

```18:30:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolDriverBase.cs
/// <summary>
/// 状态字段，按底层类型 <see cref="int"/> 存放。
/// </summary>
/// <remarks>
/// 为什么不用 <see cref="ConnectionState"/> 直接加 volatile？
/// <see cref="Volatile"/> 的泛型重载要求 <c>T : class</c>（枚举不满足），
/// 而 <c>volatile</c> 关键字也不允许用于枚举字段。
/// 因此这里以 int 存放，再配合 <see cref="Volatile"/> 读写：
/// <see cref="State"/> 会被后台仿真循环线程写入、被 UI 线程读取，
/// 枚举底层是 int、读写本身原子，但没有内存屏障时读线程可能长期看到旧值
///（JIT 可以把字段缓存在寄存器中）。
/// </remarks>
private int _state = (int)ConnectionState.Disconnected;
```

```50:63:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolDriverBase.cs
public ConnectionState State
{
    get => (ConnectionState)Volatile.Read(ref _state);
    private set
    {
        if (Volatile.Read(ref _state) == (int)value)
        {
            return;
        }

        Volatile.Write(ref _state, (int)value);
        StateChanged?.Invoke(this, value);
    }
}
```

setter 里"先比较再写再广播"没有加锁——注释明说这是取舍：极端并发下可能重复触发一次 `StateChanged`，但订阅方是幂等的状态同步逻辑，**热路径免锁比理论完美更重要**（`:44-49` 的 remarks）。

**可能的追问：**"`Interlocked` 和 `volatile` 什么关系？"——`Interlocked` 提供原子复合操作（增量、交换、比较交换），`volatile` 只管可见性；`FrameCount += processed` 在 UI 线程单点执行所以不需要 `Interlocked`——**"哪里真的有并发"要指得出来**。

## 五、E 组：架构与工程化（3 题）

### E1. 你的项目分几层？怎么防止"一个类越写越大"？

**怎么答（要点）：**

- 三层：**表现层**（Views / ViewModels）→ **业务服务层**（购物车、订单、设置、结算编排）→ **数据与通信层**（仓储、Markdown 数据源、协议驱动）；
- 防膨胀的手段不是"少写代码"，是**让每类只有一个变化理由**：界面显示归 ViewModel、业务规则归服务/静态规则类、设备配合归编排器；
- 最典型的例子：**同一条业务规则被三处需要时，抽"单一事实来源"**。

**对着代码讲：**"能不能加购、最多加多少"这条规则，购物车服务（约束数量）、收银台（拦截零库存并提示）、购物车行项（"+"按钮可用性）三处都要用，于是收敛成一个静态类：

```15:33:c:/code/WpfStudy/CommunityToolkitDemo/Services/CartLimits.cs
public static class CartLimits
{
    /// <summary>允许超库存销售时不再限制数量。</summary>
    public const int Unlimited = int.MaxValue;

    public static int MaxQuantityFor(Product product, bool allowOversell)
        => allowOversell ? Unlimited : Math.Max(product.Stock, 0);

    public static bool CanAdd(Product product, bool allowOversell)
        => MaxQuantityFor(product, allowOversell) > 0;
}
```

同类决策还有：结算后的"打印/开钱箱/上报"从收银台抽出为 `CheckoutCoordinator`（设备编排与界面显示分离）、协议报文翻译成消息由 `ProtocolMessageBridge` 单独承担。**答这题时最好带上一个反例**："如果规则散落三处，任何一处漏改就会出现'按钮能点但加不进去'的不一致"——有反例的原则才是真原则。

**可能的追问：**"三层之间怎么防止越层引用？"——靠接口收窄：ViewModel 只见 `IProductQuery`/`ICartService`，见不到仓储；驱动只见 `IDeviceCatalog`，见不到整个仓储（`App.xaml.cs:141-145` 的两个最小契约接口都指向同一单例）。

### E2. 多设备协同的操作怎么编排？一台失败怎么办？

**怎么答（要点）：**

- 原则一：**互不依赖的动作并行下发**，缩短总等待时间；
- 原则二：**异常隔离**——一个设备失败不能拖垮整体，逐个 try/catch 或"未连接返回 false 不抛"；
- 结果以**结构化结果**返回（哪台成了哪台没成），而不是抛异常或返回 bool 了事。

**对着代码讲：**结算后三件事并行 + 结果汇总：

```42:53:c:/code/WpfStudy/CommunityToolkitDemo/Services/CheckoutCoordinator.cs
public async Task<OrderFollowUpResult> CompleteAsync(Order order, bool openCashBox)
{
    var printTask = _protocols.PrintReceiptAsync(order);
    var cashBoxTask = openCashBox ? _protocols.OpenCashBoxAsync() : Task.FromResult(false);
    var uploadTask = _protocols.PublishOrderAsync(order);

    // 用 WhenAll 的返回值取值，而不是各任务上再读 .Result：
    // 后者容易被误读为"同步阻塞"（sync-over-async）而引发无谓的改造。
    var results = await Task.WhenAll(printTask, cashBoxTask, uploadTask);

    return new OrderFollowUpResult(results[0], results[1], results[2]);
}
```

"未连接不抛"的语义由协议管理器统一保证——收银台允许**离线收银**，设备没接不该让用户结不了账：

```145:149:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolManager.cs
/// <summary>
/// 向指定协议的驱动下发一条报文。
/// 未连接时安全返回 false（收银台允许"离线收银"，不因设备未接而报错）。
/// </summary>
```

连接全部设备同样是"并行 + 逐台隔离异常"（`Task.WhenAll(_drivers.Select(ConnectSafelyAsync))`，失败只写 `Debug` 日志，`:54-90`）；最后 `BuildDeviceNote` 把结果拼成用户能看懂的"哪台成了哪台跳过了"文案。

**可能的追问：**"什么时候该并行什么时候不该？"——无共享状态、无依赖才并行；三件事写三个不同的设备，天然满足。**"判断依据"永远比"结论"重要**。

### E3. 项目质量怎么保证？测试怎么写的？

**怎么答（要点）：**

## 七、结语：面试的"元技巧"

最后说四件比答案本身更重要的事：

1. **每个答案都落到代码。**"我用过虚拟化"值 1 分，"我写过虚拟化换行面板、知道 Reset 时为什么不能回收容器、还有对照测试"值 10 分。这 26 道题的设计全部遵循这个原则。
2. **主动交代已知缺陷。**这个项目不是完美的：队列没上限、接口只支持单设备寻址、指标 key 还在拼字符串——但每一条都写进了注释和第 07 篇，**"知道自己哪里没做好 + 有改进方案"在面试里是强信号，被追问出来才是弱信号。**
3. **说取舍，不说教条。**150 ms 是旋钮不是真理；`State` 写入不加锁是因为订阅方幂等；`CanSave` 手动订阅 `PropertyChanged` 是因为 `HasErrors` 不是生成属性——每个"不标准"的地方都有理由，能讲出理由的候选人是"做过"，只会背最佳实践的是"看过"。
4. **拿数字说话。**943 ms → 460 ms、5.73 ms → 0.0003 ms、110 个测试全绿——量过的东西才有说服力；而说数字时记得补一句"绝对值跨机器不可比，看的是同轮对照"，这是懂行的人才会说的话。

> 系列九篇到此完结。从"只会拖控件"到能对着一份 341 行的 ViewModel 讲清楚消息、线程与性能——这条路没有捷径，但有一条已被验证的路径：**跑起来 → 跟一条链路 → 改一处 → 加一条测试 → 量化一次**（第 07 篇的六天路线图）。
