前面六篇基本都在讲"这个项目哪里做得好"。

这一篇要反过来，讲讲**它现在还剩哪些毛病**——以及**一个 WPF 小白今天该从哪里下手**。

我把项目里的问题分成了三档，这个分法不是我拍脑袋定的，而是照着一句话来的：

> **先止"会持续变坏"的，再拆"妨碍演进"的，最后才做"锦上添花"的。**

- **会持续变坏**（长跑就出事）：队列无上限、字符串逐帧拼接 → **必须做**；
- **妨碍演进**（现在能跑，但加需求就难受）：仓储没有订单契约、数据源不可替换、多设备不可寻址 → **值得做**；
- **锦上添花**（不影响正确性与扩展性）：未使用的转换器、命名规范、分析器配置 → **有空再说**。

**先声明两件事：**

1. 下面所有"还没做"的判断，都基于**代码里实际能看到的现状**，不是猜的；
2. 所有性能数字，都直接引用项目里那份《性能与内存专项分析报告》的实测口径，我不自己造数字。

**关于"批次 4 的 Reset 回收"，这一条值得单独说说，因为它是个很典型的"查了才发现不是 bug"的情况。**

《性能与内存专项分析报告》的 4.4 节曾指出：`VirtualizingWrapPanel` 在收到集合 `Reset` 时只做 `RemoveInternalChildRange`，绕过了容器回收，导致每次搜索/切分类都会丢弃全部可视容器。

我照着这条去查了，结论写在现在的代码注释里：

```243:253:c:/code/WpfStudy/CommunityToolkitDemo/Common/Controls/VirtualizingWrapPanel.cs
case NotifyCollectionChangedAction.Reset:
    // Reset（整体替换）时框架的 OnItemsChangedInternal → ResetChildren → ClearChildren
    // 已经调用过 generator.RemoveAll() 并清空了 InternalChildren，生成器的位置映射随之失效。
    // 此刻再把容器交回回收池已不可能（Remove/Recycle 的坐标不再有效），
    // 内置的 VirtualizingStackPanel 行为完全一致（见 Reset_DropsContainersLikeBuiltIn 对照测试）。
    // 因此这里只做兜底清理，保证不残留内部子元素；回收复用只在明确受支持的滚动/增量变更路径生效。
    if (InternalChildren.Count > 0)
    {
        RemoveInternalChildRange(0, InternalChildren.Count);
    }
    break;
```

**也就是说：不是"忘了回收"，而是"Reset 时刻根本没法回收"——框架已经把生成器的位置映射清掉了。** 而且我写了一个对照测试把这个结论"钉"住了：

| 测试 | 位置 | 锁住什么 |
| --- | --- | --- |
| `Reset_DropsContainersLikeBuiltIn` | `tests/.../VirtualizingWrapPanelTests.cs:64` | 自定义面板的 Reset 行为**不比内置 `VirtualizingStackPanel` 更差** |
| `Reset_KeepsRealizedContainerCountBounded` | 同上 `:109` | Reset 后已实现容器数量仍然**有界**，不会无限增长 |
| `Scroll_ReusesContainersFromRecyclePool` | 同上 `:140` | 滚动路径**确实**从回收池复用容器 |

> **这条经验的普适价值**：性能报告给出的是"待验证的线索"，不是"结论"。去查、去测、写个测试把结论固定下来，比照着报告无脑改代码重要得多。
> 报告 4.4 节的原始描述在这个点上已经**被后续验证修正**了——这也是为什么写测试比写报告更能定案。

### 1.3 三项"差一点点"没达标的指标

这部分我**不想含糊过去**，因为它是这份报告里最有信息量的内容。

| 指标 | 目标 | 实测 | 结论 |
| --- | --- | --- | --- |
| 加载 10 万行耗时 | ≤ 400 ms | 460.2 ms（纯解析）/ 425.2 ms（含 IO） | ⚠️ 差 8%~15% |

| 稳态保留内存 | ≤ 30 MB | 32.6 MB | ⚠️ 差 9% |

报告自己的判断是：

> 三项未达标项与阈值仅差 8%~15%，说明"消除中间表示"这一步已基本做到位 —— 剩余分配量主要来自 `Split('|')` 为每行产生的单元格字符串，属于当前存储格式下的必要成本。继续压缩需要改变"行 × 列"的文本存储方式（如列式/二进制），投入产出比明显下降。**因此建议维持现状。**

**我完全同意这个判断，并且这一条我特意写进文章里**，因为它是一个很典型的工程决策样本：

> **"没达标"不等于"必须继续优化"。** 目标是我自己定的，8% 的差距换来的是"改变整个数据存储格式"——这笔账算不过来，就应当停下来，把预算投到收益是数量级的地方（比如索引化带来的 2 万倍）。

## 二、必须做：会"持续变坏"的三件事

说完好的，说不好的。

**这三件事的共同特征是：现在跑起来一切正常，但时间一长、数据一多，问题就会自己长大。**

### 2.1 监控页待处理队列没有上限

这是我心里最不踏实的一条。

```35:36:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/DeviceMonitorViewModel.cs
/// <summary>后台驱动线程写入、UI 计时器批量读取的待处理报文队列</summary>
private readonly ConcurrentQueue<ProtocolFrame> _pendingFrames = new();
```

`ConcurrentQueue` 保证了线程安全，但**它没有容量约束**。

回想一下上一篇讲的设计：后台线程只管 `Enqueue`，UI 每 150 ms 清一次仓。正常情况下一进一出是平衡的。

**但如果"进得比出得快"呢？**

报告里点出了触发条件：当产帧速率持续高于 150 ms 的批量刷新节奏时（比如某个驱动的 `IntervalMs` 设得很小、`FaultRate = 0` 从不故障），队列会**无界增长**。

后果很直白：**内存持续上升，而且不会自己下来。** 一个演示程序跑几小时也许看不出来，但这是个"结构性隐患"，不是"配置问题"。

**我的改进方案（三选一，按推荐度排）：**

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A（推荐）** | 入队前判 `Count > MaxPendingFrames`，超出则**丢弃最旧的**（或直接丢新帧） | 实现最简单，内存上界确定 | 极端情况下会丢报文（但报文日志本来就是"看得见就够"，且已有 200 条环形缓冲） |
| B | 按 `(协议, 指标名)` **合并**队列里的同键帧，只保留最新值 | 不丢信息，最省内存 | 复杂度高，日志类报文仍会堆积 |
| C | 给 `DispatcherTimer` 加"积压越多刷新越勤"的**自适应节流** | 不丢数据 | 治标不治本（速率长期高于消费能力时仍然涨） |

**我倾向 A**，理由是：这个队列的消费方是"给人看的监控面板"，**不是必须一条不丢的业务数据**。而且项目里已经有了同样的思路先例——报文日志本身就是个环形缓冲：

```24:25:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/DeviceMonitorViewModel.cs
/// <summary>报文日志容量上限（环形缓冲，防止长时间运行内存膨胀）</summary>
private const int MaxLogItems = 200;
```

**同一个类里，日志有上限、队列没上限——这本身就是不一致。** 补上它，语义就统一了。

**验收方式**（照抄报告批次 5 的要求）：新增测试——超过上限时按策略丢弃、且队列长度不发生无界增长。

### 2.2 指标 key 每帧都在拼字符串

```278:285:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/DeviceMonitorViewModel.cs
foreach (var (name, value) in frame.Values)
{
    var key = $"{frame.Type}.{name}";

    if (!_metricIndex.TryGetValue(key, out var item))
    {
        item = new LiveMetricItem(frame.Type, name);
        _metricIndex[key] = item;
```

`$"{frame.Type}.{name}"` 看着无害，但它是**在每一帧、对每一个指标**都执行一次。

算一笔账：5 个驱动、每个假设 4 个指标、150 ms 一轮 → 每秒约 133 次字符串插值，每次产生一个短命字符串。跑一小时就是约 48 万个字符串对象。**这不是"卡"，这是纯粹的 GC 压力**，而且完全没有必要。

**改进方案：把 key 换成结构化键。**

最直接的做法是不再拼字符串，直接用元组当字典键：

```csharp
// 结构键：不产生新字符串，且相等性由值语义保证
private readonly Dictionary<(ProtocolType Type, string Name), LiveMetricItem> _metricIndex = new();
```

`ValueTuple` 的 `GetHashCode`/`Equals` 都是结构化的，`string` 部分靠引用+内容比较，编译器生成的代码比"插值 + 字符串哈希"便宜得多。

**顺带一个护栏**：报告还提到了 `_metricIndex` / `Metrics` **没有显式容量保护**。当前 5 种协议的指标名是固定的（都来自 `Data/devices.md` 的 `Metrics` 列），规模有界；但一旦将来出现"动态指标名"，这两个集合就会无界增长。

所以改进方案是**两件事一起做**：结构键（省分配）+ 加上限或"按协议分表"（防无界）。

**改进方案：收敛到单一来源。** 两种做法：

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| A | 在 `VirtualizingWrapPanel` 上**自动测量**第一个卡片的 `DesiredSize + Margin`，不给 `ItemWidth/ItemHeight` 就自动推导 | 最彻底，但虚拟化面板要"提前知道格子大小"来算总高度，自动测量会把这件事推迟到第一次布局之后，实现复杂 |
| **B（推荐）** | 把 `162 / 128 / 10` 提成**资源键**（如 `ProductCardWidth`），样式与面板都引用同一批资源 | 改动小、风险低，仍然保留"提前知道格子大小"这个虚拟化必需的前提 |

我选 B 的理由很实际：**虚拟化面板需要 `ItemWidth/ItemHeight` 来算滚动范围，这是它的既定契约；与其绕开契约，不如把数值变回"一处定义"。**

## 三、值得做：会"妨碍演进"的四件事

这几件事的共同特征是：**都不是 bug，现在都能正常工作，但你一旦想加新需求，就会立刻撞上它们。**

### 3.1 仓储的订单部分还没有契约

这是《架构审查报告》P0-6（上帝对象）的收尾工作，也是《性能与内存专项分析报告》6.4 节点名的那条。

现状是：`PosRepository` 已经把商品、设备两块能力分别通过接口对外暴露了：

```13:13:c:/code/WpfStudy/CommunityToolkitDemo/Services/PosRepository.cs
public sealed class PosRepository : IProductCatalog, IDeviceCatalog
```

**但订单没有对应契约。** 订单集合和写入方法还是直接挂在仓储上：

```61:80:c:/code/WpfStudy/CommunityToolkitDemo/Services/PosRepository.cs
/// <summary>订单（历史 + 本次运行新增）</summary>
/// <remarks>
/// 使用支持批量替换的集合类型：加载时一次性重建只发一次变更通知，
/// 避免逐条 Add 造成订单列表反复刷新（详见 <see cref="RangeObservableCollection{T}"/>）。
/// </remarks>
public RangeObservableCollection<Order> Orders { get; } = new();

/// <summary>订单历史上限：超出后丢弃最旧的，避免长时间运行内存无界增长</summary>
public const int MaxOrders = 2000;

/// <summary>写入新订单：插到最前（界面按时间倒序）并裁剪超出上限的旧订单。</summary>
public void AddOrder(Order order)
{
    Orders.Insert(0, order);

    while (Orders.Count > MaxOrders)
    {
        Orders.RemoveAt(Orders.Count - 1);
    }
}
```

`IOrderService` 是存在的，但它是**业务服务**（负责"下单"这件事），不是**存储契约**：

```9:16:c:/code/WpfStudy/CommunityToolkitDemo/Services/IOrderService.cs

{
    /// <summary>订单集合（历史订单 + 本次运行新增），供订单列表绑定。</summary>

    /// <summary>结算：把购物车转成订单并落库；购物车为空时返回 null。</summary>
```

**改进方案：新增 `IOrderStore`**（`Orders` / `AddOrder` / `MaxOrders` 语义），由 `PosRepository` 实现，`OrderService` 依赖它而不是整个仓储。

**为什么这件事值得做？** 因为现在的状态是"商品和设备都能按最小契约取用，只有订单必须拿到整个仓储"。**同一个类里两种风格并存，比两种都不好还糟**——它会让后来的人不知道该照哪个来。

> 报告把这条登记为**破坏性改动**（`IOrderStore` 抽取会改变构造注入点），所以它被放在批次 5、而不是混在之前的兼容批次里。**这个节奏是对的：破坏性改动手续要清楚，一次做一件。**

### 3.2 `MarkdownDataService` 职责过载、数据源不可替换

性能报告 6.2 说得挺狠：这一个类承担了**"文件定位 → 体积校验 → 读文本 → 解析 → 映射 → 写仓储"**六件事。

```64:95:c:/code/WpfStudy/CommunityToolkitDemo/Services/MarkdownDataService.cs
public async Task LoadAsync(CancellationToken cancellationToken = default)
{
    // 放在开头清理：即使中途被取消或抛错，也不会残留上一次加载的错误信息。
    _errors.Clear();

    // 4 个文件互不依赖，先把任务全部启动（真正的并行发生在 IO 等待期间），
    // 再逐个 await 取结果。……
    var categoriesTask = ReadAsync<ProductCategory>(CategoriesFile, MapCategory, cancellationToken);
    var productsTask = ReadAsync<Product>(ProductsFile, MapProduct, cancellationToken);
    var ordersTask = ReadAsync<Order>(OrdersFile, MapOrder, cancellationToken);
    var devicesTask = ReadAsync<DeviceInfo>(DevicesFile, MapDevice, cancellationToken);

    var categories = await categoriesTask;
    var products = await productsTask;
    var orders = await ordersTask;
    var devices = await devicesTask;

    // 错误统一在这里汇总……
    CollectError(categories.Error);
    CollectError(products.Error);
    CollectError(orders.Error);
    CollectError(devices.Error);

    // 全部解析完成后再一次性替换，避免加载中途出现"部分数据"的不一致状态。
    _repository.ReplaceAll(categories.Items, products.Items, orders.Items, devices.Items);
}
```

注意这一段其实**写得很好**（并行启动、结果对象避免共享可变状态、一次性替换）——**问题不在实现质量，而在"职责范围"**：

- 想换成 CSV / SQLite / 远程接口？没有抽象层，得改这个类；
- 想按需分页加载（不全量载入）？`LoadAsync` 的语义就是"全量"；
- 想单独测解析逻辑？它和"文件定位 + 写仓储"绑在一起。

**改进方案：拆成"数据源" + "解析器"两个角色。**

```
IMarkdownDataService.LoadAsync()
  └─ IPosDataSource.ReadAsync()          ← 只管"从哪读、读出来是什么"
       └─ MarkdownTableParser / MarkdownRowReader   ← 只管"文本 → 实体"
  └─ PosRepository.ReplaceAll(...)        ← 只管"写进去"
```

拆完之后，换数据源只需要新增一个 `IPosDataSource` 实现，`MarkdownDataService` 一行不改。

**这件事我排在"值得做"而不是"必须做"**，因为它的收益是**未来**的，不是现在的。但从架构评分来看，它确实是拉低"扩展性"那项的主要因素。

### 3.3 同类型多设备无法寻址

这条是《架构审查报告》里被评级为"待改进 C+"的核心原因，我单独讲一下，因为它的**约束性质**很典型。

```188:197:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolManager.cs
/// <summary>按协议类型定位驱动。</summary>
/// <remarks>
/// 已知限制：当同一协议注册了多个设备时，这里只会返回<b>最先注册</b>的那一个，
/// 因此"同类型第二台设备"目前无法被寻址（例如第二块客显屏、第二台小票机）。
/// 若要支持多设备，需要把 <see cref="IProtocolManager"/> 的语义方法扩展为
/// "按设备 Id + 指令"寻址（属破坏性接口变更，未在本次向后兼容优化范围内实施），
/// 或改为按设备 Id 注册独立的管理器实例。
/// </remarks>
private IProtocolDriver? Find(ProtocolType type)
    => _drivers.FirstOrDefault(d => d.Type == type);
```

**为什么会这样？** 因为 `IProtocolManager` 的语义方法本身就是"按协议类型"设计的：

```106:117:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolManager.cs
public Task<bool> RequestBarcodeScanAsync(CancellationToken cancellationToken = default)
    => SendToAsync(ProtocolType.SerialPort, ProtocolKeys.ScanCommand, "上位机触发扫码", cancellationToken);

public Task<bool> PushDisplayAmountAsync(decimal amount, CancellationToken cancellationToken = default)
    => SendToAsync(
        ProtocolType.Socket,
        $"{ProtocolKeys.DisplayAmountPrefix}{amount.ToString("F2", CultureInfo.InvariantCulture)}",
        "推送客显屏应收金额",
        cancellationToken);
```

`PushDisplayAmountAsync(amount)` 连"发给哪块屏"这个参数都没有——**因为接口一开始就没有"设备"这个概念，只有"协议类型"。**

**所以这个问题的正解不是"改 `Find`"，而是"改接口语义"**：

```csharp
// 现在（按协议类型）：
Task<bool> PushDisplayAmountAsync(decimal amount, ...);

// 需要演进为（按设备寻址）：
Task<bool> SendAsync(string deviceId, DeviceCommand command, ...);
```

**这是一次破坏性接口变更**，报告明确把它排在"后续批次"而没有硬塞进兼容性改造里。**我认同这个决定**，理由是：现在的接口"能用"（单设备场景完全正常），而破坏性变更的成本必须在真实需求（真的要接第二块屏）出现时才值得付。

**这条经验值得记住：知道一个限制的存在，并且写清楚它的边界和改法，比"暂时用不到就先不管"要专业得多。** 那段 `<remarks>` 就是为此存在的。

### 3.4 表现层仍然直接依赖 WPF 集合类型

性能报告 6.3 提到：`CashierViewModel` 持有 WPF 的集合类型，业务筛选逻辑与 UI 类型混在一起，筛选规则无法复用。

这个问题在批次 3 里改善了不少——筛选已经下沉到 `IProductQuery`，`CashierViewModel` 不再持有 `ListCollectionView`：

```127:134:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/CashierViewModel.cs
/// <summary>
/// 当前分类/关键字过滤后的商品。
/// </summary>
/// <remarks>
/// 暴露具体集合类型而非 <c>ICollectionView</c>：过滤已下沉到 <see cref="IProductQuery"/>，
/// 不再需要 WPF 视图层参与，界面只需一个可观察集合。
/// </remarks>
public ObservableCollection<Product> Products => _products;
```

**但"依赖 `ObservableCollection<T>`"这件事本身还在。** 这意味着 `CashierViewModel` 依然无法脱离 WPF 做纯单元测试（要测它就得起 STA 线程、造 WPF 类型）。

**改进方案**：`CashierViewModel` 对外暴露 `IReadOnlyList<Product>`，由 View 层的 `CollectionViewSource` 接收；或者继续走现在的路线——**接受这个依赖，但把"必须要 WPF"的部分压到最小**（现在只剩"集合类型"这一项了）。

**我的实际选择是后者。** 理由：项目里已经有 `StaTestRunner` 专门解决"在测试里起 STA 线程"这件事，成本可控；而完全去 WPF 化会让 ViewModel 与 XAML 的绑定更绕。**这是一个"用一点点测试便利换 ViewModel 简洁性"的取舍，我选了简洁。**

### 3.5 性能护栏要"进日常"，不能只跑一次

性能报告 6.5 说了一句很关键的话：

> 本次改造前无任何性能测试，导致 8 MB 上限与 10w 需求的冲突**直到实测才暴露**。

**这句才是整份报告里最贵的一句话。** 一个性能问题如果只能靠"人工发现"，那它必然会在某次重构后悄悄回来。

现在项目里已经有 14 个性能基准用例了，**缺的是"每次改完都跑一遍"这个习惯和护栏**。

**改进方案**：把基准用例纳入常规回归（本地提交前跑一次，或接入 CI），并且**对关键项设"不劣化"阈值**（报告批次 5 的验收就有"全部 11 项不劣化于基线"这一条）。

## 四、锦上添花：不影响正确性的三件事

这三件我列出来只是"让账目完整"，**真没空的时候可以不做**。

### 4.1 四个未使用的转换器

《架构审查报告》P2-21 列出了四个"全量 XAML grep 无引用"的转换器：`InverseBooleanConverter`、`EqualityToBooleanConverter`、`TimeTextConverter`、`PaymentMethodToTextConverter`。

但报告给的处置方案是**保留 + 补注释说明用途**，理由是兼容性红线不允许删除公开成员：

> **优化（保守方案，本次采用）**：保留类型（属公开成员，删除违反兼容性红线），补 `/// <remarks>` 说明其用途与"当前未使用"状态，避免被误判为可删。

**我完全认同这个处置，而且它比"删掉"更需要纪律**——因为死代码最大的危害不是占内存，而是"让下一个人以为它有用"或"让下一个人以为它可以删"。**加一句注释，两个误解同时消除。**

> 如果这是一个"从零开始的新项目"、没有兼容性约束，那正确的做法就是直接删。**"保留还是删"取决于有没有对外契约，不取决于代码本身好不好。**

### 4.2 命名与注释规范化

报告 C1 提到：像 `ShortNameOf` 这类命名可以规范，部分公开成员缺 `<param>` / `<returns>`。

这个项目的注释整体评价是"优秀 A-"，**但确实存在"历史性注释"**——就是那些描述"改造前是什么样"的注释。它们对理解演进有帮助，但在代码稳定后会慢慢变成噪音。

**建议**：把"为什么这么写"的注释留下（这是最有价值的），把"以前是怎么写的"移到提交信息或这类文章里。

### 4.3 分析器与代码样式检查

`EnforceCodeStyleInBuild` 目前是关的，理由写在工程文件里：

```19:20:c:/code/WpfStudy/CommunityToolkitDemo/CommunityToolkitDemo.csproj
<!-- 生成器会产生大量 partial 成员，关闭严格样式检查避免噪音 -->
<EnforceCodeStyleInBuild>false</EnforceCodeStyleInBuild>
```

**这个理由成立**（源生成器产生的 partial 成员确实会带来大量样式告警），但如果做单人项目的话，代价不大；将来多人协作时值得重新评估——**至少把"明显的问题"（未使用的 `using`、未处理的返回值）打开**。

顺便认识一下那个"给 WPF 写测试"的关键小工具：

```14:44:c:/code/WpfStudy/CommunityToolkitDemo/tests/CommunityToolkitDemo.Tests/StaTestRunner.cs
internal static class StaTestRunner
{
    /// <summary>在 STA 线程上同步执行 <paramref name="action"/>，并把异常原样抛出。</summary>
    public static void Run(Action action)
    {
        ArgumentNullException.ThrowIfNull(action);

        Exception? captured = null;

        var thread = new Thread(() =>
        {
            try
            {
                action();
            }
            catch (Exception ex)
            {
                captured = ex;
            }
        });

        thread.SetApartmentState(ApartmentState.STA);
        thread.IsBackground = true;
        thread.Start();
        thread.Join();

        if (captured is not null)
        {
            ExceptionDispatchInfo.Capture(captured).Throw();
        }
    }
}
```

**为什么需要它？** xUnit 默认的测试线程是 **MTA**，而 WPF 的视觉树要求 **STA**——直接 `new UIElement()` 会抛 `InvalidOperationException`。这个小工具就干一件事：**为每个测试体单起一条 STA 线程，并等它跑完。**

两个细节很讲究：

- **异常用 `ExceptionDispatchInfo.Capture(...).Throw()` 回抛**，保留原始堆栈。如果直接 `throw captured;`，堆栈会被重置成"在测试方法里抛出"，你就看不到真正出错的位置了；
- **`thread.Join()` 保证测试体真的跑完**再返回，否则 xUnit 会以为测试通过了。

### 第 5 天：看看性能长什么样

**目标：把前面几篇讲的性能数字，变成你自己跑出来的数字。**

```powershell
# 1) 生成 10 万条商品数据（不会覆盖演示用的 47 行数据）
pwsh -File tools/GenerateProducts.ps1

# 2) 只跑性能基准，看详细输出
dotnet test tests/CommunityToolkitDemo.Tests/CommunityToolkitDemo.Tests.csproj `
  --filter "FullyQualifiedName~Performance" `
  --logger "console;verbosity=detailed"
```

你会看到 14 项基准的实测输出，其中包括：

- 线性扫描 vs 索引查找的**同轮对照**（这是最有说服力的一组，因为它排除了机器负载差异）；
- 流式解析路径 vs 旧字典式路径的耗时与分配对比。

**为什么要"同轮对照"？** 因为跨时间、跨机器的绝对耗时不可比（报告 10.4 明确写了"机器负载敏感，同条件实测在 33~95 ms 区间波动"）。**只有在同一个进程里、同一时刻跑出来的两组数字，才值得直接比。** 这也是我后来才学会的——**做性能对比时，对照组比绝对值重要得多。**

## 八、结语

这一篇我想让你带走的，其实是**一种看代码的眼光**：

1. **分清"已完成"和"未完成"。** 别把已经修好的问题当成骂人的理由，也别把"差 8% 没达标"和"完全没做"混为一谈。
2. **改进要有优先级，而且要有"为什么不改"。** 会持续变坏的先修；妨碍演进的排第二；锦上添花的随手做。
3. **"已知限制"要写进注释。** 比如 `Find(type)` 只返回首个驱动态、比如 Reset 时容器无法回收——**写清楚边界和改法，比默默留着强一百倍。**
4. **上手新项目最有效的方式是"跟一条链路"**，而不是从 `Main` 往下读。
