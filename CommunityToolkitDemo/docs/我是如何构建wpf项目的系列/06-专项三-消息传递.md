前两篇一直在讲"怎么把活搬走、怎么把结果送回来"。

这一篇讲的是"送回来之后，送给谁"。

听起来很简单，但我在这上面翻过一次车：**第一版代码里，我的 `MainWindowViewModel` 直接持有 `CashierViewModel` 的引用，然后互相调方法。**

代码能跑，但越写越难受：主窗口要认识收银台，收银台要认识主窗口，设备监控页又要认识它们俩……最后变成一团互相引用的网，删掉任何一个类都得改十几个地方。

这一篇就是我怎么从"互相持有"改成"广播站"的过程。

## 一、先看看这个项目到底需要传递什么

把需求列出来，你会发现问题比想象的多：

| 需求 | 谁产生 | 谁关心 |
| --- | --- | --- |
| 购物车变了（件数/金额） | 购物车服务 | 主窗口状态栏、收银台结算面板 |
| 扫码枪扫到条码了 | 串口协议驱动 | 收银台（自动加购） |
| 设备报警了 | 任意协议驱动 | 主窗口提示条、设备监控页警示条 |
| 要弹一条全局提示 | 任何地方 | 主窗口底部提示条 |
| 设置保存了 | 设置服务 | 主窗口（门店名）、收银台（默认支付、超卖上限） |
| 数据加载完了 | 启动流程 | 收银台（重建分类、刷新商品） |
| 想切到收银台页面 | 收银台自己 | 主窗口（导航外壳） |
| 订单支付成功了 | 收银台 | 主窗口状态栏 |

**这张表最要命的是"一对多"和"多对一"：**

- `StatusNotificationMessage` 的发送方有十几处（收银、监控、启动、设置……），接收方只有一个；
- `DeviceAlarmMessage` 的发送方是协议层，接收方有两个（主窗口 + 监控页）；
- `CartChangedMessage` 发送方一个，接收方两个。

如果用"互相持有引用"的方式实现，就会变成：收银台得认识主窗口，设备监控得认识主窗口，购物车服务得认识收银台和主窗口……

**于是我在第一个重构里推翻了这个设计。**

## 二、为什么我最后选了 `IMessenger`

先说结论：这个项目用的是 **`CommunityToolkit.Mvvm` 自带的 `IMessenger`**，注册方式只有一行：

```134:136:c:/code/WpfStudy/CommunityToolkitDemo/App.xaml.cs
// ---------- 基础设施 ----------
// 全局消息总线：整个应用共用同一个 WeakReferenceMessenger 实例
services.AddSingleton<IMessenger>(_ => WeakReferenceMessenger.Default);
```

**"全局唯一一个实例"**——这就是整个设计的支点。

把它想成一个**广播站**：

> 广播站不关心谁在听。电台主持人（发送方）只管对着话筒播报"**购物车变更了，件数 3、合计 12.5 元**"。
> 谁家收音机（接收方）调到了这个频道，谁就听到。
> 主持人不需要认识任何一位听众，听众也不需要认识主持人。

换成技术语言，它给了我四样东西：

| 好处 | 具体含义 |
| --- | --- |
| **发送方不认识接收方** | 发送代码里只出现"消息类型"，不出现任何 ViewModel 的名字 |
| **接收方数量随意** | 一个消息可以被 0 个、1 个、N 个接收方消费，发送方代码不变 |
| **强类型** | 接收方法签名是 `Receive(CartChangedMessage message)`，编译器帮你检查，不用强转 |
| **无需显式引用** | 两个类在代码里完全不认识，也能通信（靠共同的"消息类型"作为契约） |

## 三、消息长什么样

项目里所有消息都在 `Messages/` 目录下，一共 8 个文件。它们长得非常统一：

```9:12:c:/code/WpfStudy/CommunityToolkitDemo/Messages/CartChangedMessage.cs
public sealed class CartChangedMessage : ValueChangedMessage<CartSummary>
{
    public CartChangedMessage(CartSummary summary) : base(summary) { }
}
```

**就这么几行。** 关键就是 `ValueChangedMessage<T>` 这个基类——它表示"**某个值变了**"，并把值放进 `Value` 属性。

### 3.1 载荷用 `record`，不可变

`CartSummary` 没有写成一个普通类，而是写成了 `record`：

```5:12:c:/code/WpfStudy/CommunityToolkitDemo/Messages/MessagePayloads.cs
/// <summary>购物车汇总信息（消息载荷，不可变）。</summary>
/// <param name="ItemCount">商品总件数</param>
/// <param name="KindCount">商品种类数</param>
/// <param name="Total">合计金额</param>
public sealed record CartSummary(int ItemCount, int KindCount, decimal Total)
{
    public static readonly CartSummary Empty = new(0, 0, 0m);
}
```

同一份文件里还有另外两个载荷：

```14:25:c:/code/WpfStudy/CommunityToolkitDemo/Messages/MessagePayloads.cs
/// <summary>设备报警载荷。</summary>
/// <param name="Protocol">来源协议</param>
/// <param name="DeviceName">设备名称</param>
/// <param name="Message">报警描述</param>
/// <param name="At">发生时间</param>
public sealed record DeviceAlarm(ProtocolType Protocol, string DeviceName, string Message, DateTime At);

/// <summary>数据加载完成载荷。</summary>
/// <param name="Succeeded">是否全部加载成功（无错误）</param>
/// <param name="Errors">加载过程中的错误信息</param>
/// <param name="LoadedAt">完成时间</param>
public sealed record DataLoaded(bool Succeeded, IReadOnlyList<string> Errors, DateTime LoadedAt);
```

**为什么是 `record` 而不是普通类？** 三个理由：

1. **它是"事件快照"，不该被改。** 一条"购物车件数 3、合计 12.5"的消息，接收方如果把它改成"件数 5"，别的接收方就会看到被污染的假数据。`record` 的 `init`-only 属性天然阻止了这种改法。
2. **一行搞定。** 不用写构造函数、不用写只读属性、不用写 `ToString`。
3. **值语义。** 测试里可以直接比较两个载荷是否相等，对"消息是否正确发出"的断言非常方便。

### 3.2 需要多种状态时，用"载荷 + 枚举"

全局提示条要区分提示级别（普通/成功/警告/错误），于是消息里包了一个带枚举的嵌套载荷：

```9:26:c:/code/WpfStudy/CommunityToolkitDemo/Messages/StatusNotificationMessage.cs
public sealed class StatusNotificationMessage : ValueChangedMessage<StatusNotificationMessage.Payload>
{
    public StatusNotificationMessage(string text, StatusLevel level = StatusLevel.Info)
        : base(new Payload(text, level, DateTime.Now))
    {
    }

    /// <summary>提示内容与级别</summary>
    public sealed record Payload(string Text, StatusLevel Level, DateTime At);

    public enum StatusLevel
    {
        Info,
        Success,
        Warning,
        Error
    }
}
```

**注意这里把 `Payload` 和 `StatusLevel` 做成了嵌套类型。** 好处是它们在命名空间里不占名字，也不会跟别处的"Level"撞名。发送方写起来也顺手：

```148:150:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/SettingsViewModel.cs
_messenger.Send(new StatusNotificationMessage(
    $"门店参数已保存：{StoreName.Trim()}",
    StatusNotificationMessage.StatusLevel.Success));
```

### 3.3 常量收敛：不允许魔法字符串

导航消息是最典型的一例：

```6:17:c:/code/WpfStudy/CommunityToolkitDemo/Messages/NavigateMessage.cs
public sealed class NavigateMessage : ValueChangedMessage<string>
{
    public NavigateMessage(string pageKey) : base(pageKey) { }

    /// <summary>页面标识常量，避免魔法字符串</summary>
    public static class Pages
    {
        public const string Cashier = "cashier";
        public const string Device = "device";
        public const string Settings = "settings";
    }
}
```

用 `"cashier"` 这种裸字符串散落在各处，一旦页面标识改了，你根本搜不出来。**把字符串收进一个 `Pages` 静态类，就有了一处可改、一处可搜、编译器管不住的错也变成运行时立刻暴露的错（值只有三个，改起来一目了然）。**

**看到这个接口列表，不用读一行方法体就知道"它关心哪些事件"。** 这比在构造函数里藏十几行 `messenger.Register<...>()` 清晰太多了。

### 5.2 实现 `Receive`

每个 `IRecipient<T>` 对应一个 `Receive` 方法重载：

```223:256:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/MainWindowViewModel.cs
#region 消息接收

public void Receive(CartChangedMessage message)
{
    CartItemCount = message.Value.ItemCount;
    CartTotal = message.Value.Total;
}

public void Receive(StatusNotificationMessage message)
{
    StatusMessage = message.Value.Text;
    StatusLevel = message.Value.Level;
    RestartStatusTimer();
}

public void Receive(DeviceAlarmMessage message)
{
    StatusMessage = $"[{message.Value.DeviceName}] {message.Value.Message}";
    StatusLevel = StatusNotificationMessage.StatusLevel.Warning;
    RestartStatusTimer();
}

public void Receive(PaymentCompletedMessage message)
{
    StatusMessage = $"订单 {message.Value.OrderNo} 支付成功，收款 ¥{message.Value.Total:N2}（{message.Value.PaymentText}）";
    StatusLevel = StatusNotificationMessage.StatusLevel.Success;
    RestartStatusTimer();
}

public void Receive(NavigateMessage message) => Navigate(message.Value);

/// <summary>设置保存后同步门店名称。</summary>
public void Receive(SettingsChangedMessage message) => StoreName = message.Value.StoreName;

#endregion
```

**方法重载的写法特别舒服：** 六个 `Receive` 挨在一起，一眼看完"收到消息后我做了什么"。

### 5.3 `IsActive` 才是那个开关

声明了 `IRecipient` **不等于**就订阅上了。真正打开开关的是这一句：

```118:119:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/MainWindowViewModel.cs
// 激活消息接收：ObservableRecipient 内部会调用 Messenger.RegisterAll(this)
IsActive = true;
```

`IsActive = true` 时，`ObservableRecipient` 会扫描本类实现了哪些 `IRecipient<T>`，按类型**批量注册**；`IsActive = false` 时**批量注销**。

**而这个开关还能用来做"省电"：**

```205:218:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/MainWindowViewModel.cs
// ObservableRecipient 知识点：IsActive 控制消息订阅的注册/注销。
// 设备监控页会产生大量报文，离开时置为非激活以停止订阅，回到页面再恢复。
// 注意：仅按"当前/目标实例类型"判断，避免为了激活而解析 DeviceMonitorViewModel 导致提前实例化。
if (CurrentViewModel is DeviceMonitorViewModel leaving && !ReferenceEquals(leaving, viewModel))
{
    leaving.IsActive = false;
}

if (viewModel is DeviceMonitorViewModel entering)
{
    entering.IsActive = true;
}
```

设备监控页是唯一一个"高频接收"的页面。用户切走之后，它的 `IsActive` 变 `false`，`DeviceAlarmMessage` 就不再投递进来。

**注意那个"避免提前实例化"的注释。** 页面 ViewModel 是单例、惰性解析的；如果这里写成 `_pageFactory(typeof(DeviceMonitorViewModel)) is DeviceMonitorViewModel m` 去判断，就会**为了判断它的类型而把它创建出来**——一个本来还没用到的页面，就这么被实例化了。这种"为了看一眼就把对象造出来"的写法是新手很爱犯的错，项目里用 `CurrentViewModel is DeviceMonitorViewModel leaving` 绕开了。

顺便对照一下收银台：

```115:116:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/CashierViewModel.cs
// 收银台需要随时响应扫码枪，因此常驻激活
IsActive = true;
```

**"哪里需要长期在线，哪里需要按需在线"——这句话决定了 `IsActive` 怎么用。**

## 六、发送：`Messenger.Send`

发送只需要一行。`ObservableRecipient` 帮我们把 `Messenger` 属性准备好了（`MainWindowViewModel : base(messenger)`），服务类则是构造函数注入。

**服务层的发送：**

```161:162:c:/code/WpfStudy/CommunityToolkitDemo/Services/CartService.cs
/// <summary>广播购物车汇总：主窗口状态栏等订阅方据此刷新。</summary>
private void Publish() => _messenger.Send(new CartChangedMessage(Summary));
```

```21:26:c:/code/WpfStudy/CommunityToolkitDemo/Services/SettingsService.cs
ArgumentNullException.ThrowIfNull(settings);

Current = settings;
_messenger.Send(new SettingsChangedMessage(settings));
```

**注意 `Publish()` 这个方法名。** 购物车的每个写操作（`Add` / `Increase` / `Decrease` / `Remove` / `Clear`）最后都会调它一次。**"改完就广播"这个纪律，让购物车的任何变化都不会漏掉通知。**

```86:107:c:/code/WpfStudy/CommunityToolkitDemo/Services/CartService.cs
public bool Increase(CartItem item)
{
    if (item is null)
    {
        return false;
    }

    var maxQuantity = CartLimits.MaxQuantityFor(item.Product, _settings.Current.AllowOversell);

    // 顺手同步行项上限：库存或"允许超卖"设置变化后，
    // 界面绑定的"+"按钮可用状态能跟着回到正确值。
    item.MaxQuantity = maxQuantity;

    if (item.Quantity >= maxQuantity)
    {
        return false;
    }

    item.Quantity++;
    Publish();
    return true;
}
```

**ViewModel 里的发送：**

```394:399:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/CashierViewModel.cs
// 4) 广播支付完成 + 全局提示
Messenger.Send(new PaymentCompletedMessage(order));
Messenger.Send(new StatusNotificationMessage(
    $"订单 {order.OrderNo} 结算成功，收款 ¥{order.Total:F2}",
    StatusNotificationMessage.StatusLevel.Success));
```

**这里我特别想讲一个取舍：`Send` 是同步的。**

`Send` 会**立刻、依次、在当前线程上**调用所有接收方。这意味着：

- 好处：日志顺序清晰，调试时调用栈一眼看到底（发送方 → 接收方的 `Receive` 是同一根调用栈）；
- 坏处：**接收方慢，发送方就慢；接收方抛异常，异常会直接冒到发送方**。

所以项目里有个纪律：**`Receive` 里只做"改几个属性"这种轻量操作。** 看第六节那些实现，全是赋值 + `RestartStatusTimer()`，没有一个是耗时的。

> 如果将来某条消息真的需要耗时处理，正确的做法不是把 `Send` 改成异步，而是**在 `Receive` 里 fire-and-forget 一个异步方法**（`_ = DoWorkAsync()`），并在内部自己兜异常——就像 `App.InitializeAsync` 那样。

## 七、关键问题：消息在哪个线程被处理？

这是我在上一篇埋的伏笔，也是我在这个项目里**踩得最惨的一个坑**。

**规则一句话：`Send` 在哪个线程调，`Receive` 就在哪个线程跑。**

所以看这个桥接器：

```48:64:c:/code/WpfStudy/CommunityToolkitDemo/Services/ProtocolMessageBridge.cs
/// <summary>识别串口扫码枪回传的条码报文并广播。</summary>
private void OnFrameReceived(object? sender, ProtocolFrame frame)
{
    if (frame.Type is not ProtocolType.SerialPort ||
        frame.Direction is not ProtocolDirection.In ||
        frame.Values is null ||
        !frame.Values.TryGetValue(ProtocolKeys.Barcode, out var barcode) ||
        string.IsNullOrWhiteSpace(barcode))
    {
        return;
    }

    UiDispatcher.Post(() => _messenger.Send(new BarcodeScannedMessage(barcode)));
}

private void OnAlarmRaised(object? sender, DeviceAlarm alarm)
    => UiDispatcher.Post(() => _messenger.Send(new DeviceAlarmMessage(alarm)));
```

**`UiDispatcher.Post(() => _messenger.Send(...))` —— 把 `Send` 本身包进 `Post`，而不是让接收方去处理线程问题。**

为什么要这么写？我们顺着走一遍：

1. 串口驱动在线程池线程上造出一条条码报文，触发 `FrameReceived` 事件；
2. `ProtocolMessageBridge.OnFrameReceived` 在**线程池线程**上被调用；
3. 如果它直接 `_messenger.Send(...)`，那么接收方 `CashierViewModel.Receive(BarcodeScannedMessage)` 也在**线程池线程**上执行；
4. 而它做的事是——

```468:473:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/CashierViewModel.cs
/// <summary>扫码枪扫到条码 → 自动加购并跳回收银台。</summary>
public void Receive(BarcodeScannedMessage message)
{
    AddByBarcodeCore(message.Value);
    Messenger.Send(new NavigateMessage(NavigateMessage.Pages.Cashier));
}
```

`AddByBarcodeCore` 里会往 `ObservableCollection<CartItem>` 里加数据（`Services/CartService.cs:53 Items.Add(item)`）、还会改 `ObservableProperty`……

**在第 3 步直接 `Send`，第 4 步就会炸在 `InvalidOperationException` 上。**

### 一个设计的取舍

我在这里做过一个选择：

| 方案 | 做法 | 结果 |
| --- | --- | --- |
| A | 让每个 `Receive` 自己记得切回 UI 线程 | **每个接收方都要写一遍 `UiDispatcher.Post`**，漏一个就是随机崩溃 |
| B | **让发送方保证"消息一定在 UI 线程上发出"** | 接收方完全不用考虑线程，写起来跟普通同步代码一样 |

**项目选了 B。** 因为发送方只有 1 个（桥接器），接收方有 2 个（收银台、监控页）、将来可能更多。**把复杂度压在那一个点上，而不是散布到每一个接收点上。**

这条纪律的代价是：**谁在非 UI 线程上 `Send`，谁就得自己负责 `Post`。** 所以我把这条写进注释（`ProtocolMessageBridge` 的类注释第 18-19 行），并在这一篇里专门讲一遍。

### 那张"谁发谁收"的表可以再看一遍

回头再看第四节的表，你会发现**所有"后台线程发起"的消息，发送点都包着 `UiDispatcher.Post`**：

- `BarcodeScannedMessage` ← `ProtocolMessageBridge.cs:60`（有 `Post`）
- `DeviceAlarmMessage` ← `ProtocolMessageBridge.cs:64`（有 `Post`）

而**所有"UI 线程发起"的消息都是裸 `Send`**：

- `CartChangedMessage`（用户在 UI 上点加购）
- `SettingsChangedMessage`（用户在设置页点保存）
- `PaymentCompletedMessage`（用户在收银台点结算）
- `StatusNotificationMessage`（绝大多数来自 UI 操作）

唯一的例外是启动流程：

```76:81:c:/code/WpfStudy/CommunityToolkitDemo/App.xaml.cs
// 数据就绪广播：页面据此刷新（如收银台重建分类 / 商品视图）
Services.GetRequiredService<IMessenger>().Send(new DataLoadedMessage(
    new DataLoaded(dataService.LoadErrors.Count == 0, dataService.LoadErrors.ToArray(), DateTime.Now)));

// 数据就绪后再连接设备（驱动会按仓储中的设备配置建立会话）
await Services.GetRequiredService<IProtocolManager>().ConnectAllAsync();
```

`InitializeAsync` 是在 UI 线程上被调用的（`OnStartup` 里 `_ = InitializeAsync()`），而 `LoadAsync()` 内部的 `await` 会回到 UI 线程——**所以第 77 行的 `Send` 恰好在 UI 线程上**，`CashierViewModel.Receive(DataLoadedMessage)` 里重建分类才安全。

> **这类"恰好安全"是可以的，但也是脆弱的。** 如果哪天有人给 `InitializeAsync` 外面套一个 `Task.Run`，第 77 行就会在后台线程发消息，收银台直接崩。
> **知道它为什么安全，比知道它安全更重要。**

## 八、为什么协议层用 `event`，业务层用消息？

写到这里肯定有人要问：既然消息这么好，为什么 `ProtocolDriverBase` 还在用 C# `event`？

```65:69:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolDriverBase.cs
public event EventHandler<ProtocolFrame>? FrameReceived;

public event EventHandler<ConnectionState>? StateChanged;

public event EventHandler<string>? AlarmRaised;
```

我的答案是：**这两者的适用场景本来就不一样。**

| 维度 | C# `event` | `IMessenger` |
| --- | --- | --- |
| 关系 | **一对一 / 一对少**（"我这个对象上发生了事"） | **一对多、多对一、多对多**（"全局世界里发生了事"） |
| 发送方是否知道接收方 | 不需要知道**具体是谁**，但必须暴露事件名，接收方**必须能引用到这个对象** | 完全不认识，只共享消息类型 |
| 类型安全 | 委托签名（`EventHandler<T>`） | 强类型消息类（可携带富载荷） |
| 生命周期 | **必须手动 `-=`**，忘了就是内存泄漏 + 幽灵回调 | 弱引用（`WeakReferenceMessenger`），但单例仍需显式注销 |
| 调试 | 调用栈直白，一眼看到谁触发的 | 需要打断点在 `Receive` 上 |
| 性能 | 更快，无字典查找 | 有类型查找开销（可忽略，但确实更慢） |

**落到这个项目上：**

- **协议驱动 → 协议管理器**：这是**确定的、一对一**的"硬件回调"关系。`ProtocolManager` 在构造函数里就把 5 个驱动的事件全订上了：

```30:35:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolManager.cs
foreach (var driver in _drivers)
{
    driver.FrameReceived += OnDriverFrameReceived;
    driver.StateChanged += OnDriverStateChanged;
    driver.AlarmRaised += OnDriverAlarmRaised;
}
```

驱动的生命周期由容器管理，和 `ProtocolManager` 一样长，退订在 `Dispose` 里做一次就够——**用 `event` 天经地义，还更省。**

- **协议层 → 业务层**：这是**跨层、一对多**的。收银台关心条码、监控页关心报警、主窗口关心所有东西。**用消息，两边都不必认识对方。**

**所以更准确的说法是：`event` 是"对象级的通知"，`IMessenger` 是"应用级的通知"。** 协议层的 `event` 保留在通信层内部，跨出层边界的那一步才由 `ProtocolMessageBridge` 翻译成消息：

```9:20:c:/code/WpfStudy/CommunityToolkitDemo/Services/ProtocolMessageBridge.cs
/// 协议层 → 消息总线的桥接器。
///
/// 为什么需要它？
/// 协议驱动只认识"报文"，业务页面只认识"消息"，两者不该互相依赖；
/// 由这个单例在中间做一次翻译，就把通信层与表现层彻底解耦：
/// - 串口扫到条码  → <see cref="BarcodeScannedMessage"/>（收银台自动加购）
/// - 驱动上报报警  → <see cref="DeviceAlarmMessage"/>（提示条 + 监控页）
///
/// 线程说明：驱动事件来自后台线程，这里统一经 <see cref="UiDispatcher"/> 切回 UI 线程再发送，
/// 保证接收方可以安全地更新 WPF 可观察集合。
```

**这个桥接器我特别喜欢。** 它只有 65 行，却承担了两个职责：**类型翻译**（报文 → 消息）和**线程整流**（后台线程 → UI 线程）。它存在的意义，就是让"通信层"和"表现层"两个世界不用互相认识。

## 九、弱引用与生命周期：`WeakReferenceMessenger` 的坑

先说清楚 `WeakReferenceMessenger` 到底弱在哪。

**它保存的是接收方的弱引用。** 也就是说，如果某个接收方对象**没有别的引用指向它**（只被消息总线持有），GC 可以照样把它回收掉。回收之后：

- 好的一面：不会像 `event` 那样因为"忘了 `-=`"就把对象永远钉在内存里；
- **坑的一面：你注册过的接收方可能"静默消失"。** 收不到消息、不报错、不抛异常——这种 bug 最难查。

**这个项目是怎么规避的？** 靠一条铁律：**所有消息接收方都是 DI 单例。**

```186:190:c:/code/WpfStudy/CommunityToolkitDemo/App.xaml.cs
// 页面 ViewModel 使用单例，切换页面时保留状态（购物车、日志等）
services.AddSingleton<MainWindowViewModel>();
services.AddSingleton<CashierViewModel>();
services.AddSingleton<DeviceMonitorViewModel>();
services.AddSingleton<SettingsViewModel>();
```

单例由容器持有强引用，不会被 GC 回收，所以"静默消失"的风险不存在。

**但单例带来另一个问题：它活得和整个应用一样久。** 不退订，就永远不会停止接收。所以项目里给每个接收方都安排了明确的注销点：

**主窗口 ViewModel：**

```298:322:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/MainWindowViewModel.cs
public void Dispose()
{
    if (_disposed)
    {
        return;
    }

    _disposed = true;

    _protocolManager.DriverStateChanged -= OnDriverStateChanged;

    _clockTimer.Stop();
    _statusTimer.Stop();

    // 当前若停留在设备监控页，停用它会顺带退订高频报文事件
    if (CurrentViewModel is DeviceMonitorViewModel monitor)
    {
        monitor.IsActive = false;
    }

    // ObservableRecipient：IsActive = false 会注销所有 IRecipient 订阅
    IsActive = false;

    GC.SuppressFinalize(this);
}
```

**设备监控页 ViewModel：**（`OnDeactivated` 已经在上一篇贴过，这里只点出它的位置 `DeviceMonitorViewModel.cs:201`）

**判断标准（我现在的习惯）：**

| 这个接收方的生命周期 | 需要手动注销吗 |
| --- | --- |
| 和 App 一样长（DI 单例、常驻激活） | **需要**，在 `Dispose` / `OnExit` 里 `IsActive = false` |
| 只在某个页面期间激活 | **需要**，`OnDeactivated` 里 `IsActive = false` |
| 会随页面销毁的临时对象 | 理论上弱引用会兜底，但**建议也显式注销**，别赌 |

> **"弱引用会帮你回收"不是"你可以不管"的理由。**
> 弱引用解决的是"内存泄漏"，解决不了"幽灵回调"（对象还活着，但已经不该接收了）。后者只能靠 `IsActive`。

## 十、消息传递的四条纪律

这四条是我在项目里慢慢定下来的，写在这里给你参考：

**① 载荷必须是不可变的（`record`）。**
消息一旦发出，就是一次"历史快照"。任何接收方都不该有能力改写它。

**② 字符串一律收敛成常量。**
`NavigateMessage.Pages.Cashier`、`ProtocolKeys.Barcode`，都是一样的思路。

**③ `Receive` 里只做轻量操作。**
因为 `Send` 是同步的——发送方会等所有接收方执行完。`Receive` 里做耗时操作，等于把耗时操作塞进了发送方的调用栈。

**④ 发送点负责线程。**
在非 UI 线程 `Send` 的时候，必须自己 `UiDispatcher.Post`。接收方默认"消息已经在 UI 线程上了"。

## 十一、我在消息传递上踩过的四个坑

| # | 当时的写法 | 现象 | 正确做法 | 项目对应位置 |
| --- | --- | --- | --- | --- |
| 1 | 实现了 `IRecipient<T>` 但忘了 `IsActive = true` | `Receive` **永远不触发**，不报错、不异常，纯静默 | 构造末尾（或加载后）显式激活 | `MainWindowViewModel.cs:119`、`CashierViewModel.cs:116` |
| 2 | 在后台线程直接 `_messenger.Send(...)` | 接收方改 `ObservableCollection` 时抛 `InvalidOperationException` | 发送点包 `UiDispatcher.Post` | `ProtocolMessageBridge.cs:60`、`:64` |
| 3 | 单例 ViewModel 切走页面后没注销 | 人在别的页面，`Receive` 还在被调用、CPU 不降 | `OnDeactivated` 里 `IsActive = false` | `MainWindowViewModel.cs:210`、`DeviceMonitorViewModel.cs:201` |
| 4 | 用 `event` 连接两个 ViewModel，忘了 `-=` | 页面重建后同一次操作被执行两遍（幽灵订阅） | 换 `IMessenger`，或用 `ObservableRecipient` 的 `IsActive` 统一管理 | 全项目业务层已改消息 |

**第 1 条是最阴的：** 它不报错。你写了 `Receive` 方法，编译通过，运行也正常，就是"没反应"。我第一次遇到这个问题时，在 `Receive` 里打了断点，发现根本不停——才意识到是没激活。

**第 4 条是我从"互相持有 + event"切换到 `IMessenger` 的直接原因。** 那次重构之后，我再也没写过手动 `-=` 的业务代码。

## 十二、小结：三句话记住这个专项

1. **`IMessenger` 是广播站，不是电话。** 发送方不认识接收方，接收方也不认识发送方，它们只共享"消息类型"这一份契约。
2. **`IRecipient<T>` 是订阅清单，`IsActive` 是总开关。** 清单写在类声明上（一眼看完），开关管注册/注销（生命周期）。
3. **`Send` 是同步的，且线程跟着调用方。** 所以：`Receive` 要轻；非 UI 线程发送时必须先 `Post`。

## 十三、给你的一张检查清单

| 检查项 | 要问的问题 |
| --- | --- |
| ① 契约 | 这个业务事件该不该走消息？它是不是"一对多/跨模块"的？ |
| ② 载荷 | 载荷是不是 `record`、是不是不可变、常量有没有收敛？ |
| ③ 订阅 | 接收方是不是声明了 `IRecipient<T>`？`IsActive = true` 了吗？ |
| ④ 线程 | 发送方在哪个线程？需要 `UiDispatcher.Post` 吗？ |
| ⑤ 生命周期 | 注销点在哪里？`Dispose` 还是 `OnDeactivated`？ |
| ⑥ 重量 | `Receive` 里有耗时操作吗？（`Send` 是同步的） |
