## 一、`VirtualizingWrapPanel`：让商品卡片墙数据一多也不卡

### 1.1 为什么需要它

收银台的"商品卡片墙"是典型的**换行网格**：一行摆 5 个，摆满换下一行。

WPF 内置有两个候选：

| 控件 | 问题 |
| --- | --- |
| `WrapPanel` | 布局好看，但**不虚拟化**——1000 个商品就生成 1000 个卡片控件 |
| `VirtualizingStackPanel`（`ListBox` 默认） | 能虚拟化，但只能**单行排列**，摆不出网格 |

**所以标准控件里没有"能换行 + 能虚拟化"的面板。** 这也是网上有很多第三方 `VirtualizingWrapPanel` 实现的原因。

我没引第三方库，自己写了一个（约 460 行），因为它同时是个极好的学习素材——**自定义面板涉及 WPF 布局系统最核心的两个接口：`MeasureOverride` / `ArrangeOverride` 和 `IScrollInfo`。**

### 1.2 思路：把"全部项"变成"可视区那几行"

核心思想一句话：

> **面板自己接管滚动（实现 `IScrollInfo`），然后只实例化"当前视口覆盖的那几行"。**

```
1000 个商品：
  不虚拟化 → 生成 1000 个卡片控件，测量 + 排列 1000 次
  虚拟化   → 只生成当前屏幕能看到的大约 10~15 个，滚动时回收旧的、生成新的
```

### 1.3 关键代码：`MeasureOverride`

```csharp
// CommunityToolkitDemo/Common/Controls/VirtualizingWrapPanel.cs:65-108
protected override Size MeasureOverride(Size availableSize)
{
    // 必须在触碰生成器（StartAt / GenerateNext / Remove）之前先访问 InternalChildren：
    // 首次访问会触发 WPF 内部的 ConnectToGenerator()，其中包含一次 RemoveAll() 重置生成器映射。
    // 若在 StartAt 生成过程中才首次访问，映射会在生成中途被清空，
    // 表现为“容器无法生成/无法复用”，甚至 Remove 时抛出 NullReferenceException。
    _ = InternalChildren.Count;

    var itemsControl = ItemsControl.GetItemsOwner(this);
    int itemCount = itemsControl?.Items.Count ?? 0;

    var (itemWidth, itemHeight) = ResolveItemSize();

    double availableWidth = double.IsInfinity(availableSize.Width) ? itemWidth : availableSize.Width;
    double availableHeight = double.IsInfinity(availableSize.Height) ? 0d : availableSize.Height;

    int itemsPerRow = Math.Max(1, (int)Math.Floor(availableWidth / itemWidth));
    int rowCount = itemCount == 0 ? 0 : (int)Math.Ceiling(itemCount / (double)itemsPerRow);

    _extent = new Size(availableWidth, rowCount * itemHeight);
    _viewport = new Size(availableWidth, availableHeight);
    CoerceOffsets();

    if (itemCount == 0)
    {
        return new Size(availableWidth, availableHeight);
    }

    // 计算当前视口覆盖的行区间（多测量一行，滚动时不至于立刻出现空白）
    int firstRow = Math.Max(0, (int)Math.Floor(_offset.Y / itemHeight));
    int lastRow = Math.Min(rowCount - 1, (int)Math.Ceiling((_offset.Y + _viewport.Height) / itemHeight) - 1);
    if (lastRow < firstRow)
    {
        lastRow = firstRow;
    }

    int firstIndex = firstRow * itemsPerRow;
    int lastIndex = Math.Min(itemCount - 1, ((lastRow + 1) * itemsPerRow) - 1);

    RealizeItems(firstIndex, lastIndex, itemWidth, itemHeight);
    CleanUpItems(firstIndex, lastIndex);

    return new Size(availableWidth, availableHeight);
}
```

这段代码里有 **4 个"只有自己写过才知道"的细节**：

**① `_ = InternalChildren.Count;` 那一行看着像废话，其实是保命的。**

它是"在触碰生成器之前先访问一次 `InternalChildren`"。为什么？看注释——**第一次访问 `InternalChildren` 会触发 WPF 内部的 `ConnectToGenerator()`，而它内部包含一次 `RemoveAll()` 重置生成器映射**。如果你在 `StartAt` 生成过程中才第一次访问，映射会在生成到一半时被清空，现象是"容器生成不出来"，甚至直接 `NullReferenceException`。

**这是我调了最久的一个 bug**，因为报错信息和真实原因隔了十万八千里。

**② `_extent` 是"假的高度"。**

```csharp
_extent = new Size(availableWidth, rowCount * itemHeight);
```

注意：这里的 `rowCount` 是**按全部商品算出来的行数**，不是按可视区。因为滚动条需要一个"总高度"来画滑块——虽然实际上你根本没生成那么多控件。

**所以 `ExtentHeight` 是"算出来"的，不是"量出来"的。** 这就是虚拟化面板必须自己算 `Extent` 的原因。

**③ 多测量一行。**

```csharp
int lastRow = Math.Min(rowCount - 1, (int)Math.Ceiling((_offset.Y + _viewport.Height) / itemHeight) - 1);
```

注释里写了"多测量一行，滚动时不至于立刻出现空白"。因为滚动是有惯性的、鼠标滚轮一次跳一大段，如果只精确测量视口覆盖的行，用户稍微一滚就会看到底部一条空白。

**④ `RealizeItems` + `CleanUpItems` 是一对。**

- `RealizeItems`：把可视区需要的容器要/造出来；
- `CleanUpItems`：把不在可视区的容器还回去。

```csharp
// CommunityToolkitDemo/Common/Controls/VirtualizingWrapPanel.cs:198-229
private void CleanUpItems(int firstIndex, int lastIndex)
{
    var generator = ItemContainerGenerator;
    if (generator is null)
    {
        return;
    }

    bool recycling = generator is IRecyclingItemContainerGenerator
                     && ResolveVirtualizationMode() == VirtualizationMode.Recycling;

    for (int i = InternalChildren.Count - 1; i >= 0; i--)
    {
        int index = generator.IndexFromGeneratorPosition(new GeneratorPosition(i, 0));
        if (index >= firstIndex && index <= lastIndex)
        {
            continue;
        }

        var position = new GeneratorPosition(i, 0);
        if (recycling)
        {
            ((IRecyclingItemContainerGenerator)generator).Recycle(position, 1);
        }
        else
        {
            generator.Remove(position, 1);
        }

        RemoveInternalChildRange(i, 1);
    }
}
```

注意这里有个 `Recycling` 分支：

- **`Recycling` 模式**：容器被 `Recycle` 回回收池，下次滚动进来时**复用旧容器**（只更新 `DataContext`）；
- **`Standard` 模式**：容器被 `Remove` 彻底丢弃，下次滚动进来时**重新创建**。

**为什么 `Recycling` 更快？** 因为创建控件（展开模板、建可视树）是很贵的动作。复用容器只改一个 `DataContext`，便宜得多。

**⑤ 从后往前遍历是个小技巧。**

```csharp
for (int i = InternalChildren.Count - 1; i >= 0; i--)
```

因为循环体里会 `RemoveInternalChildRange(i, 1)`（删除集合元素）。**从后往前删，索引不会被前面的删除操作打乱**；从前往后删就会"漏删一个又越界一个"。这是集合删除的通用套路。

### 1.4 一个"附加属性不继承"的坑

```csharp
// CommunityToolkitDemo/Common/Controls/VirtualizingWrapPanel.cs:259-277
/// <summary>
/// 解析生效的虚拟化模式。
///
/// <c>VirtualizingPanel.VirtualizationMode</c> 是附加属性且不参与属性值继承，
/// XAML 中写在 <see cref="ItemsControl"/>（如 ListBox）上的值不会自动传到 ItemsPanel 实例上。
/// 因此这里以面板自身显式设置为优先，未设置时回退读取 items host 的宿主控件，
/// 否则 <c>Recycling</c> 声明会被静默忽略、回收池永远为空。
/// </summary>
private VirtualizationMode ResolveVirtualizationMode()
{
    var mode = GetVirtualizationMode(this);
    if (mode != VirtualizationMode.Standard)
    {
        return mode;
    }

    var owner = ItemsControl.GetItemsOwner(this);
    return owner is null ? mode : GetVirtualizationMode(owner);
}
```

**这个坑很经典，值得单独记：**

`VirtualizationMode` 是个**附加属性**，你通常在 `ListBox` 上写：

```xml
<ListBox VirtualizingPanel.VirtualizationMode="Recycling" />
```

但**附加属性不参与属性值继承**，所以这个值**不会自动传到 `ItemsPanel` 里的 `VirtualizingWrapPanel` 实例上**。结果就是：您在 `ListBox` 上写了 `Recycling`，面板读到的还是默认的 `Standard`，**回收池永远是空的，声明被静默忽略**。

解法就是上面这段：**先读自己，读不到就回退去问宿主控件。**

### 1.5 另一个坑：`MakeVisible` 重入导致栈溢出

```csharp
// CommunityToolkitDemo/Common/Controls/VirtualizingWrapPanel.cs:406-421
public Rect MakeVisible(Visual visual, Rect rectangle)
{
    if (visual is not UIElement element)
    {
        return rectangle;
    }

    // MakeVisible 常由 BringIntoView 在布局过程中被同步调用（例如点击卡片后 Button 获得焦点）。
    // 此时若视口尚未测量（高度为 0）或生成器未就绪，任何滚动计算都会退化成：
    // SetVerticalOffset → InvalidateMeasure → 再次布局 → 再次 MakeVisible 的重入链，
    // 极端情况下会反复重入导致栈溢出。这里直接跳过，等视口有效后再处理。
    var generator = ItemContainerGenerator;
    if (generator is null || _viewport.Height <= 0)
    {
        return rectangle;
    }
    // ...
}
```

**这一段是我最喜欢的一处防御性代码**，因为它描述的是一类非常隐蔽的 bug：

用户点了一张商品卡片 → 卡片里的 `Button` 获得焦点 → WPF 触发 `BringIntoView` → 调用 `MakeVisible` → `MakeVisible` 里调 `SetVerticalOffset` → 触发 `InvalidateMeasure` → 重新布局 → 又调用 `MakeVisible` → ……

**这是一个"自发自收"的循环。** 平时可能只是白滚一下看不出来，但在"视口还没测量（高度为 0）"的边界情况下，这个循环停不下来，直接栈溢出崩溃。

解法很简单粗暴：**视口没准备好就什么都不做。** 这也是处理重入问题的通用思路——**先判断"我现在有没有条件做这件事"，没条件就退出，而不是硬算。**

> 想看这个面板的完整实现，直接打开 `Common/Controls/VirtualizingWrapPanel.cs`，459 行，注释很全。第 04 篇会从性能角度再把这几个点串一遍。

## 二、`CachedContentControl`：页面切换不重建界面

### 2.1 它是什么

内容区那一行代码，我特意用了一个自定义控件：

```xml
<!-- CommunityToolkitDemo/Views/MainWindow.xaml:202-205 -->
<controls:CachedContentControl Content="{Binding CurrentViewModel}" />
```

它的实现只有 73 行，但想法很实用：

```csharp
// CommunityToolkitDemo/Common/Controls/CachedContentControl.cs:6-63
/// <summary>
/// 缓存式内容宿主：按内容类型缓存隐式 DataTemplate 生成的 View 实例，
/// 切换页面时复用旧视觉树，避免每次导航都重建整棵 UI（商品卡片 / 日志行等）。
///
/// 知识点（WPF 内容模型与资源查找）：
/// - ContentPresenter 遇到 UIElement 内容时直接渲染，不会再套一次模板；
/// - 通过 <see cref="DataTemplateKey"/> 在资源链中查找按类型匹配的隐式 DataTemplate，
///   自行 LoadContent 并缓存，从而绕开"每次换内容就重建视图"的默认行为；
/// - 使用 <see cref="DependencyObject.SetCurrentValue"/> 回填视图，
///   不会破坏外部对 Content 的绑定。
/// </summary>
public class CachedContentControl : ContentControl
{
    /// <summary>视图模型类型 → 已实例化的视图，导航切换时复用</summary>
    private readonly Dictionary<Type, FrameworkElement> _views = new();

    protected override void OnContentChanged(object? oldContent, object? newContent)
    {
        base.OnContentChanged(oldContent, newContent);

        // 只处理"视图模型"内容；换成缓存视图后（FrameworkElement）不再二次处理，避免递归
        if (newContent is null || newContent is FrameworkElement)
        {
            return;
        }

        var view = GetOrCreateView(newContent);
        if (view is null)
        {
            return;
        }

        // 视图是复用实例，每次换页都要把 DataContext 指回当前视图模型
        view.DataContext = newContent;

        if (!ReferenceEquals(Content, view))
        {
            SetCurrentValue(ContentProperty, view);
        }
    }

    private FrameworkElement? GetOrCreateView(object viewModel)
    {
        var type = viewModel.GetType();

        if (_views.TryGetValue(type, out var cached))
        {
            return cached;
        }

        if (FindTemplate(type)?.LoadContent() is not FrameworkElement view)
        {
            return null;
        }

        _views[type] = view;
        return view;
    }
}
```

### 2.2 它解决的问题

**原生 `ContentControl` 的行为是：内容一变，就把旧的视觉树整个扔掉，按 `DataTemplate` 重新 `LoadContent` 一遍。**

也就是说，你从"收银台"切到"设备监控"再切回"收银台"，收银台的整棵界面树（商品卡片、购物车行、结算面板……）都会被销毁重建一遍。

这个代价很实在：

- 重建 = 重新解析 XAML 模板 + 重新构造控件对象 + 重新测量排列；
- 用户看到的可能是**一次可见的闪烁**，或者切换时明显"顿一下"。

`CachedContentControl` 的做法是：**把创建好的 View 实例按 ViewModel 类型存进字典，下次切换直接拿出来用。** 视觉树不动，只是把 `DataContext` 指回当前 ViewModel。

### 2.3 三个值得学的细节

**① 用"类型"当缓存键，用 `DataTemplateKey` 找模板。**

```csharp
var key = new DataTemplateKey(type);
return TryFindResource(key) as DataTemplate
       ?? Application.Current?.TryFindResource(key) as DataTemplate;
```

`DataTemplateKey` 就是 WPF 内部用来做"隐式模板查找"的东西。**我们自己复现了它的查找逻辑**：先在本元素的资源链里找，再兜底到应用级资源（也就是 `App.xaml` 里那三个 `DataTemplate`）。

**② 用 `SetCurrentValue` 而不是直接赋值。**

```csharp
SetCurrentValue(ContentProperty, view);
```

**这两个写法的区别很关键：**

- `Content = view;` 会**覆盖掉**外部对 `Content` 的绑定——`{Binding CurrentViewModel}` 这个绑定就被干掉了；
- `SetCurrentValue(ContentProperty, view)` 会**保留原有的绑定**，只是临时改一下当前值。

**所以 `SetCurrentValue` 是"我只想改值，不想破坏绑定"时的正确选择。** 这个 API 在写自定义控件时特别有用，很多人不知道它。

**③ 递归防护。**

```csharp
if (newContent is null || newContent is FrameworkElement)
{
    return;
}
```

因为 `OnContentChanged` 里会把 `Content` 换成 View（一个 `FrameworkElement`），这又会再触发一次 `OnContentChanged`。如果不判断，就是无限递归。

**"改 A 会触发 A 的回调"这类场景，一定要在回调开头写一句"如果是我自己改的，直接返回"。**

## 三、一份数据，两处刷新：共享 `LiveMetricItem` 实例

### 3.1 场景

设备监控页有两个地方要显示"实时指标"：

- **每张设备卡片**上显示"本协议的最新几个指标"；
- **下方的实时数据表**显示所有协议的指标明细。

如果做成两份数据：同一份温度值要写两次、通知两次、还要保证两边不打架。

**项目的做法是：只做一份 `LiveMetricItem`，两个视图引用同一批实例。**

```csharp
// CommunityToolkitDemo/ViewModels/LiveMetricItem.cs:6-12
/// <summary>
/// 实时数据表的一行：某个协议上报的某个指标的最新值。
///
/// 同一个实例会同时出现在"设备卡片"和"实时数据表"两个视图中，
/// 因此一次属性变更能让两处同步刷新（ObservableObject 的价值）。
/// </summary>
public partial class LiveMetricItem : ObservableObject
```

设备卡片里：

```csharp
// CommunityToolkitDemo/ViewModels/DeviceCardViewModel.cs:63-64
/// <summary>该协议的最新指标（与实时数据表共享同一批实例）</summary>
public ObservableCollection<LiveMetricItem> Metrics { get; } = new();
```

### 3.2 为什么这招好用

`LiveMetricItem` 是个 `ObservableObject`。当后台报文到达、某个指标的值被更新时：

```
LiveMetricItem.Value = "12.35 kg"
  └─> PropertyChanged 事件
        ├─> 设备卡片上的那个 TextBlock 收到 → 刷新
        └─> 实时数据表里的那行 TextBlock 收到 → 刷新
```

**一次赋值，两处刷新，而且没有一行"同步代码"。**

这就是 WPF 数据绑定最迷人的地方：**数据只有一份，视图可以有无数个，视图通过订阅同一个对象来保持同步。**

**反过来，如果你做了两个对象，就得写"A 变了通知 B 变"的同步代码**——这种代码永远是 bug 的温床（漏同步、循环触发、顺序依赖）。

### 3.3 一个"小气"但重要的细节

`LiveMetricItem` 里的字段是这样的：

```csharp
/// <summary>最新值（带单位）</summary>
[ObservableProperty]
private string _value = "-";

/// <summary>最近一次更新时间</summary>
[ObservableProperty]
private DateTime _updatedAt;

/// <summary>数值刚更新时为 true，用于界面高亮闪烁</summary>
[ObservableProperty]
private bool _isFlashing;
```

注意 `Value` 和 `UpdatedAt` 都是 `[ObservableProperty]`，而 `Protocol`、`Name` 是**只读的普通属性**（因为它们创建后不会变）。

**这个区分很重要**：`[ObservableProperty]` 是有成本的（每次赋值都要比较、可能触发通知链）。**只给"会变的"数据加通知，不变的数据就用只读属性。**

很多人习惯把所有属性都写成 `[ObservableProperty]`，那会白白增加开销。

## 四、`ProtocolKeys`：把"暗号"变成明规则

### 4.1 它解决的问题

硬件通信里有个非常常见的坏味道：**驱动和上层之间靠字符串暗号沟通。**

- 串口驱动生产一条报文，里面有个键叫 `"条码"`；
- 报文桥接器要读这个键，写的是 `frame.Values["条码"]`。

看起来没问题？问题是这两个字符串写在两个不同的文件里，**编译器完全不知道它们有关系**。哪天有人在驱动里把 `"条码"` 改成 `"条形码"`，编译一样通过，测试可能也过（如果测试没覆盖），**故障只在运行时才暴露，而且是"扫码没反应"这种最难查的症状。**

### 4.2 项目的解法

```csharp
// CommunityToolkitDemo/Protocols/ProtocolKeys.cs:3-30
/// <summary>
/// 协议中立常量：把"跨层引用的报文键名与指令载荷"从具体驱动里抽出来。
///
/// 为什么需要它？
/// 报文键名（如条码）与指令载荷（如触发扫码）是<b>驱动与上层之间的隐式契约</b>：
/// 驱动负责"生产"，协议管理器与报文桥接器负责"消费"。
/// 如果这些字面量定义在某个具体驱动类里，上层就会被迫依赖该驱动类型（分层倒置），
/// 而字符串常量本身也没有编译期保护 —— 一旦两处不一致，故障只在运行时才暴露。
/// 收敛到本类后，生产方与消费方引用同一常量，改动只需改一处。
/// </summary>
public static class ProtocolKeys
{
    /// <summary>条码在 <see cref="Models.ProtocolFrame.Values"/> 中的键名。</summary>
    /// <remarks>生产方：串口驱动；消费方：<c>ProtocolMessageBridge</c>（识别扫码报文）。</remarks>
    public const string Barcode = "条码";

    /// <summary>触发扫码的指令载荷。</summary>
    /// <remarks>生产方：<c>ProtocolManager.RequestBarcodeScanAsync</c>；消费方：串口驱动。</remarks>
    public const string ScanCommand = "TRIGGER_SCAN";

    /// <summary>客显屏金额指令前缀（完整指令形如 <c>AMT=12.50</c>）。</summary>
    /// <remarks>生产方：<c>ProtocolManager.PushDisplayAmountAsync</c>；消费方：Socket 驱动。</remarks>
    public const string DisplayAmountPrefix = "AMT=";

    /// <summary>打开钱箱的指令载荷。</summary>
    /// <remarks>生产方：<c>ProtocolManager.OpenCashBoxAsync</c>；消费方：Socket 驱动。</remarks>
    public const string OpenCashBox = "CASHBOX=OPEN";
}
```

### 4.3 为什么这不只是"抽个常量"那么简单

**① 它解决了"分层倒置"。**

如果 `"条码"` 这个键定义在 `SerialPortSimDriver` 里，那么 `ProtocolMessageBridge` 想用它，就得 `using` 那个驱动类——**上层被迫依赖下层的具体实现**。

放在协议中立的 `ProtocolKeys` 里，双方都只依赖"常量仓库"，谁也不用认识谁。

**② 注释里写了"生产方 / 消费方"。**

这是我觉得最值得学的一点：**每个常量都标注了谁生产、谁消费。**

为什么有用？因为将来要改这个常量时，你不只知道"有几处引用"，还知道"改动会影响哪条链路"。**好的注释不是解释代码在做什么，而是解释这段代码在全局里的位置。**

**③ 它把"运行时故障"变成了"编译期约束"。**

改常量名 → 所有引用处都编译不过 → 你被迫全部检查一遍。这就是从"靠人记得"变成"靠编译器保证"。

**这条经验可以推广到很多地方：凡是"两处必须一致"的东西，就该共享同一个定义。**

## 五、`CartLimits`：同一条规则只留一份

这个在上一篇第 12.3 节提过，这里补充"不这么做会怎样"。

### 5.1 规则本身很简单

> 不允许超卖时，某商品最多能加"库存"件；库存为 0 就不能加。允许超卖时，随便加。

### 5.2 但它被三处同时需要

| 使用方 | 需要它做什么 | 代码点 |
| --- | --- | --- |
| `CartService` | 把数量夹到上限（真正执行约束） | `Services/CartService.cs:36`、`:52-58` |
| `CashierViewModel` | 零库存时**提前拦截**，给用户一个明确提示 | `ViewModels/CashierViewModel.cs:239` |
| `CartItem` | 告诉界面"+"按钮该不该灰 | `Models/CartItem.cs:63` |

### 5.3 三个使用方的"动机"其实不一样

这个是关键点，我一开始没意识到：

- `CartService` 要的是"**执行**"（这才是真正的约束），它**不负责提示**；
- `CashierViewModel` 要的是"**提示**"，所以要提前判断（注释里写了"服务内部的拒绝是静默的"）；
- `CartItem` 要的是"**界面状态**"，所以要一个能绑定到按钮的 `bool`。

**三个不同的动机，指向同一条规则。** 如果各自实现一遍：

- 服务里写 `Math.Min(qty, product.Stock)`；
- ViewModel 里写 `if (product.Stock <= 0)`；
- `CartItem` 里写 `Quantity >= Product.Stock`；

看起来"都能跑"，但**在"允许超卖"这个开关上就会打架**：服务不限量了，`CartItem` 还在用 `Stock` 判上限，界面就会显示"已达上限"、按钮灰掉——而服务其实还能加。

**这正是"界面说不行、底层说可以"这类 bug 的典型成因。**

### 5.4 收敛后的样子

```csharp
// CommunityToolkitDemo/Services/CartLimits.cs
public static class CartLimits
{
    /// <summary>允许超库存销售时不再限制数量。</summary>
    public const int Unlimited = int.MaxValue;

    public static int MaxQuantityFor(Product product, bool allowOversell)
        => allowOversell ? Unlimited : Math.Max(product.Stock, 0);

    public static bool CanAdd(Product product, bool allowOversell)
        => MaxQuantityFor(product, allowOversell) > 0;
}
```

还有一个细节：`CartItem` 里存的是 `MaxQuantity`（服务**写进去**的上限），而不是自己去算。所以界面的上限永远等于服务实际用的上限——**同源，而不是同规则算两遍。**

**"单一事实来源"（Single Source of Truth）这个词听着像架构大词，落到代码里就是这么一个小类。**

## 六、`CheckoutCoordinator`：把设备编排从 ViewModel 里请出去

### 6.1 原来的样子

结算成功之后要干三件事：打印小票、现金时开钱箱、订单上报云端。

**这三件事最初全都写在收银台 ViewModel 的 `CheckoutAsync` 里：**

```csharp
// 伪代码：改造前的样子
private async Task CheckoutAsync()
{
    var order = _orders.Checkout(...);

    // 打印
    var printed = await _protocols.PrintReceiptAsync(order);
    // 开钱箱
    bool opened = false;
    if (IsCashPayment) opened = await _protocols.OpenCashBoxAsync();
    // 上报
    var uploaded = await _protocols.PublishOrderAsync(order);

    _dialogs.ShowInfo($"打印：{printed}，钱箱：{opened}，上报：{uploaded}");
}
```

问题在哪？**`CashierViewModel` 这个类开始同时承担两种职责**：界面状态（购物车、金额、按钮）和设备编排（哪台设备先做、失败了怎么描述）。

结果是：这个类越写越长，而且**设备逻辑没法脱离 UI 单独测试**。

### 6.2 抽出来之后

```csharp
// CommunityToolkitDemo/Services/CheckoutCoordinator.cs:12-53
/// <summary>
/// 结算外设编排：把"打印小票 / 开钱箱 / 云端上报"这段设备协调逻辑
/// 从收银台 ViewModel 中独立出来。
///
/// 为什么单独抽出来？
/// 这段逻辑只关心"设备之间如何配合"，不关心"界面如何显示"。留在 ViewModel 里会让
/// 收银台类同时承担界面状态与设备编排两种职责，也无法脱离 UI 单独验证。
/// 抽出后 ViewModel 只负责发起调用与展示结果，设备失败语义集中在
/// <see cref="BuildDeviceNote"/> 一处描述。
/// </summary>
public sealed class CheckoutCoordinator
{
    private readonly IProtocolManager _protocols;

    public CheckoutCoordinator(IProtocolManager protocols)
    {
        _protocols = protocols;
    }

    /// <summary>
    /// 结算后并行执行三个互不依赖的设备动作。
    /// </summary>
    /// <remarks>
    /// 三件事分属不同设备、彼此无依赖，因此并行下发以缩短结算等待时间；
    /// 单个设备未连接时其对应方法返回 false（由协议管理器保证不抛异常），
    /// 因此这里不需要额外的 try/catch，失败会体现为结果里的 false。
    /// </remarks>
    public async Task<OrderFollowUpResult> CompleteAsync(Order order, bool openCashBox)
    {
        var printTask = _protocols.PrintReceiptAsync(order);
        var cashBoxTask = openCashBox ? _protocols.OpenCashBoxAsync() : Task.FromResult(false);
        var uploadTask = _protocols.PublishOrderAsync(order);

        // 用 WhenAll 的返回值取值，而不是各任务上再读 .Result：
        // 后者容易被误读为"同步阻塞"（sync-over-async）而引发无谓的改造。
        var results = await Task.WhenAll(printTask, cashBoxTask, uploadTask);

        return new OrderFollowUpResult(results[0], results[1], results[2]);
    }
    // ...
}
```

### 6.3 这里有两个非常高价值的点

**① 三个设备动作是并行下发的。**

```csharp
var printTask = _protocols.PrintReceiptAsync(order);
var cashBoxTask = openCashBox ? _protocols.OpenCashBoxAsync() : Task.FromResult(false);
var uploadTask = _protocols.PublishOrderAsync(order);

var results = await Task.WhenAll(printTask, cashBoxTask, uploadTask);
```

**因为是"三个互不依赖的设备动作"，所以可以同时发出去。**

假设每个耗时 100ms：

- 串行：`await` 打印 → `await` 开钱箱 → `await` 上报 = **300ms**；
- 并行：三个 `Task` 一起发，`await Task.WhenAll` = **约 100ms**。

**收银台上每一毫秒都是顾客的排队时间**，所以这个优化很实在。

**注意 `Task.WhenAll` 用的时候是怎么取值的**——注释里专门说了"用 WhenAll 的返回值取值，而不是各任务上再读 `.Result`"。因为 `xxxTask.Result` 是**同步阻塞**的读法（哪怕任务已经完成，也容易被误读），而 `WhenAll` 返回的数组本身就是结果。

**② 设备没连接不抛异常，而是返回 `false`。**

```csharp
/// 单个设备未连接时其对应方法返回 false（由协议管理器保证不抛异常），
/// 因此这里不需要额外的 try/catch，失败会体现为结果里的 false。
```

这是一个**非常有品味的接口设计**：

- 方案 A（不好）：设备没连上就抛异常 → 调用方要到处 `try/catch`，而且"没连上"和"打印失败"混在一起；
- 方案 B（项目采用）：**把"设备不可用"定义成一种正常返回值**。

于是 `CheckoutCoordinator` 里一个 `try/catch` 都不用写，调用方拿到的是一个明确的结果对象：

```csharp
/// <summary>结算后外设联动结果（打印小票 / 开钱箱 / 云端上报）。</summary>
public readonly record struct OrderFollowUpResult(bool Printed, bool CashBoxOpened, bool Uploaded);
```

**用 `readonly record struct` 而不是 `class`**：它只是个"三个 `bool` 的袋子"，用完就扔，放栈上更省。

最后，把这些 `bool` 变成给人看的话，也集中在一个方法里：

```csharp
// CommunityToolkitDemo/Services/CheckoutCoordinator.cs:55-67
/// <summary>把外设联动结果整理成结算对话框中的设备说明文字。</summary>
public static string BuildDeviceNote(bool displayPushed, OrderFollowUpResult result)
{
    var lines = new List<string>
    {
        displayPushed ? "客显屏 ✓ 已显示应收金额" : "客显屏 ✗ 未连接，已跳过",
        result.Printed ? "小票打印机 ✓ 已打印" : "小票打印机 ✗ 未连接，已跳过",
        result.CashBoxOpened ? "钱箱 ✓ 已弹开" : "钱箱 — 未触发",
        result.Uploaded ? "云端 MQTT ✓ 订单已上报" : "云端 MQTT ✗ 未连接，已跳过"
    };

    return string.Join("\n", lines);
}
```

**注释里那句"设备失败语义集中在 `BuildDeviceNote` 一处描述"**，意思是：将来要改文案、要加一种设备，只改这一个方法。**而不是在 ViewModel 里拼字符串。**
