这一篇是我在项目里踩坑最多、也最有收获的部分。

先给你一个心理准备：**WPF 的性能问题，90% 不出在"WPF 本身慢"，而出在"你把不该做的事放到了 UI 线程上、或者做了太多遍"。**

这一篇我会先讲"怎么判断慢"，再一条一条讲项目里做的六件事，最后附上实测数字。

## 一、先学会一件事：什么叫"慢"

在优化之前，得先有个尺子。对 UI 来说，最实用的尺子是**帧预算**：

| 目标帧率 | 单帧预算 | 含义 |
| --- | --- | --- |
| 30 fps | 33.3 ms | 勉强算流畅 |
| **60 fps** | **16.7 ms** | 流畅的标准线 |
| 120 fps | 8.3 ms | 高刷屏的追求 |

**也就是说：UI 线程上任何一次同步操作，只要超过 16.7 毫秒，就会掉帧。**

这个数字请记住，后面所有数据都要拿它对照。

而这个项目里实测到的几个"未优化版本"的数字是这样的（10 万条商品，Debug 构建）：

| 场景 | 实测耗时 | 相当于 |
| --- | --- | --- |
| 解析 + 映射商品数据 | **943 ms** | 界面冻结约 1 秒 |
| 关键字搜索（全量过滤） | **34.8 ms** | 超过 2 帧预算 |
| 扫码查找（线性扫描最坏） | **5.73 ms** | 接近 1/3 帧 |

数据来源是项目里那份《性能与内存专项分析报告》，全部是可复现实测。

**这三个数字，正好对应三种典型的性能问题：**

1. **943 ms** = "在 UI 线程干了太久的大活" → 解法：移到后台线程（第 05 篇讲）；
2. **34.8 ms** = "每次都从头全量算" → 解法：索引 + 结果上限；
3. **5.73 ms** = "用错的数据结构" → 解法：`List` 换 `Dictionary`。

## 二、手法一：虚拟化——只渲染看得见的部分

### 2.1 问题的本质

商品卡片墙要显示可能上千个商品。**如果每个商品都生成一个真实控件，会怎样？**

- 1000 个商品 ≈ 1000 个 `Button`，每个 `Button` 的模板里还有 `Border + Grid + TextBlock×4` 等视觉元素；
- **合计一万多个视觉元素**；
- 每次布局，WPF 都要测量它们、排列它们、合成到渲染树里。

**屏幕只有那么大，你根本看不见 990 个。** 所以这些工作全是白干的。

### 2.2 虚拟化的做法

> **只实例化"当前视口覆盖的那几行"，滚出去的回收掉。**

1000 个商品，屏幕只能看到约 15 个，那就只生成约 15 个控件。**从 O(全部) 降到 O(可视区)。**

这个实现在 `Common/Controls/VirtualizingWrapPanel.cs`（第 03 篇第 1 节详细讲过实现），核心就两个方法：

```csharp
// CommunityToolkitDemo/Common/Controls/VirtualizingWrapPanel.cs:104-105
RealizeItems(firstIndex, lastIndex, itemWidth, itemHeight);
CleanUpItems(firstIndex, lastIndex);
```

### 2.3 一个容易被忽略的前提：固定尺寸

注释里专门强调了：

```csharp
// CommunityToolkitDemo/Common/Controls/VirtualizingWrapPanel.cs:18
/// - 固定项尺寸（<see cref="ItemWidth"/>/<see cref="ItemHeight"/>）是虚拟化能精确定位的前提。
```

**为什么？** 因为虚拟化要回答两个问题：

1. **第 500 项应该出现在哪个坐标？** → 需要"每项多宽多高"，才能算 `row = index / itemsPerRow`；
2. **滚动条该多长？** → 需要"总高度 = 行数 × 行高"。

如果每项高度都不一样（比如内容不定长），就必须**先把前面所有项都测量一遍**才能知道第 500 项在哪——虚拟化就失去了意义。

所以项目在 `CashierView.xaml` 里给卡片定了固定尺寸，并在 `ItemsPanel` 上对齐：

```xml
<!-- 卡片样式：Width=162 / Height=128 + Margin=10；ItemsPanel：ItemWidth=172 / ItemHeight=138 -->
```

**这是一条很实用的经验：想虚拟化，先让项尺寸确定。**

（顺带说一句：报告里把"卡片尺寸两处硬编码"列为 P1 问题——162+10=172、128+10=138，两处必须同步改，是隐性耦合。改进方向是收敛成单一来源，或者干脆让面板自动测量首个子项——面板里已经写好了这个兜底逻辑，见 `ResolveItemSize`。）

### 2.4 虚拟化的收益边界

必须说清楚一个事实：**虚拟化不是万能的。**

- ✅ 它解决的是"**渲染**贵"（视觉元素太多）；
- ❌ 它不解决"**数据准备**贵"（过滤、排序、查询）。

**所以如果搜索本身要 34.8 ms，虚拟化一点忙都帮不上。** 这也是为什么后面还要做"结果上限"和"后台过滤"。

## 三、手法二：批量通知——别让集合喊 200 次

### 3.1 问题的本质

`ObservableCollection<T>` 有个很多人不知道的特性：**它没有 `AddRange`。**

所以你想一次添加 200 条数据，只能：

```csharp
foreach (var item in list)
{
    collection.Add(item);   // 每加一条，发一次 CollectionChanged
}
```

**结果是：200 次 `CollectionChanged` 通知。**

如果这个集合绑定着一个列表控件（尤其是虚拟化面板），每一次通知都可能触发一次"重新计算索引 + 重新布局"。

**而且是滚动式的重复劳动**：第一条加完布局一次，第二条加完再布局一次……总共做了 200 次，其中 199 次都是白费。

### 3.2 项目的解法

```csharp
// CommunityToolkitDemo/Common/Collection/RangeObservableCollection.cs:7-45
/// <summary>
/// 支持批量替换的 <see cref="ObservableCollection{T}"/>。
/// </summary>
/// <remarks>
/// <see cref="ObservableCollection{T}"/> 本身没有 AddRange：逐条 Add 会为每个元素各发一次
/// <c>CollectionChanged</c>。当集合已绑定到列表控件时，这会表现为"逐条插入 + 逐条重排"，
/// 元素越多累计代价越高；本类型把"清空 + 批量填充"合并成一次
/// <see cref="NotifyCollectionChangedAction.Reset"/>，绑定方只重建一次视图。
/// </remarks>
public sealed class RangeObservableCollection<T> : ObservableCollection<T>
{
    /// <summary>用给定元素整体替换当前内容，只发出一次集合变更通知。</summary>
    /// <remarks>
    /// 若给定元素与当前内容逐一相等（按 <see cref="EqualityComparer{T}.Default"/>），则直接返回、
    /// 不发出任何通知。搜索与切换分类可能在结果未变时重复触发（重复按键、点选同一分类），
    /// 无谓的 Reset 会让虚拟化面板把可视区内的容器全部重建一遍。
    /// </remarks>
    public void ReplaceAll(IEnumerable<T> items)
    {
        ArgumentNullException.ThrowIfNull(items);

        // 先物化再改动集合：避免清空之后才去枚举惰性序列，出现"边清边取"的意外
        var incoming = items as IList<T> ?? items.ToList();

        if (HasSameContent(incoming))
        {
            return;
        }

        CheckReentrancy();

        Items.Clear();
        foreach (var item in incoming)
        {
            Items.Add(item);
        }

        RaiseReset();
    }
```

### 3.3 三个非常有价值的细节

**① 直接操作 `Items`，而不是 `Clear()` + `Add()`。**

```csharp
Items.Clear();
foreach (var item in incoming)
{
    Items.Add(item);
}

RaiseReset();
```

`Items` 是 `Collection<T>` 的**底层列表**，操作它**不会触发任何通知**。等数据全部填完，最后手动发**一次** `Reset`。

**200 次通知 → 1 次通知。**

**② 通知要发全。**

```csharp
// CommunityToolkitDemo/Common/Collection/RangeObservableCollection.cs:88-94
/// <summary>发出 Reset 通知，并补齐绑定方依赖的 Count / Item[] 属性变更。</summary>
private void RaiseReset()
{
    OnPropertyChanged(new PropertyChangedEventArgs(nameof(Count)));
    OnPropertyChanged(new PropertyChangedEventArgs("Item[]"));
    OnCollectionChanged(new NotifyCollectionChangedEventArgs(NotifyCollectionChangedAction.Reset));
}
```

**为什么连 `Count` 和 `Item[]` 也要通知？**

因为 WPF 里绑定的**不只是集合内容**。比如界面上可能绑了：

- `Text="{Binding Products.Count}"` → 显示商品数量；
- `ItemsControl` 内部的索引器绑定 → 用到 `Item[]`。

**如果你只发了 `CollectionChanged`，`Count` 的绑定不会更新**——现象是"列表刷新了，但"共 200 件"这个数字没变"。这个 bug 特别隐蔽，因为它只在特定绑定方式下才出现。

**③ 内容没变就不发通知。**

```csharp
if (HasSameContent(incoming))
{
    return;
}
```

**这是我从报告里学到的最"反直觉"的一点。** 报告里写着：

> 搜索与切换分类可能在结果未变时重复触发（重复按键、点选同一分类），无谓的 Reset 会让虚拟化面板把可视区内的容器全部重建一遍。

**想想这个场景**：用户连按两下同一个字母，或者点了两次同一个分类。数据完全没变，但如果照样发 `Reset`，虚拟化面板就会**把可视区的容器全部丢弃重建一遍**——用户看到的是画面闪一下。

所以这里做了一次逐项比较（`HasSameContent`）。**代价是 O(N) 的比较，收益是避免一次 O(可视区容器数) 的重建。**

**这个取舍非常有品味**：比较 200 个引用是纳秒级的，重建 15 个控件模板是毫秒级的。

### 3.4 顺带说：为什么要用 `Reset` 而不是 `Add` 通知

`NotifyCollectionChangedAction` 有好几种：`Add`、`Remove`、`Replace`、`Move`、`Reset`。

`Reset` 的语义是"**我全变了，你别猜了，重建吧**"。听起来最"暴力"，但在"批量替换"这个场景下**它才是最省的**——因为你不需要框架去解析"哪几条新增、插在第几位"。对虚拟化面板来说，`Reset` 就是"重新取一遍可见数据"，一次搞定。

## 四、手法三：视图缓存——页面切换不重建

这一块第 03 篇详细讲过 `CachedContentControl`，这里只补"为什么要从性能角度看它"。

**原生 `ContentControl` 的默认行为**：内容一变，旧视觉树整个丢掉，重新 `LoadContent`。

对一个页面来说，这个代价包括：

- 重新解析 XAML（虽然模板会缓存，但实例化不会）；
- 重新构造所有控件对象；
- 重新测量、排列整棵树；
- 如果有图片/图形，还要重新生成渲染资源。

**用户的主观感受**：切页面时"顿一下"，或者闪一下。

`CachedContentControl` 把这个成本降到几乎为零：**视图实例存字典，切换只改 `DataContext`。**

有个很妙的连锁收益：**视图缓存 + 页面 ViewModel 单例 = 页面状态完整保留。** 你从收银台切到设备监控再切回来，购物车、滚动位置、搜索框内容全都在。

## 五、手法四：用对数据结构——扫码从 5.73 ms 到 0.0003 ms

### 5.1 原来的写法

```csharp
// 改造前（报告中的基线 E/F）
public Product? FindByBarcode(string barcode)
    => Products.FirstOrDefault(p =>
        !string.IsNullOrWhiteSpace(p.Barcode) &&
        string.Equals(p.Barcode, barcode.Trim(), StringComparison.Ordinal));
```

这是**线性扫描**：从头一个个比。10 万条商品，最坏情况（命中的在最后）要比较 10 万次，每次还带一次 `IsNullOrWhiteSpace`。

**测出来 5.73 ms。**

**5.73 毫秒听起来不多吧？** 但想想场景：收银员在忙的时候，一秒可能扫三四件商品。每次 5.73 ms，还要叠加后续的加购、刷新、金额重算……

而且这是 **10 万条**下的数字。如果将来 50 万条呢？**线性增长**——这是最糟糕的复杂度特征。

### 5.2 改造后：字典索引

```csharp
// CommunityToolkitDemo/Services/PosRepository.cs:20-33（注释节选）
/// <summary>条码索引。与旧线性扫描的匹配规则一致：只收录非空白条码。</summary>
private Dictionary<string, Product>? _productsByBarcode;

/// <summary>编码索引。</summary>
private Dictionary<string, Product>? _productsByCode;

/// <summary>
/// 分类索引：CategoryId → 该分类下的商品（保持 Products 中的原始顺序）。
/// </summary>
private Dictionary<string, List<Product>>? _productsByCategory;
```

**实测结果对比（同一个进程内先测线性扫描、再测索引，消除机器负载干扰）：**

| 指标 | 线性扫描 | 索引查找 | 加速 |
| --- | --- | --- | --- |
| `FindByBarcode`（最坏） | 5.7970 ms | **0.0003 ms** | ≈ 2.2 万倍 |
| `FindByCode`（最坏） | 4.1717 ms | **0.0001 ms** | ≈ 3.4 万倍 |
| 分类切片（10 万中取 14,286 条） | 5.4967 ms | **0.0002 ms** | ≈ 2.7 万倍 |

报告里对数字有很诚实的注解：

> 索引侧单次耗时为 0.0001 ~ 0.0003 ms（100 次平均），已接近 `Stopwatch` 分辨率下限，因此跨多次运行的加速比在 2.2 万 ~ 3.8 万倍之间波动，**应读作"亚微秒级"而非精确倍数**。

**这句话本身就是一种专业素养**：不要拿测量工具的精度极限去吹牛。**"从毫秒级变成亚微秒级"** 就是准确的结论。

### 5.3 索引的代价：6.7 MB

天下没有免费的午餐。报告里也老老实实算了成本：

| 项 | 实测 | 说明 |
| --- | --- | --- |
| 首次构建（条码+编码+分类） | 48.2 ms | 一次性成本，发生在首次扫码/查询时 |
| 索引稳态保留内存 | 6.7 MB | 10 万商品；相对稳态约 +21% |

**"用 6.7 MB 内存换三条高频路径的数量级收益"**——这笔账很划算。

### 5.4 一个非常讲究的工程细节：索引怎么"失效"

`Products` 是个公开可变的 `List<T>`，**调用方可以直接 `Add` 一条商品**。这时候索引怎么知道要重建？

项目用的是"懒构建 + 条数比对"：

```csharp
// CommunityToolkitDemo/Services/PosRepository.cs:195-203
/// <summary>按当前 <see cref="Products"/> 内容（必要时）重建条码/编码索引。</summary>
private void EnsureProductIndexes()
{
    if (_productsByBarcode is not null
        && _productsByCode is not null
        && _indexedProductCount == Products.Count)
    {
        return;
    }
    // ...重建
}
```

**为什么要"条数比对"而不是"写入时主动失效"？**

报告里解释得很清楚：

> 索引因此不依赖"写入方主动通知"，而是在查询时比较 `Products.Count` 与建索引时的条数，不一致即重建；`ReplaceAll` 则显式失效，兜底"条数相同、内容不同"的重载场景。

**翻译成人话**：

- 因为集合是公开可变的，**你无法保证所有人都通知你**（可能有人直接 `Add`）；
- 所以不指望"别人告诉我"，而是"**自己每次用的时候检查一下有没有变**"；
- `ReplaceAll`（数据重载）这种"条数可能一样但内容全换"的场景，就**显式失效**，双保险。

**这是一个很值得抄的模式："懒校验 + 显式失效"双保险。** 单靠任何一个都会有漏洞。

## 六、手法五：把查询移出 UI 线程 + 结果上限

### 6.1 问题的本质

`34.8 ms` 的全量过滤是怎么来的？

- 10 万条商品 × 3 个字段（名称、编码、条码）；
- 每次比较用 `Contains(..., StringComparison.OrdinalIgnoreCase)`；
- **30 万次逐字符比较**。

报告里一针见血地指出：

> `Contains(string, StringComparison)` 不做向量化（不同于 `IndexOf(string, StringComparison)` 的部分路径）；10w × 3 字段 = 30 万次逐字符比较。

还有一条更重要的推论：

> 基线 I（34.8 ms，`ListCollectionView.Refresh`）与基线 H（33.5 ms，纯遍历）几乎一致 → `ListCollectionView` 自身的调度开销很小，**成本几乎全部来自过滤算法本身**。

**所以别再怪集合视图了，问题在你的过滤算法。**

### 6.2 项目的三层解法

**第一层：分类走索引，不全量扫。**

```csharp
// CommunityToolkitDemo/Services/ProductQueryService.cs:5-12
/// <summary>
/// 基于商品目录索引的查询实现（<see cref="IProductQuery"/>）。
///
/// 关键点：
/// - **分类切片**直接命中 <see cref="IProductCatalog.GetProductsInCategory"/> 的索引，不再全量扫描；
/// - **关键字过滤**在数据量大时移到线程池，避免在 UI 线程同步吃掉多帧预算；
/// - 结果始终受上限约束（<see cref="MaxResultLimit"/>），避免 10w 项涌入可观察集合。
/// </summary>
```

**第二层：大数据的过滤丢到线程池。**

```csharp
// CommunityToolkitDemo/Services/ProductQueryService.cs:25-68
/// <summary>源规模超过该值时，关键字过滤移到线程池执行。</summary>
/// <remarks>
/// 阈值取 2000：低于它时单次过滤在亚毫秒级完成，线程切换（含上下文捕获）反而不划算。
/// </remarks>
private const int BackgroundThreshold = 2000;

// ...

if (source.Count <= BackgroundThreshold)
{
    return Task.FromResult(Filter(source, keyword, offset, limit, cancellationToken));
}

// 关键字过滤是"3 字段 × 忽略大小写"的 CPU 密集比较，10w 规模下远超单帧预算。
// 放到线程池：调用方 await 返回的 Task，续体在其原始上下文（UI 线程）中执行。
return Task.Run(
    () => Filter(source, keyword, offset, limit, cancellationToken),
    cancellationToken);
```

**注意那个 `BackgroundThreshold = 2000` 的取舍，注释写得太好了：**

> 阈值取 2000：低于它时单次过滤在亚毫秒级完成，**线程切换（含上下文捕获）反而不划算**。

这解释了"为什么不是无脑丢线程池"——**线程切换本身也有成本**（大约几十微秒到几百微秒）。数据量小的时候，切线程比干活还贵。

**第三层：结果设上限。**

```csharp
// CommunityToolkitDemo/Services/ProductQueryService.cs:15-23
/// <summary>"全部"分类且无关键字时的默认结果上限。</summary>
/// <remarks>
/// POS 场景以扫码 + 搜索为主，把 10w 条全部塞进可视列表滚动意义有限。
/// 超出上限时界面会提示"请输入关键字缩小范围"（产品取舍见分析报告第 7 章）。
/// </remarks>
public const int AllCategoryDefaultLimit = 200;

/// <summary>任何查询的单次结果硬上限，防止超大分类整体进入可观察集合。</summary>
public const int MaxResultLimit = 2000;
```

**这第三层是"产品思维"，不是纯技术。**

从技术上说，你当然可以"把 10 万条都渲染出来"（有虚拟化撑着，也不至于崩）。但产品上没意义：**收银员不可能靠滚动 10 万条找到商品**——他是扫码或者搜关键字的。

所以项目做了一个明确的产品取舍：**"全部"分类默认只渲染前 200 条，超出提示"请输入关键字缩小范围"。**

**敢于做这种取舍，是"能交付的产品"和"技术演示"的分界线。**

### 6.3 一个"提前退出"的小优化

```csharp
// CommunityToolkitDemo/Services/ProductQueryService.cs:96-137
/// <summary>关键字过滤：收集到本页上限即提前退出，不再扫描剩余数据。</summary>
private static ProductQueryResult Filter(
    IReadOnlyList<Product> source,
    string keyword,
    int offset,
    int limit,
    CancellationToken cancellationToken)
{
    var items = new List<Product>(Math.Min(limit, 256));
    var skipped = 0;

    for (var i = 0; i < source.Count; i++)
    {
        // 每 1024 项检查一次取消：对 10w 规模足够灵敏，检查本身也不构成开销
        if ((i & 0x3FF) == 0)
        {
            cancellationToken.ThrowIfCancellationRequested();
        }

        var product = source[i];
        if (!Matches(product, keyword))
        {
            continue;
        }

        if (skipped < offset)
        {
            skipped++;
            continue;
        }

        if (items.Count >= limit)
        {
            // 本页已收满：存在未返回的命中，直接退出
            return new ProductQueryResult(items, HasMore: true);
        }

        items.Add(product);
    }

    return new ProductQueryResult(items, HasMore: false);
}
```

两个细节：

**① 收满就退出。**

不缺 `break`、不走完整个循环——**只需要一页 200 条，找到了就撤**。

**② `(i & 0x3FF) == 0` 是"每 1024 次检查一次取消"。**

**为什么不是每次都检查？**

`ThrowIfCancellationRequested()` 要读一个 `volatile` 字段并做判断。虽然很便宜，但在 10 万次循环里做 10 万次，也是白费。

**`i & 0x3FF` 是一种位运算技巧**：`0x3FF = 1023`，`i & 1023 == 0` 等价于 `i % 1024 == 0`，但**位运算比取模快**（现代编译器基本能优化取模，但写位运算更明确表达意图）。

**"每 N 次检查一次"是取消检查的标准做法**：既保证足够灵敏（1024 次循环也就几十微秒），又不构成额外开销。

## 七、手法六：防抖——把 5 次查询变成 1 次

```csharp
// CommunityToolkitDemo/ViewModels/CashierViewModel.cs:106-113
// 搜索输入防抖：停止输入 250ms 后才真正查询
_searchDebounceTimer = new DispatcherTimer { Interval = TimeSpan.FromMilliseconds(250) };
_searchDebounceTimer.Tick += (_, _) =>
{
    _searchDebounceTimer.Stop();
    _appliedKeyword = SearchText.Trim();
    _ = RefreshProductsAsync();
};
```

**防抖（Debounce）的逻辑**：每次输入都重置计时器，只有"停手 250 毫秒"之后才真正执行。

| 用户输入 | 不防抖的查询次数 | 防抖后的查询次数 |
| --- | --- | --- |
| "农夫山泉"（5 个字符） | 5 | 1 |
| 快速输入 10 个字符 | 10 | 1 |

**注意一个重要的认知**：报告里说了一句很清醒的话——

> 搜索防抖（250 ms）只能降低触发频率，**无法降低单次成本**。

**所以防抖不是性能优化的"解药"，它只是"减次数"。** 单次 34.8 ms 的问题，还是要靠"索引 + 后台线程 + 结果上限"来解决。

**这两者要一起用**：防抖减少触发次数，算法优化降低单次成本。

## 八、手法七：转换器里别 new 对象

```csharp
// CommunityToolkitDemo/Common/Converters/Converters.cs:10-31
/// <summary>
/// 画刷缓存：转换器里千万不要每次 Convert 都 new 一个画刷。
/// 未冻结的 Freezable 会被 WPF 属性系统登记变更通知，既增加 GC 压力又带来额外订阅开销；
/// 报文日志这类"每来一帧就新建一行"的场景会持续放大这个问题。
/// 统一使用静态只读 + Freeze 的画刷。
/// </summary>
internal static class BrushCache
{
    public static SolidColorBrush Frozen(byte r, byte g, byte b)
    {
        var brush = new SolidColorBrush(Color.FromRgb(r, g, b));
        brush.Freeze();
        return brush;
    }
    // ...
}
```

**正确的用法：**

```csharp
// CommunityToolkitDemo/Common/Converters/Converters.cs:108-113
private static readonly SolidColorBrush Disconnected = BrushCache.Frozen(0x94, 0xA3, 0xB8);
private static readonly SolidColorBrush Connecting = BrushCache.Frozen(0xF5, 0x9E, 0x0B);
private static readonly SolidColorBrush Connected = BrushCache.Frozen(0x16, 0xA3, 0x4A);
private static readonly SolidColorBrush Faulted = BrushCache.Frozen(0xDC, 0x26, 0x26);
```

**为什么 `Freeze()` 这么关键？**

`SolidColorBrush` 是 `Freezable` 的子类。**一个"未冻结"的 `Freezable` 是可变的，WPF 的属性系统必须盯着它**——给它登记变更通知、在变更时重新渲染。

而当它**冻结**之后：

- 变成只读；
- WPF 知道它永远不会变，于是**跳过所有变更跟踪**；
- 而且**可以跨线程共享、可以安全地多处引用**。

在高频场景（报文日志每 150 毫秒来一批，每行都要根据状态上色）里，这个差别非常明显：**每次 `Convert` 都 new 一个画刷 = 每秒几百个新对象 + 几百次订阅登记。**

**一句话记住：转换器返回值里出现画刷/画笔/几何图形，一律 `static readonly` + `Freeze()`。**

## 十、还没解决 / 需要注意的地方

一篇诚实的性能文章，必须列出"还没做"的部分。

### 10.1 `Reset` 时容器不回收（已明确接受）

集合整体替换（`Reset`）时，虚拟化面板的可视容器会被丢弃。项目在代码里明确写了这个决定：

```csharp
// CommunityToolkitDemo/Common/Controls/VirtualizingWrapPanel.cs:243-253
case NotifyCollectionChangedAction.Reset:
    // Reset（整体替换）时框架的 OnItemsChangedInternal → ResetChildren → ClearChildren
    // 已经调用过 generator.RemoveAll() 并清空了 InternalChildren，生成器的位置映射随之失效。
    // 此刻再把容器交回回收池已不可能（Remove/Recycle 的坐标不再有效），
    // 内置的 VirtualizingStackPanel 行为完全一致（见 Reset_DropsContainersLikeBuiltIn 对照测试）。
    // 因此这里只做兜底清理，保证不残留内部子元素；回收复用只在明确受支持的滚动/增量变更路径生效。
    if (InternalChildren.Count > 0)
    {
        RemoveInternalChildRange(0, InternalChildren.Count);
    }
    break;
```

**这里的取舍是**：不硬做"看似更优但实际无效"的回收（因为生成器的位置映射已经失效了），而是**对齐官方 `VirtualizingStackPanel` 的行为**，并为这个行为写了一个对照测试。

**缓解手段**：因为结果有上限（200/2000），即使 `Reset` 重建，重建的量也是有界的——**200 个卡片，不会变成 10 万个**。

### 10.2 卡片尺寸两处硬编码（P1）

`CashierView.xaml` 里卡片是 `Width=162 / Height=128 + Margin=10`，`ItemsPanel` 上写的是 `ItemWidth=172 / ItemHeight=138`。

**你算一下：162+10=172，128+10=138。** 两处必须同步修改，改一处忘另一处，布局就歪了。

改进方向：收敛成单一来源（比如用 `DynamicResource` / 共享常量），或者让面板自动测量（面板里已有 `MeasureFirstChild` 兜底）。

### 10.3 监控页的两个内存隐患（P1）

| 问题 | 位置 | 后果 |
| --- | --- | --- |
| 待处理报文队列无上限 | `DeviceMonitorViewModel.cs:36` 的 `_pendingFrames` | 产帧速率持续高于刷新节奏时队列无界增长 |
| 指标 key 逐帧拼接字符串 | `DeviceMonitorViewModel.cs:280` 的 `$"{frame.Type}.{name}"` | 高频报文下产生大量短命字符串，增加 GC 压力 |

这两个第 05 篇会展开讲。

### 10.4 `Products` 暴露可变 `List<T>`（架构级）

报告里把它列为架构问题，因为它形成了一条**从存储层直通 WPF 集合类型**的耦合链：

```
PosRepository → IProductCatalog.Products → CashierViewModel → ListCollectionView
```

后果是"表现层被迫持有全量商品，无法演进为分页/服务端查询"。项目已经在批次 3 里改掉了 `ListCollectionView` 那条路径（改用 `IProductQuery`），但**这仍然是一个需要持续警惕的架构约束。**

## 本篇小结

**UI 性能优化，我总结成四句话：**

1. **先量化再优化**——记住 16.7 ms 这个数，它是"流畅"的及格线；
2. **能不算就不算**——虚拟化（不渲染看不见的）、结果上限（不查用不到的）、防抖（不重复触发）；
3. **能一次算完就别算两次**——批量通知、`Freeze` 画刷、字典索引；
4. **算得久就搬走**——移到后台线程（下一篇的主角）。
