
那时候我盯着这句话看了很久，不知道"调度程序线程"是哪个，也不知道我明明"只是加了一条数据"。

## 一、先立一条铁律

WPF 里所有"有线程亲和性（Thread Affinity）"的对象——包括 `Window`、`Control`、`DependencyObject`、以及**绑定在界面上的 `ObservableCollection`**——都有一个"主人线程"，那就是创建它们的 UI 线程。

**只有主人线程能碰它们。其它任何线程碰一下，就是上面那个异常。**

所以整个项目的线程设计，其实一直在回答两个问题：

1. **这个动作会不会碰到 UI 对象？**（会 → 必须回 UI 线程）
2. **这个动作会不会超过 16.7 毫秒？**（会 → 必须搬离 UI 线程）

> 生活化类比：UI 线程就像**店里唯一那台收银机**。谁都能算账，但**只有这台机器能打印小票**。后台员工算好账（耗时计算），还是要排队回到这台机器上打小票（更新界面）。

## 二、先看这个项目的"线程地图"

在讲具体代码之前，先把全局摆出来。这个项目里一共只有两类线程在工作：

| 谁 | 在哪个线程 | 干什么 | 项目位置 |
| --- | --- | --- | --- |
| ViewModel / 绑定属性 | **UI 线程** | 改 `ObservableCollection`、改 `[ObservableProperty]` | `ViewModels/*` |
| 标记表闪烁/批量刷新计时器 | **UI 线程** | `DispatcherTimer` 的 `Tick` 天然在 UI 线程 | `DeviceMonitorViewModel._flashTimer` / `_flushTimer` |
| Markdown 数据解析 | **线程池** | `Task.Run` 里流式解析 10 万行 | `Services/MarkdownDataService.cs:129` |
| 关键字过滤 | **线程池** | 数据量大时把过滤移出 UI 线程 | `Services/ProductQueryService.cs:66` |
| 协议仿真轮询 | **线程池** | `Task.Run` 起的循环，按 `IntervalMs` 造报文 | `Protocols/ProtocolDriverBase.cs:96` |

**关键观察：所有"后台线程"的产物，最终都必须经一个统一的门回到 UI 线程。** 这个门就是 `UiDispatcher`。

## 三、第一条链路：协议驱动的后台轮询循环

这个项目最"像真实硬件"的部分，是 5 个协议驱动。它们要在后台不停地模拟"设备在吐数据"。核心实现在基类里：

```68:75:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolDriverBase.cs
/// 子类扩展点
/// <summary>每次轮询产生一批仿真报文。</summary>
protected abstract Task<IReadOnlyList<ProtocolFrame>> ProduceAsync(CancellationToken cancellationToken);
```

而循环本体是这样的：

```194:219:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolDriverBase.cs
private async Task RunLoopAsync(CancellationToken token)
{
    try
    {
        while (!token.IsCancellationRequested)
        {
            await Task.Delay(Device.IntervalMs, token).ConfigureAwait(false);

            if (token.IsCancellationRequested)
            {
                break;
            }

            await TickAsync(token).ConfigureAwait(false);
        }
    }
    catch (OperationCanceledException)
    {
        // 正常停止
    }
    catch (Exception ex)
    {
        State = ConnectionState.Faulted;
        RaiseAlarm($"轮询异常：{ex.Message}");
    }
}
```

这一段里有三个我后来才体会到的点：

**1）用 `Task.Delay` 而不是 `Thread.Sleep`。**

`Thread.Sleep` 会**真的占住一个线程**，什么都不干也占着。`await Task.Delay(...)` 是把线程**还回去**，时间到了再唤醒。所以注释里写的是"空闲时零 CPU 占用"——5 个驱动同时挂着，CPU 也几乎不动。

**2）取消是靠 `CancellationToken`，不是靠一个 `bool` 标志位。**

`Task.Delay(interval, token)` 在等待期间就能被打断；如果写成 `Thread.Sleep(interval)`，取消要等这一觉睡完才生效——退出程序时会明显卡一下。

**3）`catch (OperationCanceledException)` 被当成"正常路径"。**

这是新手最容易写错的地方：取消不是错误，取消是**预期内的流程**。项目里反复出现这个模式：

```99:107:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolDriverBase.cs
catch (OperationCanceledException)
{
    State = ConnectionState.Disconnected;
}
catch (Exception ex)
{
    State = ConnectionState.Faulted;
    RaiseAlarm($"连接失败：{ex.Message}");
}
```

### 这里的"契约"

基类头部的注释把线程模型交代得很清楚：

```8:11:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolDriverBase.cs
/// 线程模型：
/// - 仿真循环跑在后台线程（<c>Task.Run</c> + <c>Task.Delay</c>），空闲时零 CPU 占用；
/// - 所有事件都在后台线程触发，订阅方（ViewModel）负责用 Dispatcher 切回 UI 线程；
/// - 断开时通过 CancellationToken 取消循环，避免资源泄漏。
```

**注意最后半句：订阅方负责切回 UI 线程。**

这是一个非常重要的设计决定。驱动层完全不知道 WPF 的存在（它的 `using` 里没有 `System.Windows`）。它只负责"我拿到数据了，喊一嗓子"，至于谁在听、听了要不要切线程，是上层的事。

好处是：驱动层可以脱离 WPF 单独测试；代价是：**每个订阅方都得记得切线程**。这个代价，靠"统一入口"来降低（见第六节）。

## 四、`CancellationToken`：不止是"能取消"

### 4.1 一处很隐蔽的竞态

先看连接时启动后台任务的写法：

```82:98:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolDriverBase.cs
try
{
    await OnConnectAsync(cancellationToken).ConfigureAwait(false);
    State = ConnectionState.Connected;

    // 先用局部变量持有本次的 CTS，再交给后台任务闭包捕获。
    // 若闭包直接读取 _loopCts 字段，在"连接后立刻断开"的竞态下，
    // DisconnectAsync 已把字段置为 null，而后台任务才刚启动，
    // 读取 _loopCts.Token 会抛 NullReferenceException。捕获局部变量可彻底避免。
    var loopCts = new CancellationTokenSource();
    lock (_sync)
    {
        _loopCts?.Dispose();
        _loopCts = loopCts;
        _loopTask = Task.Run(() => RunLoopAsync(loopCts.Token), CancellationToken.None);
    }
}
```

这里我踩的坑值得单独说：

我一开始写的是 `Task.Run(() => RunLoopAsync(_loopCts.Token))`。看起来没问题，但 `Task.Run` 里的 lambda 是**延迟执行**的——它可能在一小会儿之后才真的跑起来。如果这期间用户手快点了"断开"，`DisconnectAsync` 会把 `_loopCts` 置成 `null`，等那个后台 lambda 终于跑起来时，一读 `_loopCts.Token` 就 **NullReferenceException**。

修法就是项目里这样：**先在栈上用局部变量 `loopCts` 抓住这一份 CTS，再让闭包捕获局部变量。** 局部变量不会被别的线程改掉，竞态自然消失。

> 这是我第一次真正理解"闭包捕获的是变量本身，不是当时的值"这句话的威力。

### 4.2 断开是怎么"停干净"的

```110:144:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolDriverBase.cs
public async Task DisconnectAsync()
{
    Task? loop;
    CancellationTokenSource? cts;

    lock (_sync)
    {
        cts = _loopCts;
        loop = _loopTask;
        _loopCts = null;
        _loopTask = null;
    }

    if (cts is not null)
    {
        await cts.CancelAsync().ConfigureAwait(false);
    }

    if (loop is not null)
    {
        try
        {
            await loop.ConfigureAwait(false);
        }
        catch (OperationCanceledException)
        {
            // 正常取消
        }
    }

    cts?.Dispose();

    await OnDisconnectAsync().ConfigureAwait(false);
    State = ConnectionState.Disconnected;
}
```

顺序是**先取字段、再取消、再等它跑完、最后 `Dispose`**：

- 在 `lock` 里只做"把字段取下、置空"这种**极短的操作**，`await` 全放到锁外面——**锁里绝不能有 `await`**，否则等于长时间占着门。
- `await loop` 是关键：**确保后台任务真的结束了**再返回。否则会出现"你以为断开了，后台还在吐数据"。
- 最后才 `Dispose` CTS。顺序反了会抛 `ObjectDisposedException`。

（顺带一提，`Dispose()` 里也做了一套同样的清理，并且 `catch (ObjectDisposedException)` 兜底——因为"重复释放"在容器生命周期里几乎必然发生。）

### 4.3 长循环里的取消检查，要不要每次都查？

看商品查询里最耗时的那个循环：

```104:113:c:/code/WpfStudy/CommunityToolkitDemo/Services/ProductQueryService.cs
var items = new List<Product>(Math.Min(limit, 256));
var skipped = 0;

for (var i = 0; i < source.Count; i++)
{
    // 每 1024 项检查一次取消：对 10w 规模足够灵敏，检查本身也不构成开销
    if ((i & 0x3FF) == 0)
    {
        cancellationToken.ThrowIfCancellationRequested();
    }
```

`(i & 0x3FF) == 0` 就是 **`i % 1024 == 0`**，用位运算是因为更快也更直观地表达"每 1024 次一次"。

**为什么不是每一项都查？** `ThrowIfCancellationRequested()` 本身也有开销（读一下字段、判断、可能抛异常的分支）。在 10 万次循环里逐次调用，就是 10 万次额外操作；而每 1024 次查一次，最多晚 1024 项响应取消——对 10 万规模来说仍然是"瞬间"。

这是个很典型的取舍：**取消的"灵敏度"和"检查开销"要找平衡点**，不是越勤越好。

## 五、跨线程可见性：`State` 为什么写成 `int`

这一节稍微硬一点，但它是"从能跑升级到不容易出诡异 bug"的分水岭。

看驱动的状态字段：

```18:30:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolDriverBase.cs
/// 状态字段，按底层类型 <see cref="int"/> 存放。
/// </summary>
/// <remarks>
/// 为什么不用 <see cref="ConnectionState"/> 直接加 volatile？
/// <see cref="Volatile"/> 的泛型重载要求 <c>T : class</c>（枚举不满足），
/// 而 <c>volatile</c> 关键字也不允许用于枚举字段。
/// 因此这里以 int 存放，再配合 <see cref="Volatile"/> 读写：
/// <see cref="State"/> 会被后台仿真循环线程写入、被 UI 线程读取，
/// 枚举底层是 int、读写本身原子，但没有内存屏障时读线程可能长期看到旧值
///（JIT 可以把字段缓存在寄存器中）。
/// </remarks>
private int _state = (int)ConnectionState.Disconnected;
```

配套的属性读写：

```50:63:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolDriverBase.cs
public ConnectionState State
{
    get => (ConnectionState)Volatile.Read(ref _state);
    private set
    {
        if (Volatile.Read(ref _state) == (int)value)
        {
            return;
        }

        Volatile.Write(ref _state, (int)value);
        StateChanged?.Invoke(this, value);
    }
}
```

三个知识点：

1. **枚举不能用 `volatile` 关键字**（C# 限制），泛型版的 `Volatile.Read<T>` 又要求 `T` 是引用类型。所以只能退成 `int` 存取——好在枚举底层本来就是 `int`。
2. **光有原子性不够，还需要内存屏障**。`Volatile.Read/Write` 除了保证读写不可分割，还会插入屏障，防止 JIT 把字段缓存进寄存器导致"读线程永远看到旧值"。这类 bug 极难复现，一旦出现就是"程序偶发失灵"。
3. **用 `Volatile.Read` 做"值没变就不通知"的短路**，避免重复触发 `StateChanged`。

至于注释里坦白的那个"已知不完美"：

```44:49:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolDriverBase.cs
/// <summary>当前连接状态（跨线程安全读）。</summary>
/// <remarks>
/// 说明：判断与写入之间没有加锁，两个线程同时切换状态时理论上可能各触发一次
/// <see cref="StateChanged"/>。这里的订阅方都是幂等的状态同步逻辑，重复一次无害，
/// 因此为避免在热路径上加锁而保留当前实现。
/// </remarks>
```

**判断和写入之间没有加锁，理论上可能重复触发一次事件——但因为订阅方是幂等的，重复一次无害，所以为了热路径性能就保留了。**

这就是我在项目里学到的态度：**不要为了"绝对正确"而在热路径上无脑加锁；先把"出错的后果"算清楚，如果后果可接受，就用更轻的方案，并把它写进注释。**

## 六、回 UI 线程的唯一入口：`UiDispatcher`

这个文件只有 46 行，但它是整个项目线程安全的关键。

```25:45:c:/code/WpfStudy/CommunityToolkitDemo/Common/UiDispatcher.cs
public static void Post(Action action)
{
    ArgumentNullException.ThrowIfNull(action);

    var dispatcher = Current;

    if (dispatcher is null)
    {
        Debug.WriteLine("[UiDispatcher] 无 Application，action 将在当前线程同步执行（仅测试/设计器场景）。");
        action();
        return;
    }

    if (dispatcher.CheckAccess())
    {
        action();
        return;
    }

    dispatcher.InvokeAsync(action);
}
```

三个分支，各自都有理由：

| 分支 | 场景 | 行为 |
| --- | --- | --- |
| `dispatcher is null` | 单元测试、XAML 设计器（没有 `Application.Current`） | 就地同步执行，保证测试里能直接观察集合变化 |
| `CheckAccess() == true` | 调用方**本来就在** UI 线程 | 直接执行，**省掉一次 Dispatcher 排队** |
| 其它 | 真正的后台线程 | `InvokeAsync` 投递，**不阻塞后台线程** |

**为什么是 `InvokeAsync` 而不是 `Invoke`？**

`Invoke` 是**同步**的：后台线程会一直等到 UI 线程执行完才继续。如果 UI 线程正忙（比如在等一个锁），后台线程就被卡住，严重时互相等待形成死锁。

`InvokeAsync` 是**投递即返回**：后台线程把活交给 UI 线程就继续干自己的事。项目里所有跨线程更新都用它。

**那个 `Debug.WriteLine` 也不是随手写的。** 它的注释解释得很清楚：没有 `Application` 时会在当前线程**静默**执行，万一将来出现"后台线程直改 UI 集合"的问题，这里会悄悄放过——所以显式打一条日志便于定位。

> 这个小细节我特别想强调：**"能兜底的分支"一定要留一条可观测的痕迹**，否则它会变成 bug 的藏身处。

**注意桥接器里的过滤条件放在 `Post` 外面。** 因为 `frame.Type`、`frame.Direction` 这些判断不碰任何 UI 对象，完全可以在后台线程做完；真正需要回 UI 线程的，只有 `_messenger.Send(...)` 这一句。**能在后台做的判断，别丢给 UI 线程做**——这跟上一篇的原则一脉相承。

> 为什么"消息发送"要回 UI 线程？因为接收方（比如收银台）收到 `BarcodeScannedMessage` 后会直接往 `ObservableCollection` 里加购物车项。所以必须在 UI 线程上"发"，接收方才能安全地"改"。

### 姿势 B：高频数据——入队 + UI 计时器批量刷新

姿势 A 有个前提：**事件频率不高**。可设备报文是"高频"的——5 个驱动、每个按 `IntervalMs` 吐数据，如果每一帧都 `Post` 一次，那就是"每帧一次线程切换 + 一次 UI 操作"。

清仓逻辑：

```235:266:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/DeviceMonitorViewModel.cs
private void FlushPendingFrames()
{
    if (_pendingFrames.IsEmpty)
    {
        return;
    }

    int processed = 0;

    while (_pendingFrames.TryDequeue(out var frame))
    {
        processed++;
        UpdateMetrics(frame);

        if (IsLogPaused)
        {
            continue;
        }

        Logs.Add(frame);
    }

    // 计数一次性累加，避免逐帧触发属性通知
    FrameCount += processed;

    // 环形缓冲：一次性裁剪超出部分，避免逐条 RemoveAt(0) 造成反复位移与重排
    int overflow = Logs.Count - MaxLogItems;
    for (int i = 0; i < overflow; i++)
    {
        Logs.RemoveAt(0);
    }
}
```

**这个方案的收益是量化的：** 不管后台 150ms 内塞进来 1 条还是 100 条报文，UI 线程都只被唤醒一次、只做一轮刷新。线程切换次数从"O(报文数)"降到"O(1)"。

### 为什么用 `ConcurrentQueue` 而不是 `Queue`？

因为它是**唯一被两个线程同时碰的集合**：后台线程 `Enqueue`，UI 线程 `TryDequeue`。普通 `Queue<T>` 在这种情况下会数据损坏；`ConcurrentQueue<T>` 是无锁（lock-free）实现，专门干这个。

**注意 `_pendingFrames` 是唯一一个"跨线程共享"的集合。** 项目里其它所有 `ObservableCollection`（`Metrics`、`Logs`、`Cards`）都严格只在 UI 线程上操作——`FlushPendingFrames` 是 `DispatcherTimer.Tick` 触发的，天然在 UI 线程。

> 这一条判断标准很好用：**看到 `ObservableCollection`，就问一句"它有没有可能在非 UI 线程被改"，答案必须永远是否。** 看到 `ConcurrentQueue`，就说明这里确实有跨线程共享，是有意为之。

## 八、批量刷新里的四个"顺手优化"

`FlushPendingFrames` 这个函数看着普通，但每一行都在防着"通知风暴"。这几条我在上一篇也提过，这里从**线程**角度再补一层。

**1）`FrameCount += processed`——计数一次性累加。**

如果写在循环里 `FrameCount++`，每条报文都会触发一次 `PropertyChanged`。50 条报文就是 50 次通知、50 次绑定刷新。改成"先累计、循环后加一次"，通知次数从 N 次变成 1 次。

**2）环形缓冲一次性裁剪。**

`Logs.RemoveAt(0)` 每次都要把后面所有元素往前挪。如果循环里逐条删，50 条溢出就是 50 次 O(n) 位移。**先把溢出量算出来（`int overflow = ...`），再一次性裁掉**，视觉上还避免了中间态闪烁。

**3）值没变就不通知。**

```292:301:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/DeviceMonitorViewModel.cs
// 值未变化就不触发属性通知与高亮，避免无意义的 UI 刷新
if (string.Equals(item.Value, value, StringComparison.Ordinal))
{
    continue;
}

item.Value = value;
item.UpdatedAt = frame.Timestamp;
item.IsFlashing = true;
```

设备很爱重复上报同一个值。这里用 `Ordinal`（序数比较，比区域性比较快）先比一次，值相同就 `continue`，一个通知都不发。

**4）一个计时器统一清除闪烁标记。**

```53:58:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/DeviceMonitorViewModel.cs
// 单一计时器统一清除闪烁标记，避免每个数据项各自开计时器
_flashTimer = new DispatcherTimer(DispatcherPriority.Background)
{
    Interval = TimeSpan.FromMilliseconds(450)
};
_flashTimer.Tick += (_, _) => ClearFlashing();
```

如果每个数据项都自己开一个计时器来"取消高亮"，100 个指标就是 100 个 `DispatcherTimer`，UI 线程会被它们的回调切碎。**改成"一个计时器扫一遍、把亮着的关掉"**，计时器数量恒为 1。

> 注意两个计时器都设了 `DispatcherPriority.Background`。意思是"闲着的时候再跑"，优先让用户的点击、滚动这类交互先处理。**给后台刷新任务降优先级，是 WPF 里非常便宜又好用的一招。**

## 九、`async/await` 的续体到底在哪个线程？

这是我认为**最值得讲清楚**的一个知识点，因为 `async/await` 把线程切换藏得太好了，以至于很多人以为它是"魔法"。

**规则一句话：`await` 之后接着执行的代码（续体）跑在"原来的同步上下文"上。**

- 在 UI 线程里 `await` → **续体回到 UI 线程**（终于可以放心改 `ObservableCollection`）；
- 在 `ConfigureAwait(false)` 之后 → **续体不再回原上下文**，谁空闲的线程池线程接手都行。

两个例子对照着看：

**例 1：ViewModel 里 `await` 完可以直接改集合。**

```338:344:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/CashierViewModel.cs
try
{
    var sent = await _protocols.RequestBarcodeScanAsync();

    Messenger.Send(new StatusNotificationMessage(
        sent ? "已向扫码枪下发扫码指令…" : "扫码枪未连接，请先到「设备监控」页连接串口设备",
        sent ? StatusNotificationMessage.StatusLevel.Info : StatusNotificationMessage.StatusLevel.Warning));
```

`RequestBarcodeScanAsync()` 内部一路 `ConfigureAwait(false)` 跑在线程池上；但 `await` 回到 `CashierViewModel` 时，续体被送回 UI 线程——所以后面的 `Messenger.Send(...)` 是安全的。

**例 2：服务层和协议层一律 `ConfigureAwait(false)`。**

```54:64:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolManager.cs
public async Task ConnectAllAsync()
{
    // 各驱动相互独立，可并行连接；单个失败不影响其它驱动（逐个隔离异常）。
    await Task.WhenAll(_drivers.Select(ConnectSafelyAsync)).ConfigureAwait(false);
}

public async Task DisconnectAllAsync()
{
    // 并行断开，缩短应用退出时的等待时间。
    await Task.WhenAll(_drivers.Select(DisconnectSafelyAsync)).ConfigureAwait(false);
}
```

这些类**根本不关心 UI**，没有理由为了"回 UI 线程"多付一次调度成本，所以全部 `ConfigureAwait(false)`。

**判断口诀：**

- 这段代码**最终要碰 UI**？→ **不要**加 `ConfigureAwait(false)`（保持回 UI 线程）。
- 这段代码**只是纯计算/IO，纯库代码**？→ **加** `ConfigureAwait(false)`（省一次调度）。

**反过来说：如果你在服务层写了 `ConfigureAwait(false)`，那调用方就不能假设"`await` 回来时还在 UI 线程"。** 好在项目里的服务层都是"返回值"型的（返回 `ProductQueryResult`、`bool` 等），由 ViewModel 在 UI 线程上消费结果，边界很清楚。

## 十、"搬走"的两个真实例子

### 10.1 把 943 毫秒的解析搬走

```126:131:c:/code/WpfStudy/CommunityToolkitDemo/Services/MarkdownDataService.cs
// 解析是 CPU 密集操作：await 的续体默认回到调用方的同步上下文（此处是 UI 线程），
// 若在续体里直接解析，10 万行的耗时（实测约 0.9 s）会整段冻结界面。
// 因此把"打开文件流 + 流式解析 + 映射实体"整体放进线程池，主流程只 await 结果。
var (items, truncated) = await Task.Run(
    () => ParseFile<T>(path, map),
    cancellationToken);
```

这段注释里有一句特别关键：**"await 的续体默认回到调用方的同步上下文（此处是 UI 线程）"**。

意思是：如果你写 `await SomethingAsync()` 然后**在下一行做耗时同步操作**，那这段耗时操作实际上还在 UI 线程上！这正是很多人"明明 await 了还是卡"的原因。

`Task.Run` 的作用就是把"真正耗时的那坨活"整体丢到线程池，让它在**别的线程**上跑完。

### 10.2 阈值 2000 是怎么来的

```25:29:c:/code/WpfStudy/CommunityToolkitDemo/Services/ProductQueryService.cs
/// <summary>源规模超过该值时，关键字过滤移到线程池执行。</summary>
/// <remarks>
/// 阈值取 2000：低于它时单次过滤在亚毫秒级完成，线程切换（含上下文捕获）反而不划算。
/// </remarks>
private const int BackgroundThreshold = 2000;
```

```59:68:c:/code/WpfStudy/CommunityToolkitDemo/Services/ProductQueryService.cs
if (source.Count <= BackgroundThreshold)
{
    return Task.FromResult(Filter(source, keyword, offset, limit, cancellationToken));
}

// 关键字过滤是"3 字段 × 忽略大小写"的 CPU 密集比较，10w 规模下远超单帧预算。
// 放到线程池：调用方 await 返回的 Task，续体在其原始上下文（UI 线程）中执行。
return Task.Run(
    () => Filter(source, keyword, offset, limit, cancellationToken),
    cancellationToken);
```

**这里体现的是一个很容易被忽略的事实：多线程不是免费的。**

把活搬到线程池，至少要付这些成本：任务排队、线程唤醒、可能的上下文捕获、`Task` 对象分配。如果活本身只要 0.1 毫秒，那你花在"搬运"上的时间比"干活"还多。

**2000 这个数字就是这么来的：低于它单次过滤亚毫秒级，搬了反而更慢；高于它（比如 10 万条）能省下 30 毫秒以上的冻结，就必须搬。**

> 这也是项目里唯一带"阈值"的地方——**说明这个开关是权衡出来的，不是拍脑袋的**。

## 十一、并行：`Task.WhenAll` 的两个用法

**用法一：一键连接全部设备。**

```54:58:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolManager.cs
public async Task ConnectAllAsync()
{
    // 各驱动相互独立，可并行连接；单个失败不影响其它驱动（逐个隔离异常）。
    await Task.WhenAll(_drivers.Select(ConnectSafelyAsync)).ConfigureAwait(false);
}
```

配合"异常隔离"的包装方法：

```66:77:c:/code/WpfStudy/CommunityToolkitDemo/Protocols/ProtocolManager.cs
/// <summary>连接单个驱动并隔离异常，避免一个设备失败拖垮整体连接。</summary>
private static async Task ConnectSafelyAsync(IProtocolDriver driver)
{
    try
    {
        await driver.ConnectAsync().ConfigureAwait(false);
    }
    catch (Exception ex)
    {
        Debug.WriteLine($"[协议] {driver.Name} 连接失败：{ex.Message}");
    }
}
```

**为什么必须包一层 try/catch？** 因为 `Task.WhenAll` 的语义是"**有一个抛异常，`WhenAll` 返回的 Task 就失败**"。如果其中 1 个设备连不上，`await Task.WhenAll(...)` 会直接抛异常，后面 4 个设备的连接**结果就看不到了**。

包装之后，每个驱动"自己的失败自己吞"，5 个设备互不影响，最后统一成功返回。

**用法二：结算后三个外设并行下发。**

```42:53:c:/code/WpfStudy/CommunityToolkitDemo/Services/CheckoutCoordinator.cs
public async Task<OrderFollowUpResult> CompleteAsync(Order order, bool openCashBox)
{
    var printTask = _protocols.PrintReceiptAsync(order);
    var cashBoxTask = openCashBox ? _protocols.OpenCashBoxAsync() : Task.FromResult(false);
    var uploadTask = _protocols.PublishOrderAsync(order);

    // 用 WhenAll 的返回值取值，而不是各任务上再读 .Result：
    // 后者容易被误读为"同步阻塞"（sync-over-async）而引发无谓的改造。
    var results = await Task.WhenAll(printTask, cashBoxTask, uploadTask);

    return new OrderFollowUpResult(results[0], results[1], results[2]);
}
```

**小技巧：先启动、后 `await`。**

三行 `var xxxTask = ...` 就已经把三个任务**同时启动了**，等到 `await Task.WhenAll(...)` 才统一收结果。总耗时 ≈ 最慢那个，而不是三个相加。

**另一处细节：用 `Task.WhenAll` 的返回值 `results[0..2]`，而不是回头读 `printTask.Result`。**

`Task.Result` 是同步阻塞读——在 UI 线程上读一个没完成的任务，会直接**死锁**（这就是经典的 sync-over-async）。而 `WhenAll` 已经把结果都收齐了，从数组里取是零风险的。

> 顺便说，`App.xaml.cs` 的注释也点名批评过这种写法：

```56:62:c:/code/WpfStudy/CommunityToolkitDemo/App.xaml.cs
// 先显示窗口，再做数据加载与设备连接：
// 替换旧的 sync-over-async（GetAwaiter().GetResult()）写法，避免阻塞 UI 线程导致启动白屏。
var window = Services.GetRequiredService<MainWindow>();
window.DataContext = Services.GetRequiredService<MainWindowViewModel>();
window.Show();

_ = InitializeAsync();
```

启动时把 `InitializeAsync()` **fire-and-forget** 掉，窗口立刻显示，数据加载和设备连接在后台慢慢来。

但 fire-and-forget 有个大坑：**异常会静默丢失**。所以 `InitializeAsync` 内部自己包了 try/catch，并把失败通过提示条告诉用户：

```83:90:c:/code/WpfStudy/CommunityToolkitDemo/App.xaml.cs
Debug.WriteLine($"[启动] 初始化失败：{ex}");

// 启动阶段的失败如果只写 Debug，用户看到的是"界面空白且毫无提示"，无从排查；
// 因此同时经全局提示条告知（主窗口此时已显示，提示条可直接呈现）。
NotifyStatus($"应用初始化失败，部分数据可能不可用：{ex.Message}", StatusNotificationMessage.StatusLevel.Error);
```

**这算是 `_ = SomethingAsync()` 写法的标准姿势：要么内部兜异常，要么观察返回的 Task。绝对不要"丢了就不管"。**

## 十二、什么时候必须"断线"——退出与页面切换

多线程最容易被忽视的一面：**不管好收尾，后台线程会一直在跑。**

### 12.1 离开页面：退订 + 停表

```200:211:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/DeviceMonitorViewModel.cs
/// <summary>离开页面立即退订，避免后台报文继续驱动界面刷新。</summary>
protected override void OnDeactivated()
{
    _manager.FrameReceived -= OnFrameReceived;
    _manager.DriverStateChanged -= OnDriverStateChanged;

    _flashTimer.Stop();
    _flushTimer.Stop();
    ClearFlashing();

    base.OnDeactivated();
}
```

这里干了三件事：**退订阅**（断掉后台 → 我的通道）、**停计时器**（断掉 UI 定时刷新）、**清掉残留的高亮状态**（否则下次进来还亮着）。

对应的 `OnActivated` 是反向操作：

```187:198:c:/code/WpfStudy/CommunityToolkitDemo/ViewModels/DeviceMonitorViewModel.cs
protected override void OnActivated()
{
    base.OnActivated();

    _manager.FrameReceived += OnFrameReceived;
    _manager.DriverStateChanged += OnDriverStateChanged;

    SyncCardStates();
    _flashTimer.Start();
    _flushTimer.Start();
}
```

**这是 `ObservableRecipient` 给的一对生命周期钩子，配合"单例 ViewModel + 页面切换"简直是绝配。** 页面在后台时，报文一条都不会处理；切回来的瞬间 `SyncCardStates()` 补一次状态，界面上看不出差别。

### 12.2 退出应用：先退订，再停后台，最后释放

```104:128:c:/code/WpfStudy/CommunityToolkitDemo/App.xaml.cs
protected override void OnExit(ExitEventArgs e)
{
    // 先退订协议事件（Dispose 幂等，容器随后还会再释放一次，重复调用安全）
    _bridge?.Dispose();
    _bridge = null;

    // 再断开全部协议驱动（优雅停止后台仿真循环），最后释放容器内所有单例
    if (Services.GetService<IProtocolManager>() is { } manager)
    {
        try
        {
            manager.DisconnectAllAsync().GetAwaiter().GetResult();
        }
        catch (Exception ex)
        {
            Debug.WriteLine($"[退出] 断开协议失败：{ex.Message}");
        }
    }

    // 释放主窗口/页面 ViewModel：退订事件、停止计时器、注销消息订阅
    (Services.GetService<MainWindowViewModel>() as IDisposable)?.Dispose();

    // 释放实现了 IDisposable 的服务（协议管理器 / 各驱动等）
    (Services as IDisposable)?.Dispose();
    base.OnExit(e);
}
```

**顺序非常重要：退订 → 停后台 → 释放。**

如果顺序反过来（先释放，再停后台），后台线程可能在对象已经被释放之后还触发一次事件，直接崩在退出路上。

还有一点值得说：这里用了 `GetAwaiter().GetResult()`——**这正是前面被批评的 sync-over-async**。但在 `OnExit` 里它是**可以接受**的：

- 此时不会再有 UI 交互，阻塞 UI 线程不会造成"界面卡住"的观感问题（窗口已经在关了）；
- 需要**确保**驱动真的停干净了才继续释放。

**所以"sync-over-async 是坏习惯"不是绝对禁令，而是一个需要结合场景判断的取舍。** 关键是要在代码里说清为什么这里可以。

## 十四、给你的一张"线程检查清单"

写完这一篇，我给自己整理了 5 个问题。以后每写一个事件回调、每写一个 `async` 方法，我都会过一遍：

| 检查项 | 要问的问题 | 不满足会怎样 |
| --- | --- | --- |
| ① UI 亲和性 | 这段代码会碰 `ObservableCollection` / 控件 / 绑定属性吗？ | 后台线程直接抛 `InvalidOperationException` |
| ② 耗时 | 单次执行会超过 16.7 ms 吗？ | UI 冻结掉帧（10 万行解析实测 943 ms） |
| ③ 频率 | 这个回调会被高频触发吗？ | 逐次切线程，UI 被切碎 |
| ④ 可取消 | 有没有"用户能中止/能退出"的长任务？ | 退出卡顿、资源泄漏 |
| ⑤ 生命周期 | 订阅方退订了吗？计时器停了吗？ | 离开页面还在跑，内存与 CPU 双涨 |

**一句话总结这张表：**

> **碰 UI 的，拉回 UI 线程；耗时的，推到后台线程；高频的，攒一批再刷；长跑的，给它一个取消令牌；订阅了，记得退订。**

## 十五、这一篇最想让你带走的三句话

1. **UI 线程只有一条，它是稀缺资源。** 你所有优化的目标，都是让它只做"必须由它做的事"——也就是"碰 UI 对象"这一件。
2. **`async/await` 不是"自动开线程"。** 它只是"等待时不占线程"。真正让耗时操作离开 UI 线程的是 `Task.Run`；而 `await` 的续体，默认是回到原来的上下文（在 UI 代码里就是回到 UI 线程）。
3. **跨线程的共享集合只应该有一个，而且应该是线程安全的那个。** 项目里就是 `_pendingFrames`（`ConcurrentQueue<ProtocolFrame>`）。看到 `ObservableCollection`，永远假设它只能在 UI 线程上改。

---
