# 项目快速认知方法论

> 刚入职新公司 / 接手新项目时，快速了解 GitHub 或本地项目的完整方法论。
> 核心心法：**先地图后领土、先广度后深度、带问题学习、以输出倒逼输入**。

---

## 一、核心心法（四条）

| 心法 | 含义 | 反例 |
|---|---|---|
| **BFS 广度优先** | 像走迷宫先看整体地图，再决定往哪条路走 | 打开文件就逐行读，一天后还在第一个模块 |
| **假设驱动** | 先根据命名/文档猜"它大概是做什么的"，再用代码验证 | 无目的浏览，看完即忘 |
| **20% 代码承载 80% 逻辑** | 任何项目核心链路就那么一两条，找到它们比通读全部更重要 | 平均用力，把时间花在工具类代码上 |
| **以输出倒逼输入** | 学完必须能讲出来/写出来（画图、笔记、复述、给团队讲） | 只看不输出，以为懂了实际没懂 |

---

## 二、七个维度，由表及里

### 维度 1：定位与价值 —— "这是个什么东西？"
第一层，30 分钟以内搞定，不需要打开任何代码。

- **README**：项目自述最诚实的地方，看它怎么介绍自己（注意和实际代码是否一致，不一致本身就是信号）
- **官方文档 / Docs 目录**：架构说明、设计文档通常比代码更能回答"为什么"
- **项目元信息**：License、Star 数、创建时间、主要贡献者（贡献者是谁 → 团队构成）
- **一句话回答**：解决什么痛点？目标用户是谁？和竞品比差异点在哪？答不上来就继续看

### 维度 2：技术栈与依赖 —— "用什么材料造的？"
- 根目录的依赖清单文件（`package.json` / `pom.xml` / `go.mod` / `requirements.txt` 等）
- 重点看**版本分布**：主版本号、是否用了很新的特性（说明团队技术偏好）
- 看**锁文件**（`package-lock.json` 等）：锁定版本 → 工程严谨性
- 看 **Build 工具和配置**：Webpack/Vite/Gradle/CMake 的配置能告诉你项目复杂度和团队习惯
- **技术栈沉淀为一张表**：框架、语言版本、中间件（DB/缓存/MQ）、关键 SDK——这张表之后所有维度都要复用

### 维度 3：架构与模块 —— "房子怎么盖的？"
最关键的一层，决定后续所有效率。

- **目录结构是架构的第一现场**：从根目录开始一层层看，先看第一层就停，脑内画出目录树
- **识别分层模式**：经典分层（Controller/Service/DAO）、领域驱动、微服务、插件化……识别出模式后，以前的架构知识就能迁移
- **找"三入口"**：
  - 进程入口（`main` / `index.js` / `App.tsx`）
  - 配置入口（配置文件、环境变量）
  - 路由/API 入口（请求如何分发）
- **看依赖方向**：谁依赖谁？有没有循环依赖？核心模块是哪几个？（用 IDE 的 import 分析、依赖图工具）
- 产出物：**一张架构图**（手画或用工具），不用精美，自己懂就行

### 维度 4：核心流程与数据流 —— "血液怎么流动的？"
架构是静态的，这一维度是动态的。**选 2~3 条最有代表性的业务链路**，追到底：

- **启动链路**：进程起来后发生了什么（初始化顺序、注册了哪些东西）
- **一次完整请求**：用户操作 → Controller → Service → DAO → 返回，中间经过哪些过滤、校验、缓存
- **数据链路**：数据库有哪些表 / 有哪些状态流转（订单状态机、任务状态机）
- **关键算法/逻辑**：项目最值钱的那块逻辑（推荐、计费、调度……）值得单独精读

实操技巧——**追链法**：从一个入口函数开始，用语义跳转/调用关系逐层往下，每层只记"输入输出和副作用"，画一张时序图。一次追完就掌握项目一半以上的知识。

### 维度 5：运行与调试 —— "怎么让它跑起来？"
**动手跑起来比读 100 页文档都有效**，因为会在运行时被迫理解真实的依赖关系。

- 按 README 的 Quick Start 走一遍，卡住了先看 `docs`、`Makefile`、`docker-compose.yml`
- 跑起来后**打断点**：在核心链路上打几个断点，实际数据流会直观展现在眼前，比静态读代码快 10 倍
- 学会用 **debugger + call stack** 反向看"我是谁调进来的"，快速建立全局认识

### 维度 6：工程化与质量 —— "怎么保证质量的？"
决定以后怎么在这个项目里干活：

- **测试体系**：测试目录结构、覆盖率、测试怎么写（好的测试就是活的文档）
- **CI/CD**：`.github/workflows` 或 `.gitlab-ci.yml` 里能看出发布流程、多环境配置
- **代码规范**：`.eslintrc` / `prettier` / `.editorconfig` / 格式化脚本
- **错误处理与日志**：统一错误码、日志规范（团队协作的隐形约定）

### 维度 7：演进与协作 —— "这个项目是怎么长大的？"
了解历史才知道现状为什么长这样，以及未来要往哪走：

- **Git 历史**：`git log --oneline --graph` 看提交节奏和分支策略；`git log --follow` 看某个关键文件怎么演化的
- **CHANGELOG / Release Notes**：版本迭代背后的决策
- **Issue 与讨论**：没文档的地方，Issue 里的讨论就是最真实的决策记录
- **团队约定**：Wiki、Confluence、飞书文档里的"团队规范"（命名、提交信息规范、Code Review 要求）
- **Roadmap**：了解项目将去向何方，才知道该往哪个方向深耕

## 三、四个可复用的高级技巧

**1. 假设-验证循环（最重要）**
看到目录名 `payment/` 就写下假设"这是支付模块，应该有订单、退款、对账"，然后只读关键文件验证。读代码时持续用这个循环：猜 → 验 → 修正 → 再猜。这比线性阅读高效得多，且留下的记忆更深。

**2. 费曼输出法**
学完一个模块，用一段话讲清楚："这个模块的职责是 X，入口是 A，它通过 B 调用了 C，数据最后落到 D，关键点是 E。"讲不清楚 = 没学明白，回去补。

**3. 类比迁移**
把新项目映射到最熟悉的项目上："这个 `OrderService` 就相当于我们之前项目的 `TradeService`，只是加了个状态机。"用已知的锚点理解未知，是最快的认知捷径。

**4. 画图沉淀**
架构图 + 时序图（核心链路）+ 数据模型图，三张图画完，对项目的理解就超过大部分入职半年的人。推荐用 mermaid、draw.io 或白板，画完就是你的知识资产。

## 四、落地 Checklist（入职第一周照着做）

| 时间 | 动作 | 产出 |
|---|---|---|
| **第 1 天上午** | 读 README/文档，跑通 Quick Start | 能启动项目、一句话说出项目定位 |
| **第 1 天下午** | 画目录树、标出技术栈、找出三个入口 | 架构图 v0.1 |
| **第 2 天** | 追一条核心链路（请求全流程） | 时序图 v0.1 |
| **第 3 天** | 读核心模块代码 + 数据模型 | 数据流图、核心逻辑笔记 |
| **第 4 天** | 看 Git 历史、CHANGELOG、Issue | 项目演进史摘要 |
| **第 5 天** | 找导师/同事讲一遍你的理解，领一个小任务 | 验证性反馈 + 第一个 PR |

## 五、经验提醒

- **不要试图读完所有代码**：很多项目 80% 的代码是边缘功能，把 20% 的核心链路读透，就已经能用、能改了
- **工具要会用**：现代 IDE 的语义跳转（跳定义/找引用/看调用图）、全文搜索、断点调试这三板斧，是探索代码库的"勘探工具"
- **遇到"不合理"代码先别吐槽**：记录疑问，问老员工"为什么这里要这样写"，答案往往涉及历史债务或业务约束，这恰恰是项目知识最值钱的部分
- **学会提问**：好的提问是"我看了 X 和 Y，觉得应该是 A，但看到 Z 时矛盾了，是不是因为 B？"——这比"这块代码什么意思"得到的回答质量高一个量级

---

## 总结

**先定位（这是啥）→ 再搭框架（怎么组织）→ 追链路（怎么运转）→ 动手验证（跑起来）→ 复述输出（真懂了）→ 融入协作（能干活了）**

把这六步走完，从"新人"到"能独立产出"，通常只需要一到两周。
